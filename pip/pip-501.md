# PIP-501: Scheduled delivery metadata for Java Functions and IO records

# Background knowledge

Java IO sources return `org.apache.pulsar.functions.api.Record<T>` instances. The Java runtime wraps
these records and publishes their values through `PulsarSink`, applying metadata such as the key,
destination topic, properties, and event time. Functions can also return a `Record` to specify output
metadata, or use `Context.newOutputRecordBuilder()` to construct one.

The Java client already supports `TypedMessageBuilder.deliverAt(long)`, which sets an absolute
delivery timestamp in message metadata. The broker schedules delivery according to its existing
delayed-delivery policies and the subscription type. Event time is independent of delivery time.

# Motivation

`Record` has no typed way to request scheduled delivery. Returning a user property with a timestamp
does not set the client delivery metadata. A source or function must publish explicitly through a
client or context builder to request delayed delivery, bypassing the normal record output path and
taking responsibility for coordinating publishing with source acknowledgement.

Expose the existing client capability through the record API so connectors and record-returning
functions can use scheduled delivery while retaining the runtime-managed publishing path.

# Goals

## In Scope

- An optional absolute delivery timestamp on the Java `Record` API.
- Propagation through Java runtime record wrappers and the `FunctionRecord` builder.
- Mapping to the existing client API before publishing, for both legacy and V5 client adapters.
- Defined absence, invalid-value, retry, and output-override semantics.

## Out of Scope

- Broker scheduling changes, new configuration, metrics, CLI flags, or wire fields.
- Connector-specific attribute names or parsing rules.
- Python and Go Functions APIs.
- Relative delays, exactly-once delivery across external systems, or global ordering by timestamp.
- Automatically rescheduling consumed Pulsar messages using their original wire delivery metadata.

# High Level Design

A record optionally declares the absolute time at which its output should become eligible for
delivery. The runtime carries this value through its record wrappers and applies it to the output
message builder before sending. Publishing completes when Pulsar acknowledges the send, not when
the scheduled time arrives or a consumer processes the message. Existing processing guarantees and
acknowledgement paths remain in place for successfully constructed output messages.

Returning an explicit output record makes that record authoritative: an absent output delivery time
clears any delivery request on the input. A function returning a plain value inherits the input
record metadata through the existing `SinkRecord` path.

# Detailed Design

## Design & Implementation Details

Add the following default method to `Record<T>`:

```java
default Optional<Long> getDeliverAtTime() {
    return Optional.empty();
}
```

The contract is:

- The value is a non-negative Unix epoch timestamp in milliseconds, matching `deliverAt(long)`.
- Empty means the runtime does not call `deliverAt`. User properties are not interpreted.
- Zero and past timestamps are valid and are passed through unchanged. They do not create a new
  relative delay. Retry and instance reassignment must not recompute the timestamp from the local clock.
- Negative values are invalid. Before constructing or sending the output message, the runtime records
  a sink exception, calls `fail()` on the source record, and skips that output. It does not deliberately
  throw a validation exception that would terminate the instance loop. If the source failure handler
  itself throws, existing runtime failure handling applies.
- Implementations must return a non-null `Optional`; exceptions thrown by a custom getter retain the
  existing behavior for exceptions thrown by record accessors.

`SinkRecord` delegates to its source record. `OutputRecordSinkRecord` delegates to its output record,
including when output encoding/decoding changes the schema. `PulsarFunctionRecord`, which exposes the
current record to user code, delegates to its wrapped record.

`FunctionRecord` gains an optional `Long deliverAtTime` field and the builder method
`deliverAtTime(Long)`. `FunctionRecord.from(context, schema)` copies the current record delivery time,
as it does other record metadata. A caller can override it or clear it with `deliverAtTime(null)`.
The runtime performs validation, including for records implemented outside this builder.

`PulsarSink.write()` reads the effective output record timestamp once, validates it, and calls
`TypedMessageBuilder.deliverAt()` before the existing processor sends the message. This is independent
of property forwarding and does not alter event time, destination selection, sequence IDs, or producer
cache keys. Each message gets its own builder; no cross-instance scheduling state is introduced.

`PulsarRecord` keeps the default empty value. This proposal is an explicit output scheduling request,
not an implicit copy of historical scheduling metadata from a consumed message. No client message
implementation casts are needed.

The runtime validates all processing modes, but cannot undo an earlier acknowledgement in
`ATMOST_ONCE`. External sources that require redelivery on failure should use `ATLEAST_ONCE`.
This feature does not extend the guarantees of any processing mode.

### Validation

Tests cover default absence, future/zero/past values, invalid negative values, independence from
property forwarding and event time, source and output wrapper precedence, builder inheritance and
clearing, and successful/failed publication acknowledgement. An invalid record must not prevent the
next valid record from being published. Client adapter coverage verifies timestamp forwarding.
Existing broker delayed-delivery tests remain authoritative for scheduling behavior; an end-to-end
test should verify the source-to-consumer path with a supported subscription before release.

## Public-facing Changes

### Public API

- `Record<T>.getDeliverAtTime(): Optional<Long>` with a default empty implementation.
- `FunctionRecord<T>.getDeliverAtTime()` and `FunctionRecordBuilder<T>.deliverAtTime(Long)`.

No existing public method signatures are removed or changed. No new public wire protocol,
configuration, CLI, or metrics are introduced.

# Monitoring

Use existing runtime sink exception reporting for invalid delivery times and publishing failures,
and existing source acknowledgement/failure reporting. Use broker delayed-message and backlog
observability to monitor scheduled messages. A successful send is not evidence of consumer delivery.

# Security Considerations

Publishing uses the same authenticated client and destination authorization as ordinary record
output. This adds no privileged operation. Long scheduling horizons can increase retained backlog
and delayed-message tracking costs. Existing broker policies, quotas, and expiry rules continue to
apply; a valid timestamp does not override those controls or guarantee retention until delivery.

# Backward & Forward Compatibility

## Upgrade

Existing record implementations inherit the default empty method and retain their behavior on the
new runtime. Before enabling delivery timestamps in a connector or function, upgrade every runtime
instance that can execute it, then deploy the feature-using artifact.

A default interface method is not a capability negotiation mechanism. An old runtime will not read
the new getter and may publish immediately. Code calling the new API or builder method can also fail
with linkage errors against an old API jar. Producers of feature-using artifacts must document the
minimum runtime version; mixed old/new runtimes are not supported for a scheduled-delivery guarantee.

## Downgrade / Rollback

Stop or replace feature-using connectors/functions before downgrading their runtimes. Drain pending
external records through an upgraded runtime or pause ingestion so they cannot be published early
by an old instance. Messages already published retain the ordinary Pulsar delivery metadata and
remain governed by the broker policies.

## Pulsar Geo-Replication Upgrade & Downgrade/Rollback Considerations

No replication protocol changes are introduced. Existing behavior for delayed-message metadata and
the destination cluster policies applies. This proposal adds no cross-cluster clock, ordering, or
exact-delivery-time guarantee.

# Alternatives

- **Reserved user property interpreted by the runtime:** avoids an API addition but couples arbitrary
  string properties to scheduling semantics, requires parsing, and risks changing existing data meaning.
- **Direct publication from connectors/functions:** existing context builders support it, but it bypasses
  the normal record output path and moves publish/ack coordination into application code.
- **An additional relative-delay getter:** retries or restarts could move the delivery time. An absolute
  timestamp is sufficient; applications can compute it once when creating the logical record.
- **Use event time:** event time describes the event and must not become a scheduling instruction.

# General Notes

The delivery timestamp is an eligibility request, not an exact execution deadline. Subscription
support, broker tracker precision/strictness, clock synchronization, backlog, and consumer availability
affect actual delivery. In particular, non-strict broker scheduling can allow delivery before the
requested timestamp. Connectors must not wait locally until the timestamp before publishing.

This proposal is a draft pending community discussion and approval. Implementation work is a draft
for review, not an accepted change.
