# PIP-496: Pulsar Functions and IO support for the V5 client and scalable topics

# Background knowledge

**Pulsar Functions and Pulsar IO** run user code — functions, sources and sinks, together called *components* —
in a function worker. The Java runtime reads a component's input topics, calls the user code and publishes the
results with the Pulsar Java client. There is one `PulsarClient` per runtime, shared by the instances it runs.
User code reaches the same client through its context (`Context.getPulsarClient()`, `newOutputMessage(...)`,
`newConsumerBuilder(...)`). The worker stores a component's configuration (`FunctionConfig`, `SourceConfig`,
`SinkConfig`) as the `FunctionDetails` protobuf message. The instances re-read it when they start, and in the
process and Kubernetes runtimes they receive it as JSON.

**Scalable topics** ([PIP-460](pip-460.md)) are a new topic type, named with the `topic://` domain. A scalable
topic is a DAG of hash-range *segments* (`segment://` topics) that split and merge as load changes. Segments are
an internal detail; clients address the parent `topic://` name.

**The V5 Java client** ([PIP-466](pip-466.md)) is the only client that can produce to and consume from scalable
topics. The v4 client (`org.apache.pulsar.client.api`) rejects `topic://` and `segment://` names. The V5 client
also reads and writes regular `persistent://` topics, which it presents as scalable topics with a *synthetic
layout*: one legacy segment for a non-partitioned topic, or one per partition for a partitioned topic. It does not
support `non-persistent://` topics. It replaces the v4 subscription types with two consumer models:

- **`QueueConsumer`**: unordered. It supports individual and negative acknowledgment, a processing timeout and a
  dead letter policy, and each segment is a Shared subscription.
- **`StreamConsumer`**: ordered per key, and acknowledged only cumulatively, with no negative acknowledgment.
  - A controller assigns segments, and the key ranges within a segment ([PIP-486](pip-486.md)), to the members of
    a *consumer group*, which it identifies by consumer name.
  - A V5 message id carries a position vector, the last delivered position of every segment. A cumulative
    acknowledgment of a message therefore acknowledges every segment up to that point.

**Regular-to-scalable topic migration** ([PIP-475](pip-475.md)) converts a `persistent://` topic into a scalable
topic in place. Unless forced, it refuses with HTTP 409 while any v4 producer or consumer is attached, because a
v4 client cannot follow the topic once it is scalable. A V5 client's producers and consumers on legacy segments
carry the `__pulsar.v5.managed=true` metadata, and the check does not count them.

The `pulsar-client` and `pulsar-perf` CLIs already pick the client from the topic domain: V5 for `topic://`, v4
otherwise. A `--client-api {V4,V5}` option lets the V5 client drive a `persistent://` topic.

# Motivation

The Functions and IO runtime uses the v4 client throughout. As a result:

1. **A function, source or sink cannot use a scalable topic.** A `topic://` input, output, log topic or dead
   letter topic fails when the instance starts. Scalable topics are the direction of Pulsar 5.0, and stream
   processing that cannot run on them is a gap users will hit as soon as they adopt them.
2. **Functions and connectors block migration.** Every function or connector attached to a `persistent://` topic
   holds a v4 consumer or producer on it, so PIP-475 migration of that topic fails with 409 until the component is
   stopped. There is no way to keep a pipeline running while its topics are migrated.
3. **User code has no V5 client.** A function that needs a scalable topic in its own code has to build and manage
   a client itself, duplicating the worker's authentication and TLS configuration.

# Goals

## In Scope

- The Java runtime reads and writes a component's topics with the V5 client when they are `topic://` topics,
  without any configuration.
- A per-component setting that makes the V5 client drive `persistent://` topics, so that PIP-475 can migrate
  them while a component with a Shared subscription keeps running.
- The component's subscription type and processing guarantees map onto the V5 consumer models, and the
  differences are stated precisely.
- User code can publish to `topic://` topics through the existing context API, and can use the runtime's V5
  client.
- Every combination that the V5 runtime cannot honor is rejected when the component is submitted, with a message
  that names the offending topic or setting.

## Out of Scope

- **The Python and Go runtimes.** They keep the v4 client, and the V5 setting is rejected for them.
- **V5 consumption of `persistent://` topics with an ordered subscription** (Failover, Key_Shared,
  EFFECTIVELY_ONCE). A V5 stream consumer registers with the topic's controller, and a `persistent://` topic has
  no controller until it is migrated, so the subscription fails. Lifting this belongs to the V5 client and broker.
  Until then, ordered components keep the v4 client until their topics are migrated (see *Migration*).
- **EFFECTIVELY_ONCE output with the V5 client.** It relies on producer deduplication by sequence id, and
  sequence ids are not monotonic across segment splits and merges.
- **Consumer and producer encryption, message payload processors, consumer properties, topic patterns,
  `skipToLatest`, and `SinkContext.seek`/`pause`/`resume`** with the V5 client. Each is rejected, and each can be
  added later without changing this proposal's interfaces.
- **Changing the default.** A component without `topic://` topics keeps the v4 client.

# High Level Design

**One client per component, picked from its topics.** A component's topics are its inputs, its output, its log
topic and its dead letter topic. The runtime uses the V5 client for all of them when any of them is a `topic://`
topic, and the v4 client otherwise. This is the rule the CLIs already follow. An optional `clientApi` setting
(`V4` or `V5`) overrides the choice: `V5` makes the V5 client drive `persistent://` topics. Mixing `topic://`
topics with other topics in one component is rejected, as is any setting the chosen client cannot honor. The
worker checks the rule when a component is created or updated, and each instance checks it again when it starts.

**Consumer models.** A component's configuration maps onto the V5 consumers as follows:

| Component setting | V5 consumer | Delivery and failure |
|---|---|---|
| Shared subscription (default) | `QueueConsumer` | Unordered. Individual ack, negative ack on failure, processing timeout (`timeoutMs`) and dead letter policy (`maxMessageRetries`, `deadLetterTopic`), as with v4. |
| `retainOrdering` (Failover) | `StreamConsumer` | Ordered per key. The instances share the segments. A failed record fails the instance. |
| `retainKeyOrdering` (Key_Shared) | `StreamConsumer` | Ordered per key. The instances share the segments and their key ranges. A failed record fails the instance. |
| `EFFECTIVELY_ONCE` input | `StreamConsumer` | Ordered per key. A failed record fails the instance, as with v4. |

The ordered rows differ from v4 in three ways:

- **Ordering is per key, not per topic.** A multi-segment topic has no total order, so `retainOrdering` gives the
  same per-key guarantee as `retainKeyOrdering`.
- **A failed record cannot be redelivered on its own.** A stream has no negative acknowledgment, so a failed
  record fails the instance, which restarts from the last acknowledged position.
  - A stopping instance leaves the consumer group, so the failed record's key range moves to another instance.
  - A record that keeps failing therefore fails one instance after another, and each failure rebalances the
    group.
- **Redelivery settings are rejected.** `timeoutMs`, `maxMessageRetries` and `deadLetterTopic` are rejected with
  ordered subscriptions, because a stream cannot honor them.

A stream acknowledges only cumulatively, so the runtime acknowledges the completed prefix of the received records,
in receive order. A record that completes early waits for the records received before it, and nothing past an
unfinished record is acknowledged. A record that is never completed or failed therefore holds back all later
acknowledgments of that input. On a stream input, a cumulative acknowledgment of a record
(`PulsarRecord.cumulativeAck()`) completes it and every record received before it. On a queue input, it
acknowledges only that record, since a queue has no cumulative acknowledgment.

**The same runtime, the same code paths.**

- **One shared V5 client.** The runtime owns one V5 client next to its v4 client. It is created on first use with
  the worker's service URL, authentication and TLS settings, and shared by the instances the runtime runs.
- **Records.** Records read with the V5 client are the runtime's existing Pulsar record type, backed by the v4
  view of the message.
- **Producers.** The output, the context's messages and the log topic use V5 producers behind the runtime's
  existing producer interfaces.

**User code.** `Context.newOutputMessage(...)` publishes to a `topic://` topic with the V5 client, in every
component and whichever client the component's own topics use. `BaseContext.getPulsarClientV5()` returns the
runtime's V5 client for everything else. These are the only user-facing API changes.

**Migration.** How a pipeline moves to scalable topics depends on its subscription type.

- **Shared subscriptions.** Set `clientApi=V5` on the components attached to a `persistent://` topic. This is an
  update, which restarts the instances. The Shared subscription keeps its cursor, because the V5 queue consumer
  uses the same subscription on the same topic. PIP-475 migration then succeeds without force.
- **Ordered subscriptions.** These components cannot use the V5 client on `persistent://` topics. Their input
  topics must be renamed to the `topic://` name after the migration, and input topics cannot be changed by an
  update. The procedure is:
  1. Update the component with `cleanupSubscription=false`, so that deleting it keeps its subscriptions.
  2. Stop the component. Its v4 clients detach, so the migration needs no force.
  3. Migrate its topics.
  4. Delete the component.
  5. Recreate it with the `topic://` names and the same subscription name.

  PIP-475 keeps the subscriptions' cursors, and the stream subscription drains the former partitions before their
  successors.

# Detailed Design

## Design & Implementation Details

### Client selection

`ClientApiResolver.resolve(FunctionDetails)` returns `V4` or `V5`. It collects the component's topics:

- the input topics, from `SourceSpec.inputSpecs` and the deprecated `topicsToSerDeClassName` (regex inputs are
  collected separately);
- `SinkSpec.topic`;
- `logTopic`;
- `RetryDetails.deadLetterTopic`.

It then applies these rules, in order:

1. A `segment://` topic is rejected, because segments cannot be addressed directly.
2. A `topic://` topic together with any other topic is rejected.
3. `clientApi=V4` with a `topic://` topic is rejected.
4. The result is `clientApi` when it is set, otherwise `V5` if there is a `topic://` topic and `V4` if not.
5. If the result is `V5`, it rejects:
   - a `non-persistent://` topic;
   - a topic pattern;
   - a runtime other than Java;
   - `EFFECTIVELY_ONCE` together with an output topic;
   - producer encryption;
   - `skipToLatest`;
   - an input with consumer encryption, a message payload processor or consumer properties;
   - for an ordered subscription (Failover, Key_Shared or `EFFECTIVELY_ONCE`) on `persistent://` inputs: always;
   - for an ordered subscription on `topic://` inputs: `maxMessageRetries`, `deadLetterTopic` or `timeoutMs`.

A rejection is an `IllegalArgumentException` whose message names the offending topic or setting, and the worker
returns it as HTTP 400 on create and update.

The batch-source intermediate topic is not one of the component's topics. It is internal to the runtime and always
`persistent://`.

**Invariant: the rules may only be relaxed.** An instance resolves again when it starts, so the rules are part of
the compatibility contract of stored components. A later version may relax any rule, for example once the V5 client
supports encryption. A tightened rule would stop stored components from starting after an upgrade.

The rules classify topic names as they are written: only a `topic://` name counts as scalable, and a name without a
domain is not `topic://` whatever the default domain is. A `persistent://` topic that PIP-475 has migrated is
still resolved as `persistent://`. A Shared component keeps working under that name with `clientApi=V5`, since the
V5 client follows the migrated topic. Changing its inputs to the `topic://` name takes deleting and recreating it,
because input topics cannot be changed by an update.

### Runtime

- **The V5 client.** `ThreadRuntimeFactory` is used by the thread, process and Kubernetes runtimes. It creates
  the V5 client on first use from the worker's client settings, and closes it with the factory.
  - **TLS:** the TLS policy is set only when TLS is enabled. The worker's configured hostname verification is
    always passed explicitly, so that both clients apply the worker's setting rather than their own defaults.
  - **Memory:** a configured client memory limit applies to the V5 client as well; each client gets its own limit.
    Without a configured limit, the V5 client keeps its default limit of 64 MiB.
  - **Class loading:** the V5 API finds its implementation once per JVM, through `ServiceLoader` on the thread
    context class loader. The runtime does this lookup when it starts, under its own class loader, so that the
    first V5 call from user code (which runs under the function's class loader) cannot fail it.
- **Consuming.**
  - One V5 consumer per input topic, as the runtime does with v4 consumers today.
  - Common to both consumer models:
    - The subscription name, the initial position and the instance's consumer metadata properties map as before.
    - The consumer name is `<tenant>-<namespace>-<name>-<instanceId>-<random>`, new on every start of an
      instance. A stream consumer group treats a second consumer with the same name as a reconnect of the first,
      so a reused name could let two live instances share an assignment.
    - A stopping instance leaves its stream consumer group, which rebalances immediately. This covers a
      parallelism reduction too. After an unclean exit, the instance's key ranges are reassigned when its
      session expires.
  - Queue consumers also map:
    - the receiver queue size;
    - `timeoutMs` to the processing timeout;
    - `negativeAckRedeliveryDelayMs` to a fixed negative-ack backoff;
    - `maxMessageRetries` and `deadLetterTopic` to the dead letter policy.
  - **Default dead letter topic:** without a configured `deadLetterTopic`, the runtime passes the v4 client's
    default, `<input>-<subscription>-DLQ`, in the input topic's domain.
    - For a non-partitioned input, switching a Shared component to the V5 client keeps its dead letter topic.
    - For a partitioned input, the v4 client derives one dead letter topic per partition
      (`<input>-partition-<n>-<subscription>-DLQ`), and the V5 client uses the single topic above. Consumers of
      the per-partition topics must follow the change.
    - For a `topic://` input, the dead letter topic must exist, because the V5 client does not create scalable
      topics.
- **Records.** A record read with the V5 client is the runtime's existing Pulsar record type, over the v4 message
  that the V5 message wraps.
  - The schema, the properties, the key, the event time and the encryption context behave as today.
  - `getTopicName()` returns the configured input topic.
  - `getMessage()` returns the v4 view of the message. Its topic is the internal segment (or the partition, for a
    partitioned `persistent://` topic), and its message id is the id within that segment.
  - `getPartitionId()` is `<input topic>-0`, and `getRecordSequence()` is derived from the segment's message id, so
    it is not monotonic across segments. Connectors that track offsets by partition id and sequence must not assume
    a single monotonic sequence per input topic.
  - `fail()` on a record of a stream subscription invokes the instance's fatal handler, from whatever thread calls
    it, and then throws to its caller.
- **Publishing.**
  - Producer settings map from `ProducerConfig`: compression, the batching delay, maximum messages and maximum
    bytes, and no send timeout, as today.
  - Settings with no V5 counterpart are ignored with a warning: the pending-message limits (the V5 client's memory
    limit bounds pending messages), the key-based batcher and the round-robin partition switch frequency.
  - A V5 producer writes with one schema, so a record whose schema differs from the producer's fails on send.
  - The message ids returned for published messages serialize in the V5 format, so they are restored with the V5
    `MessageId.fromByteArray`.
  - `keyBytes`, `orderingKey` and transactions are not supported on V5 output messages.
- **Worker.**
  - `cleanupSubscription` deletes a `topic://` input's subscription with the scalable topics admin API.
  - Triggering a function (`pulsar-admin functions trigger`) is rejected with 400 for `topic://` topics, because
    triggering uses the worker's v4 client.
  - The worker's own coordination topics are unchanged.

`org.apache.pulsar.client.impl.v5.V5Interop`, a new `@InterfaceAudience.Private` class in `pulsar-client-v5`,
gives the runtime the V5 client's existing schema adapters and the v4 message a V5 message wraps. It is not a
public API.

## Public-facing Changes

### Public API

**Java API.** One addition, as a `default` method, so that existing implementations of `BaseContext` keep
compiling:

```java
// org.apache.pulsar.functions.api.BaseContext
/**
 * The runtime's shared V5 client, created on first use. Use it to reach topic:// (scalable) topics. The
 * function must not close it.
 */
default org.apache.pulsar.client.api.v5.PulsarClient getPulsarClientV5() {
    throw new UnsupportedOperationException("not implemented");
}
```

Behavior changes of existing methods:

- `Context.newOutputMessage(...)` and `SourceContext.newOutputMessage(...)` publish to a `topic://` topic with the
  V5 client, in every component. Before this change they failed, because the v4 client rejects `topic://`.
- In a component whose own topics use the V5 client, `SinkContext.seek`, `pause` and `resume` throw
  `UnsupportedOperationException`, and `newOutputMessage` publishes every topic with the V5 client.
- `getPulsarClient()` and `newConsumerBuilder(...)` keep returning the v4 client. Clients that user code creates
  with them are v4 clients, and PIP-475 counts them.

**Admin API types.** A new enum, `FunctionConfig.ClientApi { V4, V5 }`, and a `clientApi` field of that type on
`FunctionConfig`, `SourceConfig` and `SinkConfig`.

- `null`, the default, means "pick from the topics".
- On update, a non-null value replaces the stored one and `null` keeps it.
- `V4` therefore also serves to take back a stored `V5`. For a component without `topic://` topics, `V4` behaves
  like the default.

**REST API.**

- The create and update endpoints of functions, sources and sinks accept `clientApi` in the component's
  configuration JSON, and the get endpoints return it. A rejected combination returns HTTP 400 with the resolver's
  message.
- `POST /admin/v3/functions/{tenant}/{namespace}/{functionName}/trigger` returns 400 for a function with a
  `topic://` input or output.

**Stored metadata.** `FunctionDetails` gains a field:

```protobuf
message FunctionDetails {
    // Pulsar client API that the Java runtime uses for the component's own topics.
    enum ClientApi {
        // V5 if any of the component's topics is a topic:// (scalable) topic, otherwise V4
        AUTO = 0;
        V4 = 1;
        V5 = 2;
    }
    ...
    ClientApi clientApi = 24;
}
```

**Packaging.**

- `pulsar-functions-api` depends on `pulsar-client-api-v5`, so the V5 client API is part of the Functions and IO
  API. Its published POM brings the V5 API's own dependencies: `pulsar-tls-factory-api`, `pulsar-http-client-api`
  and, through `pulsar-tls-factory-api`, the OpenTelemetry API.
- `java-instance.jar`, the parent class loader of user code in the process and Kubernetes runtimes, bundles the V5
  API but not the OpenTelemetry API. It already leaves OpenTelemetry out for the v4 client API, which names
  OpenTelemetry types in its signatures too.
  - This works because the V5 API modules only name OpenTelemetry types in method signatures and never run
    OpenTelemetry code. The client implementations, which do run it, are loaded by the instance class loader,
    which has it.
  - This is verified by reading the code; the process and Kubernetes runtimes have no end-to-end test yet.
- The in-tree connector NARs exclude `pulsar-client-api-v5`, `pulsar-client-v5`, `pulsar-tls-factory-api` and
  `pulsar-http-client-api`, which the runtime provides. Third-party NARs should treat these as provided, too.

### Binary protocol

No changes.

### Configuration

No broker or worker configuration changes. The V5 client uses the worker's existing client settings: the service
URL, the authentication plugin and parameters, the TLS settings, and the thread runtime's client memory limit.

### CLI

`pulsar-admin functions`, `sources` and `sinks` gain `--client-api {V4,V5}` on `create`, `update` and `localrun`,
with the same name and meaning as in `pulsar-client` and `pulsar-perf`.

### Metrics

No new metrics. The existing function, source and sink metrics apply unchanged to components that use the V5
client.

# Monitoring

A component's client choice is visible in its configuration (`clientApi`). On `persistent://` topics, the
publishers and consumers of a V5 component carry `__pulsar.v5.managed=true` in their metadata, which is what
PIP-475 checks. Before migrating a topic, operators can list the v4 clients still attached with the topic stats;
the 409 response of the migration gives their number.

# Security Considerations

- **Same credentials, same authorization model.** The V5 client authenticates with the same plugin, parameters
  and TLS settings as the runtime's v4 client. The broker authorizes it the same way; for a scalable topic,
  permissions apply to the parent `topic://` name ([PIP-466](pip-466.md)).
- **Same effective TLS behavior.** Hostname verification follows the worker's configured setting, passed
  explicitly, so the effective TLS behavior matches the v4 client's. An authentication plugin that supplies
  in-memory TLS key material, rather than files, cannot contribute it to the V5 client's TLS policy (see
  [PIP-478](pip-478.md)). File-based mutual TLS works.
- **No new endpoints or commands.** There are no new REST endpoints or protocol commands. `cleanupSubscription`
  for a `topic://` input uses the worker's existing admin client and permissions, as it already does for
  `persistent://` inputs.
- **Same sharing scope.** The V5 client is shared by the instances of one runtime, as the v4 client already is.
  In the thread runtime, that means all components on the worker, which run with the worker's identity in either
  case. `getPulsarClientV5()` exposes nothing that `getPulsarClient()` does not already expose.

# Backward & Forward Compatibility

## Upgrade

Stored components have no `clientApi` (`AUTO`) and use the v4 client unless one of their topics is a `topic://`
topic, which could not work before this change. No action is needed.

Before setting `clientApi=V5` on any component, upgrade:

- **every function worker.** An older worker may drop the unknown field 24:
  - Workers that parse the metadata with LightProto skip unknown fields, so they drop it whenever they rewrite
    the metadata: on an update, and when the leader writes assignments.
  - Every older worker rebuilds the metadata from the configuration on an update.
  - An older worker also drops `clientApi` from a configuration it receives, since it ignores unknown JSON
    properties.
- **the process and Kubernetes runtime images.** An older instance ignores `clientApi` and runs the v4 client.

## Downgrade / Rollback

An older worker runs every component with the v4 client, and may drop `clientApi` from any metadata it rewrites.

- A component with `topic://` topics fails to start, as it did before this change.
- A component with `clientApi=V5` on `persistent://` topics runs with the v4 client again. It blocks the migration
  of its topics again, and it cannot reach a topic that has already been migrated.

Before rolling back, stop the components whose topics have been migrated. After upgrading again, set `clientApi` again on components whose metadata an older worker rewrote.

## Pulsar Geo-Replication Upgrade & Downgrade/Rollback Considerations

None specific to this proposal. The client choice is local to a cluster's function workers and does not change
replication.

# Alternatives

- **One worker-wide switch.** A worker setting that moves every component to V5 cannot handle
  `non-persistent://` topics, topic patterns, or the Python and Go runtimes, none of which V5 supports. It would also
  force every component to move at once. Per-component selection lets each pipeline move when it is ready, and the
  domain rule means `topic://` components need no setting.
- **Always V5 for Java components.** This has the same limitations, and it changes the behavior of every existing
  component.
- **Map Key_Shared to a V5 queue consumer.** A queue consumer is Shared on every segment and does not keep key
  order, so a function relying on `retainKeyOrdering` would silently lose it. A stream consumer group keeps per-key
  order across instances.
- **Allow `topic://` and other topics in one component.** The V5 client serves `persistent://` topics too, so a
  component could read a `persistent://` topic and write to a `topic://` one, or keep a `persistent://` log topic.
  This proposal keeps the stricter rule of the CLIs: one domain per component, so that adding one `topic://` topic
  does not silently move the component's other topics to the V5 client. Relaxing the rule later is compatible;
  tightening it would not be. **This is an open question for the discussion.**
- **V5-typed runtime classes** (a V5 sink, a V5 record type, a V5 producer cache). They would duplicate the output
  and consumption paths. Presenting V5 producers and messages behind the runtime's existing interfaces keeps one
  code path, and connectors see the same record type as today.

# General Notes

## Resolved design decisions

**Cut**, each with its additive way back:

- **`Context.newOutputMessageV5(topic, v5Schema)`, and the same on `SourceContext`.** `newOutputMessage` routes
  `topic://` topics to the V5 client by the same domain rule as everything else. That needs no new method and no V5
  types in two stable interfaces.
  - *Add back:* a default method, if V5-only schema or message-builder features are needed.
  - *Tradeoff:* user code passes v4 `Schema`s and gets a v4 `TypedMessageBuilder` for `topic://` topics.
- **`BaseContext.getPulsarClientBuilderV5()`.** No consumer needs a second V5 client lifecycle, and the shared
  client covers access.
  - *Add back:* a default method.
  - *Tradeoff:* user code that needs its own client settings builds a client itself.
- **`Record.getMessageV5()`.**
  - Wrapper records, including the runtime's sink records, would each have to forward it.
  - The V5 message's value type follows V5 schemas while the record's type follows v4 schemas; for generic records
    they differ.
  - The main use, the V5 message id, is not actionable in user code.
  - *Add back:* a default method, with a forwarding contract.
- **An `AUTO` value in the admin enum**, to reset a stored `V5` to "pick from the topics".
  - `V4` takes back a stored `V5`, and it behaves like the default for components without `topic://` topics.
  - *Add back:* an additional enum value (the proto enum already has `AUTO`).
- **Consumer-builder shortcuts on the context.** `getPulsarClientV5().newQueueConsumer(...)` covers them.

**Kept**, with the reason:

- **Two enums**, the admin `ClientApi {V4, V5}` and the proto `ClientApi {AUTO, V4, V5}`. Proto3 needs a zero
  default, and the admin type uses `null` for it. This follows the `ProcessingGuarantees` and `Runtime` precedent.
- **Re-resolving at instance start.** It guards against metadata that did not come through the worker, such as
  LocalRunner configurations. The cost is the "rules may only be relaxed" invariant.
- **A new consumer name on every start.** A stable name would only help after an unclean exit, because a clean
  stop leaves the consumer group anyway, and it could let two live instances share one assignment. A stable name
  can be adopted later, since old random names simply expire.

## Related work

- The reference implementation also fixes a V5 client bug that it exposed. When two stream consumers joined a
  subscription at the same moment, the first one's initial subscribe retried with a stale assignment and never
  completed. The fix goes in its own pull request.
- Stream consumption of `persistent://` topics that have not been migrated needs V5 client and broker support for
  stream subscriptions on the synthetic layout. Once that exists, the resolver's "Shared only on `persistent://`"
  rule can be relaxed without other changes.
- [PIP-466](pip-466.md) lists Key_Shared under `QueueConsumer`. Since [PIP-486](pip-486.md), key-ordered
  consumption is a `StreamConsumer` feature, which is the mapping this proposal uses.
