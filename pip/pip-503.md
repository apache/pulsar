# PIP-503: Topic-scoped subscription permissions

**Summary.** Subscription permissions are namespace-scoped today: the roles granted for a subscription
name apply to that name on every topic of the namespace. This proposal adds subscription permissions
scoped to a single topic. For a topic and subscription, a topic-scoped entry takes precedence over the
namespace-scoped entry for the same subscription name; without one, the namespace-scoped entry applies
as today. The permissions are stored next to the existing topic-level permissions in the namespace
policies and managed with new `pulsar-admin topics` commands, REST endpoints and admin client methods
that mirror the namespace ones. Existing grants keep their current effect.

# Background knowledge

Pulsar authorizes a consumer in two steps (`PulsarAuthorizationProvider#canConsumeAsync`):

1. **Subscription permission.** The namespace policies hold a map from subscription name to roles,
   `auth_policies.subscription_auth_roles` (`AuthPolicies#getSubscriptionAuthentication()`). If the
   subscription name has a non-empty set of roles, only those roles may use it; if it has none, any role
   that may consume is allowed. With `subscription_auth_mode: Prefix`, the subscription name must also
   start with the role.
2. **Consume permission** on the topic, granted at namespace level (`auth_policies.namespace_auth`) or
   topic level (`auth_policies.destination_auth`, keyed by the partitioned topic name).

Both maps live in the namespace policies (`Policies#auth_policies`), which are stored in the
configuration metadata store. Subscription permissions are managed with
`pulsar-admin namespaces grant-subscription-permission`, `revoke-subscription-permission` and
`subscription-permission`, backed by the `AuthorizationProvider` methods
`grantSubscriptionPermissionAsync(NamespaceName, ...)`, `revokeSubscriptionPermissionAsync(NamespaceName, ...)`
and `getSubscriptionPermissionsAsync(NamespaceName)`.

A subscription belongs to exactly one topic, but its permission is keyed by its name only, so it applies
to every topic of the namespace that has a subscription with that name.

# Motivation

Because subscription permissions are namespace-scoped, they cannot express a permission for one
subscription of one topic. Issue #27578 gives an example: in one namespace, `topic1` has the
subscriptions `common-subscription` and `distinct-subscription`, and `topic2` has `common-subscription`.
To let role X consume `topic1` only through `common-subscription`, an operator would grant X
`common-subscription` and restrict `distinct-subscription` to other roles. Both settings then apply to
`topic2` as well, so the operator cannot give X a different set of subscriptions on `topic2`.
Operators either have to use globally unique subscription names, which they do not always control, or
split topics across namespaces.

The same limitation was raised in #21254. It was closed with the note that making subscription
permissions topic-scoped changes authorization semantics and the stored policy format, so it needs a PIP.

# Goals

## In Scope

- Allow granting, revoking and listing the roles of a subscription on a single topic.
- Define how topic-scoped and namespace-scoped subscription permissions combine, without changing the
  behavior of any existing grant.
- Add the corresponding `AuthorizationProvider` methods, admin REST endpoints, Java admin client
  methods and `pulsar-admin topics` commands.
- Remove the topic-scoped subscription permissions of a topic when the topic is deleted, as the
  topic-level permissions are today.

## Out of Scope

- Changing the namespace-scoped subscription permissions or `subscription_auth_mode`.
- Migrating existing namespace-scoped grants to topic scope.
- Subscription permissions in authorization providers other than `PulsarAuthorizationProvider`; they
  can implement the new methods, whose default implementations report that they are not supported.

# High Level Design

Add a topic-scoped subscription permission: for a topic and a subscription name, the set of roles that
may use that subscription on that topic.

When a consumer subscribes, the broker resolves the roles for the topic and subscription in this order:

1. If the topic has a topic-scoped entry for the subscription, it applies, and the namespace-scoped entry
   for that subscription name is not used for this topic.
2. Otherwise, the namespace-scoped entry applies, as today.
3. With neither, any role that may consume the topic may use the subscription, as today.

As with namespace scope, a non-empty set of roles restricts the subscription to those roles.
`subscription_auth_mode` and the consume permission are checked as today, whatever the scope of the
subscription permission.

In the example above, the operator grants X `common-subscription` on `topic1` and restricts
`distinct-subscription` on `topic1` to other roles, without affecting `topic2`:

```shell
# On topic1, only role X may use common-subscription, and only role Y may use distinct-subscription
pulsar-admin topics grant-subscription-permission persistent://tenant/ns/topic1 \
    --subscription common-subscription --roles X
pulsar-admin topics grant-subscription-permission persistent://tenant/ns/topic1 \
    --subscription distinct-subscription --roles Y

# List the topic-scoped rules of topic1: common-subscription -> [X], distinct-subscription -> [Y].
# topic2 keeps the namespace-scoped rules, if any, for its subscriptions.
pulsar-admin topics subscription-permission persistent://tenant/ns/topic1

# Remove the topic-scoped rule, so the namespace-scoped rule applies to topic1 again
pulsar-admin topics revoke-subscription-permission persistent://tenant/ns/topic1 \
    --subscription common-subscription --role X
```

The more specific entry wins so that an operator can narrow, or widen, the namespace-wide rule for one
topic. Existing namespace-scoped grants keep their current effect on every topic that has no
topic-scoped entry for the subscription.

# Detailed Design

## Design & Implementation Details

**Storage.** The topic-scoped permissions are stored next to the topic-level permissions
(`destination_auth`), in a new field of `AuthPolicies` in the namespace policies:

```java
@JsonProperty("topic_subscription_auth_roles")
Map<String, Map<String, Set<String>>> getTopicSubscriptionAuthentication(); // topic -> subscription -> roles
```

The key is the topic name; for a partitioned topic it is the partitioned topic name, so that a grant
covers every partition, as `destination_auth` does. `canConsumeAsync` already reads the namespace
policies, so the check needs no additional metadata read.

**Authorization.** `PulsarAuthorizationProvider#canConsumeAsync` resolves the roles as described above.
For a partition, the lookup uses the partitioned topic name. Operations on a single subscription of a
single topic go through this check. Namespace and bundle operations, which act on a subscription across
topics, are covered below.

**Management.** New `AuthorizationProvider` methods, with default implementations that fail with
"not supported", like the existing optional methods:

```java
default CompletableFuture<Void> grantSubscriptionPermissionAsync(TopicName topicName, String subscriptionName,
        Set<String> roles, String authDataJson);
default CompletableFuture<Void> revokeSubscriptionPermissionAsync(TopicName topicName, String subscriptionName,
        String role, String authDataJson);
default CompletableFuture<Map<String, Set<String>>> getSubscriptionPermissionsAsync(TopicName topicName);
```

`PulsarAuthorizationProvider` implements them by updating the namespace policies, as
`updateSubscriptionPermissionAsync` does for namespace scope. Revoking the last role of a subscription
removes its entry, and removing the last subscription of a topic removes the topic's entry, so the
policies do not keep empty maps.

**Revoking falls back to namespace scope.** Once the topic-scoped entry for a subscription is gone, the
namespace-scoped entry for that subscription name applies to the topic again, and without one any role
that may consume the topic may use the subscription. The fallback takes effect for the next subscribe or
subscription operation, as soon as the broker sees the updated namespace policies, like any other
permission change. This proposal does not change how a permission change affects consumers that are
already connected; topic-scoped changes behave as namespace-scoped ones do. A topic-scoped entry
cannot be emptied to mean "no role may use this subscription": an empty set of roles means no
restriction at both scopes, so the entry is removed instead.

**Topic deletion.** `PulsarAuthorizationProvider#removePermissionsAsync(TopicName)`, which already
removes the topic's entry from `destination_auth`, also removes it from `topic_subscription_auth_roles`.

**Admin authorization.** The new endpoints require the same permission as the existing topic-level
`grant-permission` and `revoke-permission` operations.

### Namespace and bundle subscription operations

Some admin operations act on a subscription across the topics of a namespace or bundle: unsubscribe
(`NamespacesBase#internalUnsubscribeNamespaceAsync` and `internalUnsubscribeNamespaceBundleAsync`) and
clear backlog, for a named subscription (`internalClearNamespaceBacklogForSubscriptionAsync`,
`internalClearNamespaceBundleBacklogForSubscriptionAsync`) or for all subscriptions
(`internalClearNamespaceBacklogAsync`, `internalClearNamespaceBundleBacklogAsync`). Today they authorize the
caller by subscription name only, through `validateNamespaceOperationAsync`. The namespace-level variants
then dispatch per-bundle or per-topic requests with the broker's own admin client, which are authorized as
the broker. A check by subscription name alone cannot tell the topics apart once topic-scoped entries
exist, so these operations authorize the original caller for each affected topic, before any dispatch or
mutation:

- **Named operations** (unsubscribe, and clear backlog of a named subscription S): the request is allowed
  only if the caller is allowed to use S by the namespace-scoped rule, as today, **and** by every
  topic-scoped entry for S on a topic the operation covers. Otherwise the whole request is rejected with
  `403`, before any subscription is removed or cleared. Which entries are covered depends on the scope:
  - A **namespace** operation covers every topic of the namespace, so every topic-scoped entry for S in
    the namespace policies applies. The broker that receives the caller's request decides from the
    namespace policies alone, and the per-bundle requests it then dispatches with its own identity are not
    re-checked against the caller, as today.
  - A **bundle** operation acts on the physical topics of the bundle
    (`NamespaceService#getOwnedTopicListForNamespaceBundle`), and the partitions of a partitioned topic
    are spread over bundles by their own names, not by the name the entries are stored under. The broker
    owning the bundle therefore takes the list of topics the operation is going to act on, maps each
    partition to its partitioned topic name (`TopicName#getPartitionedTopicName`, which needs no partition
    metadata), and checks the topic-scoped entries for S of those names. The check covers the whole list
    before any topic is changed, and the operation then acts on the same list.

  A topic-scoped entry that allows the caller where the namespace rule does not, does not allow the bulk
  operation: the caller can use the topic-level operations on that topic instead. Rejecting rather than
  skipping the excluded topics keeps a destructive operation on a named subscription all-or-nothing, as it
  is today.
- **Clear backlog of all subscriptions** for a caller that is not a super-user or tenant admin: today the
  broker clears only the subscriptions the caller may clear and skips the others
  (`clearAuthorizedSubscriptionsBacklogAsync`, and `clearBacklogAsync` for a bundle), caching each decision
  by subscription name. The decision becomes per topic and subscription, using the topic-scoped resolution
  above with the partitioned topic name of each physical topic, and the cache is keyed by both. Subscriptions
  the caller may not use on a topic are skipped, as they are today.

With no topic-scoped entry for the subscription, every one of these decisions is the same as today.

### Scalable topics

Topic-scoped subscription permissions follow the topic-level permissions (`destination_auth`) for scalable
topics too, so that migrating a topic does not drop them:

- **Granting.** A topic-scoped subscription permission can be granted on a scalable topic (`topic://`
  domain), and is stored under the scalable topic name. The scalable topic admin endpoints get the same
  three operations as the regular topic endpoints.
- **Enforcement.** A segment of a scalable topic has no permissions of its own: `checkPermission` already
  authorizes it with the permissions of its parent scalable topic (`SegmentTopicName#getParentTopicName`).
  The subscription check does the same, and resolves the topic-scoped entries of the parent scalable topic.
  The legacy segments of a migrated topic wrap the `persistent://` topics, and keep being authorized with
  their permissions, including their topic-scoped subscription permissions.
- **Migration.** `ScalableTopics#createMigratedScalableTopicAsync` grants the regular topic's topic-level
  permissions on the scalable topic before committing it (`AuthorizationService#copyPermissionsAsync`). The
  same step copies the regular topic's topic-scoped subscription entries to the scalable topic, in the same
  update of the namespace policies, reading them from the version being updated, so the new segments
  enforce the same subscription rules as the regular topic. As for topic-level permissions, the
  entries of a single partition are not copied, as the new segments mix the data of all partitions.
- **Deletion.** Deleting a scalable topic removes its topic-level permissions, as deleting a regular topic
  does; it removes its topic-scoped subscription entries too (`removePermissionsAsync`).

After a migration, as with the topic-level permissions today, the scalable topic's entries govern its new
segments, and changes to the regular topic's entries no longer reach them: operators manage the
subscription permissions of a migrated topic on its scalable topic name. A grant on the regular topic name
made concurrently with the copy, or after it, applies to the legacy segments only, like a topic-level grant
made at that time.

This needs no additional state or coordination: the copy is an update of the namespace policies, made by
the cluster that migrates the topic, like the copy of the topic-level permissions. Topics migrated before
the upgrade had no topic-scoped subscription entries to copy, so they need no initialization.

## Public-facing Changes

### Public API

`AuthPolicies` (pulsar-client-admin-api): the new `topic_subscription_auth_roles` field, with its
getter and builder method.

`AuthorizationProvider` (broker plugin API): the three default methods above, and the corresponding
methods in `AuthorizationService`.

REST API, for persistent and non-persistent topics:

- `GET /admin/v2/{domain}/{tenant}/{namespace}/{topic}/permissions/subscription`: the subscription
  permissions of the topic, as a map from subscription name to roles.
- `POST /admin/v2/{domain}/{tenant}/{namespace}/{topic}/permissions/subscription/{subscription}`: grant
  the roles in the request body.
- `DELETE /admin/v2/{domain}/{tenant}/{namespace}/{topic}/permissions/subscription/{subscription}/{role}`:
  revoke a role.

The GET and POST endpoints mirror the namespace endpoints
`GET /{tenant}/{namespace}/permissions/subscription` and
`POST /{tenant}/{namespace}/permissions/subscription/{subscription}` (with the roles as the request body).
The existing namespace revoke endpoint is `DELETE /{tenant}/{namespace}/permissions/{subscription}/{role}`,
without the `subscription` segment; the topic endpoint keeps the `subscription` segment, so that all three
topic endpoints share the `/permissions/subscription` prefix. None of them collides with the existing
topic-level `/{topic}/permissions/{role}` endpoints.

Java admin client, `Topics`: `getPermissionOnSubscription(String topic)`,
`grantPermissionOnSubscription(String topic, String subscription, Set<String> roles)` and
`revokePermissionOnSubscription(String topic, String subscription, String role)`, with their async
variants, mirroring the methods of the same name in `Namespaces`.

### Binary protocol

No change.

### Configuration

No change.

### CLI

`pulsar-admin topics subscription-permission`, `grant-subscription-permission` and
`revoke-subscription-permission`, taking a topic instead of a namespace and otherwise the same options as
the namespace commands of the same name:

- `grant-subscription-permission <topic> -s/--subscription <name> -rs/--roles <role1,role2>`
- `revoke-subscription-permission <topic> -s/--subscription <name> -r/--role <role>`
- `subscription-permission <topic>`

### Metrics

No change.

# Monitoring

No new metrics. A denied subscription is logged as it is today; the log entry states whether a
topic-scoped or a namespace-scoped permission denied it.

# Security Considerations

The change adds a more specific way to restrict, or allow, the roles of a subscription. A topic-scoped
entry can allow a role that the namespace-scoped entry for the same subscription name does not; this is
intended, as the topic-scoped entry is the more specific rule, and granting it requires the same
permission as granting topic-level permissions. The consume permission on the topic is still required.

With no topic-scoped entries, which is the case for every existing cluster, authorization is unchanged.

# Backward & Forward Compatibility

## Upgrade

No action is needed. Existing namespace-scoped subscription permissions keep their current effect, and
the new field is absent until an operator grants a topic-scoped permission.

During a rolling upgrade, grant topic-scoped permissions only once every broker of every cluster that
shares the configuration store has been upgraded: a broker that does not know the field ignores it, so it
would neither enforce those permissions nor copy them when it migrates a topic to a scalable topic.

## Downgrade / Rollback

Brokers that do not know the field ignore it when reading the namespace policies, since unknown
properties are ignored. After a rollback:

- topic-scoped subscription permissions are no longer enforced, and the namespace-scoped ones apply to
  every topic again;
- a namespace policy update written by an older broker drops the field, so the topic-scoped permissions
  are lost;
- a topic migrated to a scalable topic by an older broker does not get the regular topic's topic-scoped
  entries.

Operators who rely on topic-scoped permissions to restrict a subscription should restore equivalent
namespace-scoped permissions, or keep the restriction through role and topic design, before rolling
back.

## Pulsar Geo-Replication Upgrade & Downgrade/Rollback Considerations

Namespace policies are stored in the configuration metadata store, so the topic-scoped permissions are
shared by the clusters that share it, like the existing permissions. Clusters with separate
configuration stores need the grants in each store, as today. The upgrade and rollback notes above apply
to every cluster that reads the policies.

# Alternatives

**Store the permissions in topic policies** (the `__change_events` system topic). This keeps topic data
out of the namespace policies, but the check would depend on topic-level policies being enabled and
loaded, and would need an additional asynchronous lookup in the consume path. The topic-level
permissions (`destination_auth`) are stored in the namespace policies for the same reasons, and this
proposal follows them. The cost is that the namespace policies grow with the number of topic-scoped
grants, as they already do with topic-level permissions.

**Key the namespace map by `topic:subscription`.** This avoids a new field, but changes the meaning of
existing keys, would be misread by older brokers, and cannot be told apart from a subscription name
containing the separator.

**Combine the topic-scoped and namespace-scoped roles** (a role must be allowed by both, or by either).
Requiring both cannot widen a namespace rule for one topic; allowing either cannot narrow it. Letting the
more specific entry win supports both, and makes the effective rule for a topic and subscription visible
in one place.

# General Notes

**Implementation test plan.** Besides the subscribe, grant, revoke and fallback cases, with narrowing
and widening entries, on partitioned and non-partitioned topics:

- named namespace and bundle unsubscribe and clear-backlog: allowed when every covered topic-scoped
  entry allows the caller, rejected with `403` and nothing removed or cleared when one excludes it,
  including a namespace operation whose bundles are owned by another broker;
- a restricted partitioned topic whose partitions are spread over several bundles, including a partition
  in a bundle that does not include the hash of the partitioned topic name: a named bundle operation on
  that bundle is rejected, and one on a bundle without its partitions is not affected;
- clear backlog of all subscriptions, at namespace and bundle level, for a caller allowed on a
  subscription on one topic and excluded on another: only the allowed pair is cleared;
- scalable topics: grant, revoke and enforcement on a scalable topic, through its segments; migration of
  a regular topic with narrowing and widening entries, after which the new segments enforce the same rules
  and the legacy segments keep the regular topic's; deletion of a scalable topic removing its entries.

**Open question for the discussion: may a topic-scoped entry widen a namespace-scoped restriction?**
With the precedence rule above, if the namespace restricts `sub-a` to role X, a topic-scoped entry on
`topic1` can allow role Y to use `sub-a` on that topic. This keeps the rule simple (the more specific entry
wins, in both directions) and needs the same permission as granting topic-level consume permission. If
the community prefers topic-scoped entries to only narrow, the check would require a role to be allowed
by both entries when both exist; a topic could then not grant a role that the namespace excludes. Feedback
on which behavior operators expect is welcome.
