# PIP-500: Get all topic-level policies with a single admin call

# Background knowledge

Pulsar lets administrators configure behavior at three levels: broker (`broker.conf`), namespace, and topic.
A **topic-level policy** (or *topic policy*) overrides the namespace and broker values for one topic, for example
retention, message TTL, backlog quota, dispatch rate or max producers.

Topic policies are stored by the broker's `TopicPoliciesService`. Depending on `topicPoliciesServiceClassName`, they
live in the namespace's `__change_events` system topic (`SystemTopicBasedTopicPoliciesService`) or in the metadata
store (`MetadataStoreTopicPoliciesService`). Whichever service is used, one topic's policies are held in one
`org.apache.pulsar.common.policies.data.TopicPolicies` object. A topic has up to two such objects:

* **local** policies, which apply to the topic in the current cluster, and
* **global** policies, which are replicated to every cluster the topic is replicated to.

Topic policies apply to persistent and non-persistent topics, and only when `topicLevelPoliciesEnabled=true`. A
partitioned topic is addressed by its base name, and an individual partition is rejected. The `pulsar-admin
topicPolicies` commands accept only `persistent://` names.

Every policy is read through its own admin call. `pulsar-admin topicPolicies` exposes one `get-xxx`,
`set-xxx` and `remove-xxx` command per policy, backed by one REST endpoint and one method of the admin interface
`org.apache.pulsar.client.admin.TopicPolicies` each. Most getters accept an `applied` flag. Without it the call returns
only the value that was explicitly set on the topic. With it the broker falls back to the namespace value and then to
the broker default, so the result is the value in effect.

At namespace level there is already a single call that returns everything: `pulsar-admin namespaces policies
<tenant/namespace>` (`GET /admin/v2/namespaces/{tenant}/{namespace}`, `Namespaces#getPolicies`), which returns the
whole `Policies` object.

# Motivation

There is no way to read all the policies set on a topic in one call. The admin interface has 29 distinct topic-policy
getters, and two more policies (`schemaValidationEnforced` and `shadowTopics`) are read through `Topics`, so reading a
topic's full configuration takes more than 30 REST requests and `pulsar-admin` invocations.

This is a problem for several common tasks:

* **Debugging and support.** "What is configured on this topic?" cannot be answered with one command, and it is easy
  to miss a policy.
* **Auditing and configuration management.** Tools that snapshot, diff or back up topic configuration have to know and
  call every getter, and must be updated each time a policy is added.
* **Cloning or migrating a topic's configuration.** There is a `topicPolicies delete` command that removes all policies
  of a topic, but no counterpart that reads them.
* **Metadata catalogs and scrapers.** External systems that mirror Pulsar metadata into a catalog must issue more than 30
  requests per topic, and the per-policy requests are not a consistent snapshot of one point in time.

Namespaces already solved this with `namespaces policies`. Topics are the odd one out, and the asymmetry with the
existing `DELETE /{tenant}/{namespace}/{topic}/policies` endpoint, which removes all topic policies, makes the gap more
visible.

# Goals

## In Scope

* Add a REST endpoint, an admin API method and a `pulsar-admin` command that return all policies explicitly set on a
  topic, for the local or the global scope.
* Optionally return the **applied** view: for every policy, the value in effect after the local topic -> global topic ->
  namespace -> broker cascade, together with the level it came from, in a new response model (`AppliedTopicPolicies`).
* Resolve the cascade in one place in the broker, and cover the policies that `HierarchyTopicPolicies` does not model
  (for example the policies that end up in the `ManagedLedgerConfig`, such as persistence and offload).
* Keep the Java admin API result untyped (`Map<String, Object>`), so that new policies need no API change.
* Authorize and validate the call consistently with the existing per-policy getters and with `namespaces policies`.

## Out of Scope

* Changing how the existing per-policy `get-xxx --applied` getters resolve values. They keep their own code in this
  PIP. Moving them onto the new resolver is possible later, and the parity tests below guard against drift.
* A typed Java representation of the result. It can be added later under a different method name.
* Setting or replacing all topic policies in one call.
* Any change to how topic policies are stored, replicated or applied.
* Subscription-level views of the policies beyond what the `TopicPolicies` object already contains.

# High Level Design

Add a read-only counterpart to the existing `DELETE /{tenant}/{namespace}/{topic}/policies`:

```
GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/policies?isGlobal={true|false}&applied={true|false}
```

```
pulsar-admin topicPolicies get persistent://tenant/namespace/topic [--global] [--applied]
```

**Without `applied` (default)** the broker reads the topic's `TopicPolicies` object for the requested scope from the
`TopicPoliciesService`, exactly as every per-policy getter does today, and returns it as JSON. A policy that was never
set on the topic is absent (`null`). This is the same data `get-xxx` returns without `--applied`, gathered in one call
from a single object, so it is a consistent snapshot.

**With `applied=true`** the broker resolves every policy through the cascade local topic -> global topic -> namespace ->
broker, the precedence a loaded topic uses, and returns an `AppliedTopicPolicies` object. Because the view merges both
topic scopes, it does not depend on `isGlobal`, which is ignored. Each entry holds the effective value and the level it came from, so a caller can still
tell what is configured on the topic from what is inherited:

```json
{
  "retentionPolicies": { "value": { "retentionTimeInMinutes": 60, "retentionSizeInMB": 1024 }, "source": "TOPIC" },
  "messageTTLInSeconds": { "value": 300, "source": "NAMESPACE" },
  "maxProducerPerTopic": { "value": 0, "source": "BROKER" }
}
```

`source` is `TOPIC` (local topic policies), `TOPIC_GLOBAL` (global topic policies, with no local override),
`NAMESPACE` or `BROKER`.

The cascade is computed by one broker-side resolver instead of by 29 separate handlers.

# Detailed Design

## Design & Implementation Details

**Broker.** `PersistentTopics` (v2) gets a new `getTopicPolicies` method on the existing `{topic}/policies` path, next
to `deleteTopicPolicies`. It follows the pattern of the existing getters:

1. `validateTopicName`.
2. `validateTopicPolicyOperationAsync(topicName, PolicyName.ALL, PolicyOperation.READ)`. `PolicyName.ALL` is the same
   policy name `Namespaces#getPolicies` uses for the namespace dump.
3. `preValidation(authoritative)`, which rejects a disabled topic-level policy feature (405), a partition name (412),
   a non-existent topic (404) and a namespace that is not owned by this cluster, and redirects to the right broker.
4. A new `PersistentTopicsBase#internalGetTopicPolicies(isGlobal)` that calls
   `getTopicPoliciesAsyncWithRetry(topicName, isGlobal)` and returns the object, or a `TopicPolicies`
   with no policy fields set and `isGlobal` set to the requested scope if the topic has no policies in that scope.
5. `handleTopicPolicyException("getTopicPolicies", ...)` for error mapping, as the other getters do.

A topic with no policies returns `200` with a `TopicPolicies` that has no policy fields set, rather than `204`/`null`,
so callers always get a non-null object and need no special case. "No policies" is simply every policy field being null,
empty or default. The collections that `TopicPolicies` initializes (the backlog quota map, the subscription types and
the subscription policies) are returned empty, and `isGlobal` carries the requested scope, so a global read of a topic
without global policies does not report `isGlobal: false`.

**Admin API.** `org.apache.pulsar.client.admin.TopicPolicies` gets:

```java
Map<String, Object> getTopicPolicies(String topic) throws PulsarAdminException;
Map<String, Object> getTopicPolicies(String topic, boolean applied) throws PulsarAdminException;
CompletableFuture<Map<String, Object>> getTopicPoliciesAsync(String topic);
CompletableFuture<Map<String, Object>> getTopicPoliciesAsync(String topic, boolean applied);
```

The one-argument forms return the policies set on the topic and are the same as passing `applied=false`. The `applied`
overloads return the applied view described below. Local vs. global is selected the same way as for all other methods, through `PulsarAdmin#topicPolicies(boolean
isGlobal)`. The method name mirrors the existing `deleteTopicPolicies(String topic)`. `TopicPoliciesImpl` implements it
with a `GET` on the new path and deserializes the JSON body into a `Map`.

The result is **untyped on purpose**. The broker's `org.apache.pulsar.common.policies.data.TopicPolicies` class lives in
`pulsar-common`, which depends on `pulsar-client-admin-api`, so the public admin API cannot return it, and moving it is
not possible because it uses the protocol enum `CommandSubscribe.SubType` and the `OffloadPoliciesImpl` and
`SubscriptionPolicies` classes, which also live in `pulsar-common`. Existing admin methods avoid this by exposing an
interface in `pulsar-client-admin-api` and an implementation in `pulsar-common` (for example `OffloadPolicies` and
`TopicStats`), or by keeping the type in the admin API module (namespace `Policies`). Neither fits a class that is
shared with the broker's storage format, so this PIP returns the JSON structure as a map. This keeps the API surface
small and returns new policies without an API change. A typed accessor can be added later under a different name (for
example an interface in `pulsar-client-admin-api` implemented by `TopicPolicies`) without breaking this one. Numbers in
the map are decoded as `Integer`, `Long` or `Double` by Jackson, nested objects as `Map`, and arrays as `List`.

**CLI.** `CmdTopicPolicies` gets a `get` command, next to the existing `delete`, with the `-g/--global` option used by
the other commands. It prints the returned object as JSON. The `get` name pairs with `delete` and avoids repeating the
`namespaces policies` wording on a command group that already has `get-xxx` commands.

**Response shape.** The body is `TopicPolicies` serialized by the same Jackson configuration as the other admin
responses. For the metadata-store backend (`MetadataStoreTopicPoliciesService`) this is the persisted shape. The default
system-topic backend persists a `PulsarEvent` with an Avro schema instead, so the REST shape and the persisted shape are
not the same thing there.

The derived helper properties of the class (the `xxxSet` flags, `globalPolicies` and `replicationClustersSet`) are
excluded from the JSON with `@JsonIgnore`. They have no setters and no matching fields. The annotations do not affect
the Avro-persisted events. For the metadata-store backend they change what is written, in a safe way in both
directions: the stored JSON loses the derived fields, and older brokers read it unchanged, because the mapper ignores
unknown properties. `isSchemaValidationEnforced()` is a presence helper like the `xxxSet` flags, but its bean name is
the same as the real `schemaValidationEnforced` property. Jackson drops a whole property when any of its accessors
carries `@JsonIgnore`, so this one helper must **not** be annotated, or the real value would disappear from both the
REST response and the metadata-store JSON.

Fields added to `TopicPolicies` in future releases will appear automatically. They are additive, and clients must
ignore unknown fields, as with every other REST response in Pulsar. Because the persisted format already forbids
renames and removals, exposing it adds no new compatibility constraint, but it does make the shape part of the public
REST API, so the class should carry a note saying so.

## Applied view

**Why a new model.** `TopicPolicies` uses `null` for "not set on the topic", so filling inherited values into it would
destroy that distinction. `HierarchyTopicPolicies` is not a usable base either: it merges topic, namespace and broker
values for only 28 `PolicyHierarchyValue` fields and exists only inside a loaded `PersistentTopic`. It does not hold the
policies applied to the `ManagedLedgerConfig` (persistence, offload) or several others that fall back to broker or
namespace settings elsewhere, and reading it would load the topic as a side effect of an admin read. So this PIP adds
a new POJO in `pulsar-common`:

```java
public class AppliedTopicPolicies {
    private AppliedValue<RetentionPolicies> retentionPolicies;
    private AppliedValue<PersistencePolicies> persistence;
    private AppliedValue<OffloadPoliciesImpl> offloadPolicies;
    private AppliedValue<Integer> messageTTLInSeconds;
    ... one field per policy of TopicPolicies that has a namespace or broker level
}

public class AppliedValue<T> {
    @JsonInclude(JsonInclude.Include.ALWAYS)   // an unset policy is returned as "value": null
    private T value;
    private PolicySource source;   // TOPIC, TOPIC_GLOBAL, NAMESPACE, BROKER
}
```

Policies that exist only at topic level are returned with the level they were set on, or are absent when unset:
`shadowTopics` is an `AppliedValue`, and `subscriptionPolicies` is a map from subscription name to an `AppliedValue`,
so that each entry carries its own source (the local policy of a subscription wins over the global one). A policy that
is unset at every level and has no default is returned with a null `value`.

**Resolver.** A new `TopicPolicyResolver` in the broker takes the topic's local and global `TopicPolicies`,
the namespace `Policies`, and the `ServiceConfiguration`, and produces the `AppliedTopicPolicies`. It
reads them from the same caches the per-policy getters use. It needs no loaded topic and works on any broker that
owns the namespace, for loaded or unloaded topics. For the policies that reach the `ManagedLedgerConfig`, it applies the
same precedence as `BrokerService#getManagedLedgerConfig`.

The resolver mirrors the runtime rules where they differ from a plain fallback:

* A topic-level value that the broker treats as "not set" does not count as set: a negative integer value, and a dispatch,
  subscription dispatch, replicator dispatch, subscribe or publish rate without a positive limit (the CLI stores `-1/-1`
  when no limit is given), as `AbstractTopic#updateTopicPolicy` normalizes them. The inherited value is reported instead.
* A negative `managedLedgerMaxMarkDeleteRate` in the persistence policy is replaced by the broker default, as the
  managed ledger does.
* The auto subscription creation override is read from the local policies only, as the broker enforces it.
* A system topic ignores or overrides several levels, so `applied=true` is rejected for a system topic with `412`.

**Policies without an applied getter today.** 6 of the 29 admin getters have no `applied` flag
(`getDeduplicationSnapshotInterval`, `getMaxConsumersPerSubscription`, `getMaxMessageSize`,
`getMaxSubscriptionsPerTopic`, `getPublishRate`, `getSubscriptionTypesEnabled`). The resolver defines their fallback to
match what the broker enforces at runtime (namespace value, then the `broker.conf` default). The new view therefore
also reports them, which the per-policy getters cannot do. No per-policy API is added for them.

**The getters the view covers.** The admin `TopicPolicies` interface has these 29 getters:
`getAutoSubscriptionCreation`, `getBacklogQuotaMap`, `getCompactionThreshold`, `getDeduplicationSnapshotInterval`,
`getDeduplicationStatus`, `getDelayedDeliveryPolicy`, `getDispatchRate`, `getDispatcherPauseOnAckStatePersistent`,
`getEntryFiltersPerTopic`, `getInactiveTopicPolicies`, `getMaxConsumers`, `getMaxConsumersPerSubscription`,
`getMaxMessageSize`, `getMaxProducers`, `getMaxSubscriptionsPerTopic`, `getMaxUnackedMessagesOnConsumer`,
`getMaxUnackedMessagesOnSubscription`, `getMessageTTL`, `getOffloadPolicies`, `getPersistence`, `getPublishRate`,
`getReplicationClusters`, `getReplicatorDispatchRate`, `getRetention`, `getSchemaCompatibilityStrategy`,
`getSubscribeRate`, `getSubscriptionDispatchRate`, `getSubscriptionExpirationTime` and `getSubscriptionTypesEnabled`.
23 of them take `applied`. `schemaValidationEnforced` and `shadowTopics` are stored in `TopicPolicies` but are read
through `Topics#getSchemaValidationEnforced` and the shadow-topic methods. The applied view includes both, so the tests
cover the policies in this list and these two.

**Keeping the rules in sync.** The applied code in the existing handlers stays untouched. The per-policy `applied`
getters read a single scope and do not normalize topic rates, so they are not a sufficient oracle. The tests instead
compare the applied view with the loaded topic (`HierarchyTopicPolicies` and the `ManagedLedgerConfig`), with values set
in the local, global and namespace scopes. A new policy added to `TopicPolicies` must be added to the resolver: a test
compares the fields of `AppliedTopicPolicies` with those of `TopicPolicies`, and a broker test resolves empty policies
and asserts that every policy that is not topic-only is filled, so forgetting the resolver fails the build.

**Rules that are not a plain fallback.** Most policies take the first non-null value of topic, namespace and broker, and a
negative namespace value counts as unset, as for a loaded topic. Two exceptions follow the existing getters. For
`schemaValidationEnforced`, the policy is enabled when the broker setting is true or the most specific level sets it, so
a broker value of `true` is reported with `source=BROKER`. For `entryFilters`, when
`allowOverrideEntryFilters=false` the broker value is always returned. For offload policies, the topic, namespace and
broker values are merged field by field, and `source` names the most specific level that sets the policy at all.

**Consistency.** The local topic, global topic and namespace policies come from separate cached reads, so the applied view is
consistent per object but not one atomic snapshot across levels, which is the same as with the per-policy getters.

**Authorization and errors.** Same as the non-applied call (`PolicyName.ALL`, `READ`). The applied view only combines
values that are already readable through the per-policy getters.

## Public-facing Changes

### Public API

New REST endpoint (v2 only; topic policies do not exist in v1):

| | |
|---|---|
| Path | `GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/policies`. `NonPersistentTopics` extends `PersistentTopics`, so the same handler is also served at `GET /admin/v2/non-persistent/{tenant}/{namespace}/{topic}/policies`, as the existing `DELETE` is. Non-persistent topics apply topic policies too, so this is intended. |
| Query | `isGlobal` (boolean, default `false`): read the global policies instead of the local ones; ignored when `applied=true`. `applied` (boolean, default `false`): return the effective values with their source. `authoritative` (internal). |
| Response `200` | Without `applied`: `TopicPolicies` JSON. With `applied=true`: `AppliedTopicPolicies` JSON. The OpenAPI schema is `oneOf` both. Never `null`; without `applied`, an empty object when the topic has no policies in that scope. |
| `307` | This broker does not own the topic's namespace; follow the redirect. |
| `401` | The caller has the policy read permission but not the lookup permission on the topic, which `preValidation` also checks. |
| `403` | The caller does not have permission to read the topic's policies. |
| `404` | The namespace or topic does not exist. |
| `405` | Topic-level policies are disabled (`topicLevelPoliciesEnabled=false`). |
| `412` | The topic name is a partition (query the partitioned topic instead), the namespace ownership or cluster eligibility check failed, or `applied=true` was requested for a system topic. |

When `topicLevelPoliciesEnabled=true` but `systemTopicEnabled=false` with the default service class, the broker installs
`TopicPoliciesService.DISABLED`. `preValidation` checks only the configuration flag, so the call returns `200` with a
`TopicPolicies` that has no policy fields set, which a snapshot or audit tool cannot tell apart from "no policies". This
matches the existing per-policy getters, which return their null or default value in that case. See open question 7.

New admin API methods, described above. They return `Map<String, Object>` holding the same JSON the REST endpoint
returns:

```java
Map<String, Object> getTopicPolicies(String topic) throws PulsarAdminException;
Map<String, Object> getTopicPolicies(String topic, boolean applied) throws PulsarAdminException;
CompletableFuture<Map<String, Object>> getTopicPoliciesAsync(String topic);
CompletableFuture<Map<String, Object>> getTopicPoliciesAsync(String topic, boolean applied);
```

`AppliedTopicPolicies` and `AppliedValue` are new classes in `pulsar-common`. Their JSON shape is part of the public
REST API.

### Binary protocol

No change.

### Configuration

No change.

### CLI

```
pulsar-admin topicPolicies get <persistent://tenant/namespace/topic> [-g | --global] [-ap | --applied]
```

Output is the pretty-printed JSON of `TopicPolicies`, or of `AppliedTopicPolicies` with `--applied`. The flag name
matches the existing `get-xxx --applied`. Illustrative example for a topic with a retention policy and a
TTL (the exact set of null/default fields shown follows the admin JSON configuration):

```json
{
  "backLogQuotaMap" : { },
  "subscriptionTypesEnabled" : [ ],
  "isGlobal" : false,
  "retentionPolicies" : { "retentionTimeInMinutes" : 60, "retentionSizeInMB" : 1024 },
  "messageTTLInSeconds" : 300,
  "subscriptionPolicies" : { }
}
```

### Metrics

No change.

# Monitoring

No new metrics. The call has the same cost and failure modes as one per-policy getter, since it reads one object from
the `TopicPoliciesService` cache. Operators can use the existing REST request metrics and logs.

# Security Considerations

* **Authorization.** The endpoint requires `PolicyOperation.READ` on `PolicyName.ALL`, mirroring
  `namespaces policies`. The built-in authorization provider checks tenant-admin or super-user rights for the topic's
  namespace, as for every other topic-policy getter. The caller only ever receives the policies of the one topic named
  in the path, so one tenant cannot read another tenant's topic.
* **Custom authorization providers.** Providers that grant per-policy rights (a different `PolicyName` per getter)
  now see a request for `ALL`. A caller with rights on only some policies cannot use the new call, which is the
  conservative behavior and the same as for `namespaces policies`.
* **No new data exposure.** Every field of `TopicPolicies` is already readable through its own getter, including
  offload policies and their credential references. The new call returns nothing that an authorized caller could not
  already read, only in one response.
* **Applied view and broker configuration.** With `applied=true`, a value inherited from the broker is returned, for
  example the offload driver, bucket, region and credential file path from `broker.conf`. A caller with
  `PolicyName.ALL` read rights on the topic therefore sees broker-level settings. `get-offload-policies --applied` and the
  other `--applied` getters already return the same merged values, so the exposure is the same as today, but an
  operator who restricts these should be aware that the single call returns all of them.

# Backward & Forward Compatibility

## Upgrade

No action needed. The change adds a `GET` to a path that already serves `DELETE`. A new CLI or admin client calling an
old broker receives `405 Method Not Allowed`, which the CLI reports as an error. During a rolling upgrade the call
succeeds on upgraded brokers only.
The broker with this change is the first to know `applied` on this path, but a client never reaches an older broker's
`GET` handler because that returns `405`, so `--applied` cannot silently return the non-applied view.

## Downgrade / Rollback

Remove the use of `topicPolicies get`. The call itself persists nothing, so no data migration is needed. With the
metadata-store backend the stored JSON no longer contains the derived helper fields, and older brokers read it
unchanged.

## Pulsar Geo-Replication Upgrade & Downgrade/Rollback Considerations

None. The endpoint only reads. Global policies are replicated by the existing mechanism, and `--global` reads the local
cluster's copy of them.

# Open questions

1. **Source information.** The applied view reports the level each value came from. Is
   `TOPIC | TOPIC_GLOBAL | NAMESPACE | BROKER` enough, or should the namespace case name the namespace-level policy and the broker case name the config key?
2. **Response model for the non-applied call.** Should it also use a typed shape of `AppliedValue`-like wrappers, or
   stay the raw `TopicPolicies` JSON (the proposal)? The raw shape is what is persisted and what `get-xxx` shows.
3. **Untyped `Map<String, Object>` in the Java admin API** versus an interface in `pulsar-client-admin-api`. See
   Alternatives. A typed projection can convert the stored `List<SubType>` to the `Set<SubscriptionType>` that
   `getSubscriptionTypesEnabled` already returns, so the choice rests on the cost of keeping one getter per policy in
   sync and on the larger public API, not on a type limitation.
4. **Command name** `get` versus `policies`.
5. **Empty object versus `204`** when a topic has no policies.
6. **Single resolver versus reusing the per-policy handlers.** This PIP proposes a new resolver plus parity tests.
   Refactoring all handlers onto it is possible later but is a large, separate change.
7. **Disabled topic policies service.** With `topicLevelPoliciesEnabled=true` and `systemTopicEnabled=false`, the
   call returns an empty `200`. Should it return `405` in that case, so that a snapshot or audit tool can tell it from
   "no policies"? The per-policy getters return their null or default value today.

# Alternatives

* **Aggregate the per-policy getters on the client.** This is what users do today. It needs more than 30 requests per
  topic, must be updated whenever a policy is added, and is not a consistent snapshot. Keeping it as the only option is
  the problem this PIP addresses.
* **Build the applied view from `HierarchyTopicPolicies`.** It is the only existing merged model, but it covers a
  subset of the policies, omits those applied to the `ManagedLedgerConfig`, and only exists inside a loaded
  `PersistentTopic`, so it would load topics from an admin read and differ across brokers.
* **Make `applied` fill inherited values into `TopicPolicies`.** It reuses the existing type, but "not set" and
  "inherited" become indistinguishable, and clients cannot audit what is configured on the topic.
* **Resolve `applied` by calling each per-policy handler internally.** It reuses current code, but it needs applied
  support added to the 6 getters that lack it, and 23 fallbacks would be called one by one through REST-shaped code.
* **Add the command under `pulsar-admin topics`.** `topics` has no topic-policy commands. Policies live under
  `topicPolicies`, next to the existing `delete`, which is the natural home.
* **Name the command `policies`, like `namespaces policies`.** This gives the same wording for both levels, but the
  `topicPolicies` group already uses `get-xxx` and `delete`, so `get` reads as the pair of `delete`. The two names
  could both exist as aliases if reviewers prefer. This is a naming question only.
* **Return a typed object from the Java admin API.** The natural type, `TopicPolicies`, lives in `pulsar-common` and
  cannot be referenced from `pulsar-client-admin-api`. A new interface in the admin API implemented by `TopicPolicies`
  would work (as `OffloadPolicies` does), but needs one getter per policy kept in sync and enlarges the public API.
  `TopicPolicies` cannot implement a getter for `subscriptionTypesEnabled` directly, because it stores the protocol
  enum `SubType`, but a separate typed projection can convert it to `Set<SubscriptionType>`, as the existing getter
  does. It is left as future work.
* **Return the JSON as a `String`**, as `Topics#getInternalInfo` does. This is the simplest, but every caller would have
  to parse it.
* **Return `204`/`null` when there are no policies.** This matches the per-policy getters, but forces every caller to
  special-case it. An empty object is simpler for callers and has no downside.
* **Expose the system topic content directly.** Reading `__change_events` or the metadata store exposes internal
  formats, requires wider permissions, and does not work for both storage backends.

# General Notes

The REST path was chosen because `DELETE /{topic}/policies` already exists with the same meaning ("all topic
policies"). Adding `GET` makes the resource symmetric and avoids inventing a second path for the same object.
