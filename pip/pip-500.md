# PIP-500: Get all topic-level policies with a single admin call

# Background knowledge

Pulsar lets administrators configure behavior at three levels: broker (`broker.conf`), namespace, and topic.
A **topic-level policy** (or *topic policy*) overrides the namespace and broker values for one topic, for example
retention, message TTL, backlog quota, dispatch rate or max producers.

Topic policies are stored by the broker's `TopicPoliciesService`. Depending on `topicPoliciesServiceClassName`, they
live in the namespace's `__change_events` system topic (`SystemTopicBasedTopicPoliciesService`) or in the metadata
store (`MetadataStoreTopicPoliciesService`). Whichever service is used, one topic's policies are held in one
`org.apache.pulsar.common.policies.data.TopicPolicies` object. A topic has up to two such objects:

* **local** policies, which apply to the topic in the current cluster, and
* **global** policies, which are replicated to every cluster the topic is replicated to.

Topic policies are only supported for persistent, non-partition topics, and only when
`topicLevelPoliciesEnabled=true`.

Every policy is read through its own admin call. `pulsar-admin topicPolicies` exposes one `get-xxx`,
`set-xxx` and `remove-xxx` command per policy, backed by one REST endpoint and one method of the admin interface
`org.apache.pulsar.client.admin.TopicPolicies` each. Most getters accept an `applied` flag. Without it the call returns
only the value that was explicitly set on the topic. With it the broker falls back to the namespace value and then to
the broker default, so the result is the value in effect.

At namespace level there is already a single call that returns everything: `pulsar-admin namespaces policies
<tenant/namespace>` (`GET /admin/v2/namespaces/{tenant}/{namespace}`, `Namespaces#getPolicies`), which returns the
whole `Policies` object.

# Motivation

There is no way to read all the policies set on a topic in one call. The admin interface has 28 distinct topic-policy
getters, so reading a topic's full configuration takes about 28 REST requests and 28 `pulsar-admin` invocations.

This is a problem for several common tasks:

* **Debugging and support.** "What is configured on this topic?" cannot be answered with one command, and it is easy
  to miss a policy.
* **Auditing and configuration management.** Tools that snapshot, diff or back up topic configuration have to know and
  call every getter, and must be updated each time a policy is added.
* **Cloning or migrating a topic's configuration.** There is a `topicPolicies delete` command that removes all policies
  of a topic, but no counterpart that reads them.
* **Metadata catalogs and scrapers.** External systems that mirror Pulsar metadata into a catalog must issue about 28
  requests per topic, and the per-policy requests are not a consistent snapshot of one point in time.

Namespaces already solved this with `namespaces policies`. Topics are the odd one out, and the asymmetry with the
existing `DELETE /{tenant}/{namespace}/{topic}/policies` endpoint, which removes all topic policies, makes the gap more
visible.

# Goals

## In Scope

* Add a REST endpoint, an admin API method and a `pulsar-admin` command that return all policies explicitly set on a
  topic, for the local or the global scope.
* Keep the Java admin API result untyped (`Map<String, Object>`), so that new policies need no API change.
* Authorize and validate the call consistently with the existing per-policy getters and with `namespaces policies`.

## Out of Scope

* Returning the *applied* (effective) value of each policy, including inherited namespace and broker values. See
  [Open questions](#open-questions) for the reasoning and the alternatives.
* A typed Java representation of the result. It can be added later under a different method name.
* Setting or replacing all topic policies in one call.
* Any change to how topic policies are stored, replicated or applied.
* Subscription-level views of the policies beyond what the `TopicPolicies` object already contains.

# High Level Design

Add a read-only counterpart to the existing `DELETE /{tenant}/{namespace}/{topic}/policies`:

```
GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/policies?isGlobal={true|false}
```

The broker reads the topic's `TopicPolicies` object for the requested scope from the `TopicPoliciesService`, exactly as
every per-policy getter does today, and returns it as JSON. The admin API and CLI are thin wrappers:

```
pulsar-admin topicPolicies get persistent://tenant/namespace/topic [--global]
```

The response contains only what was explicitly set at topic level for that scope. A policy that was never set on the
topic is absent (`null`). This is the same data that `get-xxx` returns when `--applied` is not given, gathered in one
call, and it is read from a single `TopicPolicies` object, so it is a consistent snapshot.

# Detailed Design

## Design & Implementation Details

**Broker.** `PersistentTopics` (v2) gets a new `getTopicPolicies` method on the existing `{topic}/policies` path, next
to `deleteTopicPolicies`. It follows the pattern of the existing getters:

1. `validateTopicName`.
2. `validateTopicPolicyOperationAsync(topicName, PolicyName.ALL, PolicyOperation.READ)`. `PolicyName.ALL` is the same
   policy name `Namespaces#getPolicies` uses for the namespace dump.
3. `preValidation(authoritative)`, which rejects a disabled topic-level policy feature (405), a partition name (412),
   a non-existent topic (404) and a namespace that is not owned by this cluster, and redirects to the right broker.
4. A new `PersistentTopicsBase#internalGetTopicPolicies(isGlobal)` that calls
   `getTopicPoliciesAsyncWithRetry(topicName, isGlobal)` and returns the object, or an empty `TopicPolicies` if the
   topic has no policies in that scope.
5. `handleTopicPolicyException("getTopicPolicies", ...)` for error mapping, as the other getters do.

A topic with no policies returns `200` with an empty `TopicPolicies` rather than `204`/`null`, so callers always get a
non-null object and need no special case. "No policies" is simply every field being null, empty or default.

**Admin API.** `org.apache.pulsar.client.admin.TopicPolicies` gets:

```java
Map<String, Object> getTopicPolicies(String topic) throws PulsarAdminException;
CompletableFuture<Map<String, Object>> getTopicPoliciesAsync(String topic);
```

Local vs. global is selected the same way as for all other methods, through `PulsarAdmin#topicPolicies(boolean
isGlobal)`. The method name mirrors the existing `deleteTopicPolicies(String topic)`. `TopicPoliciesImpl` implements it
with a `GET` on the new path and deserializes the JSON body into a `Map`.

The result is **untyped on purpose**. The broker's `org.apache.pulsar.common.policies.data.TopicPolicies` class lives in
`pulsar-common`, which depends on `pulsar-client-admin-api`, so the public admin API cannot return it, and moving it is
not possible because it uses the protocol enum `CommandSubscribe.SubType` and the `OffloadPoliciesImpl` and
`SubscriptionPolicies` classes, which also live in `pulsar-common`. Existing admin methods avoid this by exposing an
interface in `pulsar-client-admin-api` and an implementation in `pulsar-common` (for example `OffloadPolicies` and
`TopicStats`), or by keeping the type in the admin API module (namespace `Policies`). Neither fits a class that is
shared with the broker's storage format, so this PIP returns the JSON structure as a map. This keeps the API surface
small and returns new policies without an API change. A typed accessor can be added later under a different name (for
example an interface in `pulsar-client-admin-api` implemented by `TopicPolicies`) without breaking this one. Numbers in
the map are decoded as `Integer`, `Long` or `Double` by Jackson, nested objects as `Map`, and arrays as `List`.

**CLI.** `CmdTopicPolicies` gets a `get` command, next to the existing `delete`, with the `-g/--global` option used by
the other commands. It prints the returned object as JSON. The `get` name pairs with `delete` and avoids repeating the
`namespaces policies` wording on a command group that already has `get-xxx` commands.

**Response shape.** The body is `TopicPolicies` serialized by the same Jackson configuration as the other admin
responses. This is the object that is also written to the system topic or the metadata store, so the REST shape is the
persisted shape. Fields added to `TopicPolicies` in future releases will appear automatically. They are additive, and
clients must ignore unknown fields, as with every other REST response in Pulsar. Because the persisted format already
forbids renames and removals, exposing it adds no new compatibility constraint, but it does make the shape part of the
public REST API, so the class should carry a note saying so.

## Public-facing Changes

### Public API

New REST endpoint (v2 only; topic policies do not exist in v1):

| | |
|---|---|
| Path | `GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/policies` |
| Query | `isGlobal` (boolean, default `false`): read the global policies instead of the local ones. `authoritative` (internal). |
| Response `200` | `TopicPolicies` JSON. Never `null`; an empty object when the topic has no policies in that scope. |
| `307` | This broker does not own the topic's namespace; follow the redirect. |
| `403` | The caller does not have permission to read the topic's policies. |
| `404` | The namespace or topic does not exist. |
| `405` | Topic-level policies are disabled (`topicLevelPoliciesEnabled=false`). |
| `409` | Concurrent modification. |
| `412` | The topic name is a partition. Query the partitioned topic instead. |

New admin API methods `TopicPolicies#getTopicPolicies` and `getTopicPoliciesAsync`, described above. They return
`Map<String, Object>` holding the same JSON the REST endpoint returns.

### Binary protocol

No change.

### Configuration

No change.

### CLI

```
pulsar-admin topicPolicies get <persistent://tenant/namespace/topic> [-g | --global]
```

Output is the pretty-printed JSON of `TopicPolicies`. Illustrative example for a topic with a retention policy and a
TTL (the exact set of null/default fields shown follows the admin JSON configuration):

```json
{
  "backLogQuotaMap" : { },
  "subscriptionTypesEnabled" : [ ],
  "isGlobal" : false,
  "retentionPolicies" : { "retentionTimeInMinutes" : 60, "retentionSizeInMB" : 1024 },
  "messageTTLInSeconds" : 300,
  "subscriptionPolicies" : { }
}
```

### Metrics

No change.

# Monitoring

No new metrics. The call has the same cost and failure modes as one per-policy getter, since it reads one object from
the `TopicPoliciesService` cache. Operators can use the existing REST request metrics and logs.

# Security Considerations

* **Authorization.** The endpoint requires `PolicyOperation.READ` on `PolicyName.ALL`, mirroring
  `namespaces policies`. The built-in authorization provider checks tenant-admin or super-user rights for the topic's
  namespace, as for every other topic-policy getter. The caller only ever receives the policies of the one topic named
  in the path, so one tenant cannot read another tenant's topic.
* **Custom authorization providers.** Providers that grant per-policy rights (a different `PolicyName` per getter)
  now see a request for `ALL`. A caller with rights on only some policies cannot use the new call, which is the
  conservative behavior and the same as for `namespaces policies`.
* **No new data exposure.** Every field of `TopicPolicies` is already readable through its own getter, including
  offload policies and their credential references. The new call returns nothing that an authorized caller could not
  already read, only in one response.

# Backward & Forward Compatibility

## Upgrade

No action needed. The change adds a `GET` to a path that already serves `DELETE`. A new CLI or admin client calling an
old broker receives `405 Method Not Allowed`, which the CLI reports as an error. During a rolling upgrade the call
succeeds on upgraded brokers only.

## Downgrade / Rollback

Remove the use of `topicPolicies get`. Nothing is persisted, so no data migration is needed.

## Pulsar Geo-Replication Upgrade & Downgrade/Rollback Considerations

None. The endpoint only reads. Global policies are replicated by the existing mechanism, and `--global` reads the local
cluster's copy of them.

# Open questions

## Should `topicPolicies get` support `--applied`?

The per-policy getters accept `--applied`. A `get-all` command raises the question of whether it should too. This
proposal recommends **not** supporting it in the first version, for these reasons:

1. **"Applied" is implemented policy by policy, not in one place.** Each REST handler hand-writes its own fallback.
   For example `internalGetRetention` returns the topic value, then the namespace value, then the broker default,
   while other policies use different fields or defaults. Of the 28 getters in the admin interface, 22 accept
   `applied` and 6 do not (`getDeduplicationSnapshotInterval`, `getMaxConsumersPerSubscription`, `getMaxMessageSize`,
   `getMaxSubscriptionsPerTopic`, `getPublishRate`, `getSubscriptionTypesEnabled`). A single `--applied` flag cannot
   be honored for those six without adding applied support to each of them first.
2. **There is no central hierarchy to read.** `HierarchyTopicPolicies` merges topic, namespace and broker values, but
   only for a subset of policies, and only inside a loaded `PersistentTopic`. Using it would load the topic as a side
   effect of an admin read, would miss policies it does not model (for example persistence, offload, dispatch rates,
   entry filters), and would fail or differ for topics that are unloaded or owned by another broker.
3. **The response type cannot express it.** `TopicPolicies` uses `null` to mean "not set at topic level". Filling in
   inherited values destroys that distinction, so the caller can no longer tell what is configured on the topic from
   what is inherited. A useful applied view would need a different response model (value plus its source: topic,
   namespace or broker).
4. **The explicit view is the most requested one.** Auditing, cloning and catalog sync all want what was set on the
   topic. The effective view is already available per policy with `get-xxx --applied`.

Alternatives for the community to weigh:

| Option | Behavior | Cost |
|---|---|---|
| **A (proposed)** | No `--applied`. Returns the explicitly set topic policies. | Smallest change. Effective values stay per policy. |
| B | `--applied` resolves each policy with the same code as its per-policy getter, filling inherited values. | Needs applied support added to the 6 missing getters, about 22 fallbacks reused or refactored, and a decision on the null-vs-inherited problem in (3). |
| C | `--applied` reads the loaded topic's `HierarchyTopicPolicies`. | Loads topics, covers only part of the policies, and is inconsistent across brokers. |

If B is wanted later, it should be a follow-up PIP that first centralizes the policy hierarchy (so the fallback rules
exist once) and defines a response model that carries the source of each value. Leaving `applied` out now does not
block that, because the new query parameter would be additive. Until then, passing an unknown `applied` query
parameter is ignored by the server, so clients must not send it.

# Alternatives

* **Aggregate the per-policy getters on the client.** This is what users do today. It needs about 28 requests per
  topic, must be updated whenever a policy is added, and is not a consistent snapshot. Keeping it as the only option is
  the problem this PIP addresses.
* **Add the command under `pulsar-admin topics`.** `topics` has no topic-policy commands. Policies live under
  `topicPolicies`, next to the existing `delete`, which is the natural home.
* **Name the command `policies`, like `namespaces policies`.** This gives the same wording for both levels, but the
  `topicPolicies` group already uses `get-xxx` and `delete`, so `get` reads as the pair of `delete`. The two names
  could both exist as aliases if reviewers prefer. This is a naming question only.
* **Return a typed object from the Java admin API.** The natural type, `TopicPolicies`, lives in `pulsar-common` and
  cannot be referenced from `pulsar-client-admin-api`. A new interface in the admin API implemented by `TopicPolicies`
  would work (as `OffloadPolicies` does), but needs one getter per policy kept in sync, cannot expose
  `subscriptionTypesEnabled` because its element type is a protocol enum, and enlarges the public API. It is left as
  future work.
* **Return the JSON as a `String`**, as `Topics#getInternalInfo` does. This is the simplest, but every caller would have
  to parse it.
* **Return `204`/`null` when there are no policies.** This matches the per-policy getters, but forces every caller to
  special-case it. An empty object is simpler for callers and has no downside.
* **Expose the system topic content directly.** Reading `__change_events` or the metadata store exposes internal
  formats, requires wider permissions, and does not work for both storage backends.

# General Notes

The REST path was chosen because `DELETE /{topic}/policies` already exists with the same meaning ("all topic
policies"). Adding `GET` makes the resource symmetric and avoids inventing a second path for the same object.
