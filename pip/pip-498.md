# PIP-497: Share retry and dead-letter producers across partitions of the same subscription

# Background knowledge

Pulsar's Java client supports two patterns that automatically forward messages between topics:

- **Retry topic**: when `enableRetry(true)` is set, a consumer that calls `reconsumeLater(...)` sends the message to a per-subscription retry topic (by default `<topic>-<subscription>-RETRY`). The retry consumer internally owns a `Producer` to that retry topic.
- **Dead Letter Queue (DLQ)**: when a `DeadLetterPolicy` is configured, a message whose redelivery count exceeds `maxRedeliverCount` is forwarded by the consumer to a DLQ topic (by default `<topic>-<subscription>-DLQ`). The consumer internally owns a `Producer` to that DLQ topic.

In the current client, both producers are **instance fields of `ConsumerImpl`**:

```java
// pulsar-client/src/main/java/org/apache/pulsar/client/impl/ConsumerImpl.java
protected volatile Producer<T> deadLetterProducer;
protected volatile Producer<byte[]> retryLetterProducer;
```

When a consumer subscribes to a **partitioned topic**, the Pulsar client transparently creates a `MultiTopicsConsumerImpl` that in turn creates one `ConsumerImpl` per partition. These per-partition consumers (we refer to them as *sub-consumers*) share the same subscription name but each one carries its own `retryLetterProducer` / `deadLetterProducer` field.

Because the retry/DLQ topic is **subscription-level** (not partition-level), every partition's sub-consumer ends up opening a producer that writes to the exact same destination topic.

Related code to be aware of:

- `MultiTopicsConsumerImpl` — manages the collection of per-partition `ConsumerImpl`s and lifecycle events (`subscribe`, `unsubscribe`, `onTopicsExtended`).
- `ConsumerImpl#initRetryLetterProducerIfNeeded()` / `initDeadLetterProducerIfNeeded()` — lazy init on the first retry/DLQ send.
- `DeadLetterProducerBuilderContextImpl` — context passed to user-supplied `producerBuilderCustomizer` in `DeadLetterPolicy`.

Further reading:
- [PIP-22: Dead Letter Topic](https://github.com/apache/pulsar/wiki/PIP-22%3A-Pulsar-Dead-Letter-Topic)
- [PIP-57: Dead letter policy take effect](https://github.com/apache/pulsar/wiki/PIP-57%3A-Dead-letter-policy-take-effect)

# Motivation

With the current design, a single subscription on a `P`-partition topic opens `P` retry-producers and `P` DLQ-producers, all pointing to **one** retry topic and **one** DLQ topic respectively. Scaled across `N` client instances, a single subscription produces `N × P × 2` broker-side producers.

Real-world example: a 32-partition topic consumed by 10 pods ⇒ **640 retry/DLQ producers on the broker side** for a single subscription, while only 2 distinct destination topics exist.

This has several concrete downsides:

1. **Broker-side resource waste**: each `Producer` consumes a connection slot, metadata, bookkeeping memory, stats structures, and (depending on configuration) a dedicated producer id. For large deployments, the retry/DLQ fan-out dominates broker memory for subscriptions that rarely actually produce retry/DLQ traffic.
2. **Client-side resource waste**: every per-partition `ConsumerImpl` holds its own Netty channel attachment, pending-messages queue, batch-timer, and stats collector for a producer that is logically identical to the ones held by its sibling partitions.
3. **Topic lookup / cnx storms**: during consumer startup, each partition independently performs a producer lookup for the same retry/DLQ topic, multiplying lookup load by `P`.
4. **Metrics noise**: `ConsumerStats#getRetryLetterProducerStats()` / `getDeadLetterProducerStats()` are reported per partition, forcing users to aggregate `P` entries that always target the same destination topic.
5. **Latent semantic bug**: the `producerBuilderCustomizer` context today receives `inputTopic = <topic>-partition-0` — a partition-level name — which is misleading because the resulting producer actually targets a subscription-level topic.

The root cause is a **wrong-granularity ownership**: the retry/DLQ producer logically belongs to the subscription on a non-partitioned topic, but the field lives on `ConsumerImpl` whose granularity is a single partition.

# Goals

## In Scope

- Introduce a shared retry/DLQ producer that is **owned by `MultiTopicsConsumerImpl`** at the subscription-level topic granularity, and reused by every per-partition sub-consumer belonging to the same subscription-level topic.
- Collapse `N × P × 2` broker-side retry/DLQ producers down to `N × 2` per subscription on a partitioned topic.
- Preserve full backward compatibility: default retry/DLQ topic names, user-supplied `DeadLetterPolicy` (including `producerBuilderCustomizer`), and the "lazy init on first use" semantic are kept unchanged.
- Provide an opt-out knob so users who prefer per-partition producers (e.g. for partition-granularity metrics) can keep the legacy behavior.
- Fix the semantic bug in `DeadLetterProducerBuilderContextImpl` where `inputTopic` was a partition-level name.

## Out of Scope

- Changing the retry/DLQ **wire protocol** or **broker-side** retry/DLQ handling.
- Sharing retry/DLQ producers **across subscriptions** or **across consumer instances** — sharing is strictly within one `MultiTopicsConsumerImpl` instance.
- Non-partitioned topics — the existing per-`ConsumerImpl` producer is already optimal; no behavior change.
- Reader API — this PIP only concerns `Consumer`.
- Any changes to the retry/DLQ **destination topic naming scheme** itself. Only *where the producer object lives* is changed.

# High Level Design

The core idea is to move retry/DLQ producer ownership one level up — from per-partition `ConsumerImpl` to the parent `MultiTopicsConsumerImpl`.

Conceptually:

```
Before (per-partition):

    MultiTopicsConsumerImpl ("foo", sub="s1")
    ├── ConsumerImpl (foo-partition-0) ── retryProducer#0 ─┐
    ├── ConsumerImpl (foo-partition-1) ── retryProducer#1 ─┼─► foo-s1-RETRY
    ├── ConsumerImpl (foo-partition-2) ── retryProducer#2 ─┤
    └── ConsumerImpl (foo-partition-3) ── retryProducer#3 ─┘   (4 broker-side producers)

After (subscription-shared):

    MultiTopicsConsumerImpl ("foo", sub="s1")
    │
    ├── SharedRetryOrDlqProducerProvider ─► retryProducer ──► foo-s1-RETRY   (1 broker-side producer)
    │                                   └─► dlqProducer   ──► foo-s1-DLQ     (1 broker-side producer)
    ├── ConsumerImpl (foo-partition-0) ─ delegates ─┐
    ├── ConsumerImpl (foo-partition-1) ─ delegates ─┤
    ├── ConsumerImpl (foo-partition-2) ─ delegates ─┼─► provider
    └── ConsumerImpl (foo-partition-3) ─ delegates ─┘
```

Key design points:

1. A new `RetryOrDlqProducerProvider` interface abstracts producer creation and lookup. Non-partitioned consumers keep using the legacy per-`ConsumerImpl` field (no provider installed).
2. For partitioned topics, `MultiTopicsConsumerImpl` creates one `SharedRetryOrDlqProducerProvider` per subscription-level topic and injects it into every sub-consumer at construction time.
3. The provider lazily creates the retry/DLQ producer on first use, using the user-provided `DeadLetterPolicy` and `producerBuilderCustomizer`. The producer's `maxPendingMessages` is scaled by partition count to preserve the aggregate client-side buffer size.
4. The provider is closed when the subscription is closed, when the topic is deleted, or when the subscription is explicitly unsubscribed. Lifecycle is centralized in `MultiTopicsConsumerImpl`.
5. For the common Pattern/MultiTopic subscription scenario where several subscription-level topics are consumed under the same subscription, each subscription-level topic gets its own provider (keyed by `TopicName.getPartitionedTopicName()`).
6. A new consumer-config boolean `shareRetryAndDeadLetterProducers` (default `true`) acts as an opt-out, flipping back to the legacy behavior.

# Detailed Design

## Design & Implementation Details

### New abstraction: `RetryOrDlqProducerProvider`

```java
public interface RetryOrDlqProducerProvider {
    CompletableFuture<Producer<byte[]>> getOrCreateRetryLetterProducer(String retryLetterTopic);
    CompletableFuture<Producer<T>>      getOrCreateDeadLetterProducer(Schema<T> schema, String deadLetterTopic);
    CompletableFuture<Void>             close();
}
```

Rationale: a single interface lets `ConsumerImpl` be oblivious to *who* owns the producer. When `provider == null`, it falls back to the legacy per-partition field — this is critical for backward compatibility and for non-partitioned topics.

### `SharedRetryOrDlqProducerProvider`

Held by `MultiTopicsConsumerImpl`, one instance per subscription-level topic:

```java
// MultiTopicsConsumerImpl
private final ConcurrentHashMap<String, SharedRetryOrDlqProducerProvider>
        sharedRetryOrDlqProducerProviders = new ConcurrentHashMap<>();
```

Key: the non-partitioned form of the subscribed topic (`TopicName.get(topic).getPartitionedTopicName()`).
Value: a provider carrying `subscription`, `DeadLetterPolicy`, `ConsumerConfigurationData`, and partition count hint.

Core semantics:
- Thread-safe lazy creation of the producer behind a per-path monitor (one for retry path, one for DLQ path, to avoid cross-path contention).
- The `closed` flag is checked inside the lock; `getOrCreate*` after `close()` returns `AlreadyClosedException` instead of silently leaking a new producer.
- `close()` uses an `AtomicBoolean` CAS so it is idempotent and safe to call from both lifecycle events and `closeAsync`.
- `maxPendingMessages` is multiplied by the current partition hint so the aggregate client-side buffer matches the pre-change `P × maxPendingMessages` sum; user-supplied `producerBuilderCustomizer` always wins.
- `updatePartitionHint(int newPartitionCount)` is invoked by `MultiTopicsConsumerImpl` when partitions are extended, so future producer creations see the correct size.

### Changes to `ConsumerImpl`

- New optional field: `private volatile RetryOrDlqProducerProvider retryOrDlqProducerProvider;` installed via `setRetryOrDlqProducerProvider(...)` right after construction.
- `initRetryLetterProducerIfNeeded` and `initDeadLetterProducerIfNeeded` delegate to the provider when present; otherwise keep the legacy local-field path.
- `closeAsync` **does not close** the retry/DLQ producer when the provider owns it, because the lifecycle belongs to the parent `MultiTopicsConsumerImpl`.
- The retry-topic back-off counters are promoted from `volatile int` to `AtomicInteger` because multiple sub-consumers can now invoke `whenComplete` callbacks on the shared producer concurrently.

### Changes to `MultiTopicsConsumerImpl`

Lifecycle hooks:

| Hook | Behavior |
| --- | --- |
| `createInternalConsumer()` | Looks up / creates a `SharedRetryOrDlqProducerProvider` for the subscription-level topic and injects it into the new sub-consumer. |
| Partition extension (`onTopicsExtended`) | Calls `updatePartitionHint(newCount)` on the existing provider. |
| `unsubscribeAsync` success | Removes and closes the provider for the unsubscribed topic. |
| Pattern consumer `onTopicDeletion` | Same as unsubscribe: remove + close. |
| `handleSubscribeOneTopicError` | Cleanup fallback: if subscribe fails after a provider was created, remove + close to prevent provider leaks. |
| `closeAsync` | Closes all sub-consumers first, then drains all providers via `whenCompleteAll`, preserving in-flight retry/DLQ writes. |

### Semantic fix: `DeadLetterProducerBuilderContextImpl`

Previously constructed with the partition-level topic name (`foo-partition-0`). The shared provider now constructs it with the non-partitioned topic name, so a user's `producerBuilderCustomizer(context, builder)` sees the correct `context.getInputTopic() == "foo"`.

### Opt-out knob

A new field is added to `ConsumerConfigurationData`:

```java
/**
 * Whether to share retry-letter and dead-letter producers across all partitions
 * of the same subscription-level topic. Enabled by default. Set to {@code false} to
 * restore the legacy per-partition producer behavior (e.g. for per-partition metrics).
 */
private boolean shareRetryAndDeadLetterProducers = true;
```

When set to `false`, `MultiTopicsConsumerImpl` does not install the provider, and every sub-consumer falls back to the legacy per-partition retry/DLQ producer field.

## Public-facing Changes

### Public API

No breaking change. One new builder method on `ConsumerBuilder`:

```java
/**
 * Control whether retry-letter and dead-letter producers are shared across all
 * partitions of the same subscription-level topic.
 *
 * <p>Default: {@code true}. For a {@code P}-partition topic this collapses
 * {@code P × 2} broker-side producers to {@code 2}, drastically reducing
 * broker and client resource usage.
 *
 * <p>Set to {@code false} to restore the legacy per-partition behavior, e.g.
 * if you depend on per-partition retry/DLQ producer stats.
 */
ConsumerBuilder<T> shareRetryAndDeadLetterProducers(boolean enabled);
```

### Binary protocol

Not affected.

### Configuration

Added:

- `ConsumerConfigurationData#shareRetryAndDeadLetterProducers` (boolean, default `true`).

Only the client-side consumer configuration is changed; no broker config change.

### CLI

Not affected.

### Metrics

Impact on existing metrics (behavioral change, no renaming):

- `ConsumerStats#getRetryLetterProducerStats()` and `ConsumerStats#getDeadLetterProducerStats()` on a `MultiTopicsConsumer` now report **one logical producer per subscription-level topic**, rather than one per partition.
- Users who aggregate retry/DLQ producer stats across partitions will see the pre-change `P ×` value collapse to `1 ×`. Semantics are unchanged — the aggregated numbers are equivalent because all partitions were pointing to the same destination topic.

No new metrics are introduced.

# Monitoring

Operators should pay attention to:

- **`DeadLetterProducerStats#numMsgsSent`**: now a per-subscription total; combine with your consumer-fleet size to estimate real DLQ throughput.
- **Broker-side `pulsar_producer_count`** on topics ending with `-RETRY` / `-DLQ`: after upgrade the count on these topics should drop by a factor of ~`P`. A sudden spike back to the old value is a strong signal that `shareRetryAndDeadLetterProducers` was turned off or that an older client is reconnecting.
- **Client-side allocated-direct-memory**: expect a measurable reduction for workloads with high partition counts.

Suggested alert: if, after upgrade, the retry/DLQ producer count per subscription on a partitioned topic is still ≥ partition count × 0.8, investigate whether the opt-out is unintentionally enabled.

# Security Considerations

Producer authentication/authorization is unchanged: the shared retry/DLQ producer uses the same `AuthenticationDataProvider` as the owning consumer. Because sharing is strictly scoped to one `MultiTopicsConsumerImpl` instance (same subscription, same subscription name, same auth principal), no cross-tenant or cross-subscription data path is introduced. The only observable change is that there is one broker-side producer object instead of `P`, which is strictly a reduction of attack surface, not an expansion.

# Backward & Forward Compatibility

## Upgrade

- No special action required. On client library upgrade, existing subscriptions on partitioned topics automatically start sharing retry/DLQ producers.
- Mixed-version client fleets are fully supported: shared vs. per-partition producers coexist on the broker side (they just happen to be different producer objects writing to the same `-RETRY`/`-DLQ` topic).
- No broker-side upgrade is required; this is purely a client-side refactor.

## Downgrade / Rollback

Two options:

1. **Downgrade the client library** to a previous release — behavior reverts automatically.
2. **In-place opt-out without downgrade**: set `shareRetryAndDeadLetterProducers(false)` on the `ConsumerBuilder` (or the field on `ConsumerConfigurationData` for API users). This restores per-partition producers without any dependency change.

Metrics consumers that previously aggregated per-partition retry/DLQ stats keep working because `ConsumerStats` still exposes the same methods; only the number of underlying producer rows reported changes.

## Pulsar Geo-Replication Upgrade & Downgrade/Rollback Considerations

Not affected. Retry/DLQ producers are purely a client-side consumer-side concept; geo-replication of the `-RETRY`/`-DLQ` topics (if enabled) is governed by the usual topic policies and does not depend on how many producer handles the client holds.

# Alternatives

**A1. Share across all consumer instances via a client-wide cache keyed by `(topic, subscription)`.**
Rejected because it introduces cross-consumer lifecycle coupling: closing one consumer should not affect another's retry/DLQ ability; and because the cache would have to be keyed by auth principal, schema and `DeadLetterPolicy`, which complicates the API surface. Within a single `MultiTopicsConsumerImpl` these dimensions are naturally uniform.

**A2. Keep per-partition producers but lower their `maxPendingMessages`.**
Rejected because it does not reduce broker-side producer count — the dominant cost — and worsens tail-latency for sub-consumers that occasionally burst retry/DLQ traffic.

**A3. Build a dedicated internal producer that bypasses `ProducerImpl` and talks straight to the destination topic.**
Rejected: too invasive, loses user-visible configuration (`producerBuilderCustomizer`, interceptors, schema), and would duplicate flow-control, batching and stats logic that `ProducerImpl` already handles.

# General Notes

- The default is **on** rather than opt-in because the behavioral change is semantically equivalent for every user who does not depend on per-partition retry/DLQ producer stats, and the resource savings on partitioned topics are substantial (common deployments see 10×–50× fewer producer objects).
- The default-on choice is documented explicitly in the opt-out field's javadoc so users spot the change in release notes.
