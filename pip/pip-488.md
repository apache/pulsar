# PIP-488: Pluggable authentication audit-event hook

# Background

**How Pulsar authenticates clients.** Two paths do the work:

- For HTTP and admin requests, a class called `AuthenticationService` (in the `pulsar-broker-common` module) checks the credentials and returns the caller's role.
- For the binary protocol, each connection has an `AuthenticationState` object inside `ServerCnx`. It either produces a role or throws an error. Long-lived connections re-check their credentials from time to time by calling `refreshAuthentication()`.

**What you can see today.** The only thing Pulsar reports per authentication is `AuthenticationMetrics`. These are just counters: how many logins succeeded or failed, grouped by provider and error code. There
is no way to get a single record that says "user P logged in with token auth from IP A at 10:00," or "someone from IP A failed to log in because the token was expired." You get numbers, not events.

**The closest thing that already exists: `BrokerInterceptor`.** Pulsar has a plugin interface, `org.apache.pulsar.broker.intercept.BrokerInterceptor`, that you load by class name with the `brokerInterceptors` setting. It is the nearest thing to an authentication hook, so it is fair to ask "why not just use that?" Here is why it does not fit, checked against the current code:

- **It only sees successes.** Its connection callback, `onConnectionCreated(ServerCnx)`, runs after a binary login *succeeds*. A failed login never gets there, and there is no callback for a re-check. But failures and re-checks are exactly what an audit trail is about.
- **It runs on the hot path and can block.** Interceptors are called one by one on the same thread that handles the connection. A slow interceptor slows down the login. There is no queue and no way to drop work under load.
- **It is not related to an authentication, and HTTP is not covered well.** `onConnectionCreated` hands you the internal `ServerCnx`, not a clean "here is what happened" record. On the HTTP side, the only hook (`onWebserviceRequest`) fires on every request and just gives you the raw servlet request - it does not tell whether authentication passed or failed, or as whom.
- **It lives in the wrong module for the HTTP path.** HTTP authentication happens in `AuthenticationService`, which is in `pulsar-broker-common`. That module cannot see `BrokerInterceptor`, because that class lives in `pulsar-broker`.

I think there is a gap. The open question is not *whether* to fill it, but *how*: grow the existing interceptor, or add a small new hook just for authentication. This PIP describes both and asks the community to pick one.

**Why operators care.** Security teams need an audit trail of logins so they can feed a SIEM, spot attacks (a burst of failures from one IP, or a user showing up from an unexpected place), investigate
incidents, and satisfy compliance rules. Counters cannot tell you "who, from where, when, and why did this fail." Other systems, such as Kafka, already expose this. Pulsar does not as it looks for me, unless you patch the broker.

# Motivation

Operators who want an authentication audit trail have no good option today, especially for failed and refreshed logins:

- Reading provider log files can be messy: the format differs per provider, and most providers do not log each login at all.
- The metrics are just counters, with no user, source, time, or reason.
- `BrokerInterceptor` only sees successful binary logins, runs on the hot path, and misses the HTTP outcome (see *Background knowledge*).
- Forking the broker is not a real option.

This proposal adds a small, optional hook. You plug in a listener, and it receives a clean record every time a login succeeds, fails, or is refreshed. The record is handed off in the background, so it never
slows down or breaks authentication. If you do not configure a listener, nothing changes and there is no cost.

# Goals

## In Scope

- A hook that receives a structured `AuthenticationEvent` on **success**, **failure**, and **refresh** of a login, for both the binary and HTTP/HTTPS paths.
- The `AuthenticationEvent` record itself: type, method, principal, remote address, transport, timestamp, and (on failure) a reason and code. No secrets.
- Delivery that is **isolated and non-blocking**, so a slow or buggy listener can never stall or fail a login.
- A decision, on the discussion thread, between the two options in *High Level Design*.

## Out of Scope

- Authorization (allow/deny on produce, consume, or admin). The same idea could later carry an `AuthorizationEvent`; this PIP handles authentication and leaves room for that, but does not build it.
- A ready-made sink (writing to a file, a topic, or a specific SIEM). This PIP defines the hook and the events; sinks can be shipped later or as examples.
- Changing what counts as success or failure. The hook only watches the existing decision. It does not change it.

# High Level Design

Whichever option we pick, three parts stay the same. They are the real work of this PIP:

1. **The `AuthenticationEvent` record** - the plain, secret-free object described in *Detailed Design*.
2. **Where events are emitted** - on success, failure, and refresh, on both the binary path (`ServerCnx` / `AuthenticationState`) and the HTTP/HTTPS path (`AuthenticationService.authenticateHttpRequest`). These are the same spots where `AuthenticationMetrics` is already updated.
3. **How events are delivered** - through a small, bounded background queue. If a listener throws, we catch it and count it. If the queue is full, we drop the event and count that too. Authentication never waits.

The only real difference between the options is *what the plugin interface looks like and where it lives*.

## Option A - grow `BrokerInterceptor`

Add one authentication callback to the interceptor Pulsar already has, and reuse everything it already does: loading by class name (`brokerInterceptors`), the `initialize`/`close` lifecycle, and the enable/disable logic.

- Add a `default` (do-nothing) method `onAuthenticationEvent(AuthenticationEvent)` to `BrokerInterceptor`. Because it does nothing by default, existing interceptors keep working and nothing breaks.
- Interceptors normally run inline, which could block. So `BrokerInterceptors` gets a small background queue used **only** for these authentication events. Every other interceptor callback keeps working exactly as before.
- Binary events are emitted from `ServerCnx`, which already has the interceptor and the client address. HTTP/HTTPS events are emitted from the web layer (`AuthenticationFilter` / `PreInterceptFilter`), which can see the interceptor - not from `AuthenticationService`, which cannot.

## Option B - a dedicated `AuthenticationEventListener`

Add a small, purpose-built interface in `pulsar-broker-common`, loaded by a new `authenticationEventListeners` setting, with the background queue owned by `AuthenticationService`.

- `AuthenticationService` emits the HTTP/HTTPS events directly. This is the simplest place, because the authentication logic and the emission sit together in one module. `ServerCnx` emits the binary events.
- The cost is one more plugin interface and one more setting to learn.

## Comparing the two

| Question | Option A: grow `BrokerInterceptor` | Option B: new `AuthenticationEventListener` |
|----------|------------------------------------|---------------------------------------------|
| New interface? | No, just one new default method | Yes, one new interface |
| How it loads | Reuses `brokerInterceptors` | New `authenticationEventListeners` setting |
| Module | `pulsar-broker` | `pulsar-broker-common` |
| Where HTTP events come from | The web filter | `AuthenticationService` (natural fit) |
| Background delivery | Have to add an async path to an otherwise-inline interface | Built in from the start |
| Objection it answers | "Why add a second plugin for this?" | "Why bolt authentication onto a general interceptor?" |
| Worry it raises | One interface now behaves two ways (inline and async) | Yet another plugin interface |

Either way, the login result is decided exactly as it is today. The listener only watches. **We recommend Option A**, to avoid adding a second plugin, and keep Option B as the fallback if people prefer keeping authentication concerns separate. Picking between them is the main thing to settle on the discussion thread.

# Detailed Design

## Design & Implementation Details

### The `AuthenticationEvent` record (shared)

```java
public final class AuthenticationEvent {
    public enum Type { SUCCESS, FAILURE, REFRESH_SUCCESS, REFRESH_FAILURE }
    public enum Transport { BINARY, HTTP, HTTPS }

    long timestampMs;
    Type type;
    String authMethod;          // e.g. "token", "tls", "scram-sha-256"
    String principal;           // the role on success/refresh; null on failure
    String remoteAddress;       // client socket address
    Transport transport;
    String failureCode;         // provider error code on failure; null otherwise
    String failureReason;       // short message on failure; null otherwise
    Long connectionStateId;     // AuthenticationState.getStateId(), when available
    // On purpose, NO credentials here: no token, no password, no proof.
}
```

Under Option A this class will be next to `BrokerInterceptor` in `pulsar-broker`. Under Option B it will be in `pulsar-broker-common` (`org.apache.pulsar.broker.authentication`). Either way it starts as `@InterfaceStability.Evolving` so we can adjust it early on.

### The delivery queue (shared)

A small, bounded background queue with one worker (or a few):

- `notifyAuthenticationEvent(event)` drops the event on the queue and returns right away. If the queue is full, it bumps a "dropped" counter and moves on. We favor keeping the broker available over guaranteeing every event.
- Each event is passed to every listener inside a `try/catch`. If a listener throws, we bump an "error" counter and keep going.
- `close()` drains and closes the listeners.

Under Option A this queue lives in `BrokerInterceptors`; under Option B it lives in `AuthenticationService`.

### Where events are emitted (shared)

- **HTTP/HTTPS:** emit a SUCCESS with the role we returned, and a FAILURE in the existing error handler. In Option B this happens inside `AuthenticationService.authenticateHttpRequest(...)`. In Option A it happens in the web filter that wraps that call (because of the module boundary above).
- **Binary:** when `AuthenticationState` finishes, emit a `BINARY` SUCCESS (principal from `getAuthRole()`, id from `getStateId()`); if it throws, emit a FAILURE. The client address is already on the connection. Both options emit this from `ServerCnx`, right where `authState.authenticateAsync(...).whenComplete(...)` runs.
- **Refresh:** when a re-check finishes or throws, emit `REFRESH_SUCCESS` or `REFRESH_FAILURE`.

All of these are the same places where `AuthenticationMetrics` is already updated, so the new emit calls sit right next to the existing metric calls.

## Public-facing Changes

### Public API

No REST changes. New plugin types, depending on the option:

- **Option A:** one new `default void onAuthenticationEvent(AuthenticationEvent)` method on `BrokerInterceptor`, plus the `AuthenticationEvent` class.
- **Option B:** new `AuthenticationEventListener`, `AuthenticationEventListenerContext`, and `AuthenticationEvent` classes in `org.apache.pulsar.broker.authentication`.

Neither breaks anything: Option A only adds a default method, and Option B only adds new classes.

### Binary protocol

None.

### Configuration

- **Option A:** no new loading setting - listeners are just interceptors under the existing `brokerInterceptors`. Adds `authenticationEventQueueSize` (queue capacity; when full, events are dropped and counted). Default TBD on the discussion thread.
- **Option B:** adds `authenticationEventListeners` (comma-separated class names; empty by default, which means the feature is off and costs nothing) and `authenticationEventQueueSize`.

### CLI

None.

### Metrics

- `pulsar_authn_events_emitted_total`
  - What it counts: authentication events put on the queue.
  - Labels: `type` (`success`, `failure`, `refresh_success`, `refresh_failure`).
  - Unit: events (counter).
- `pulsar_authn_events_dropped_total`
  - What it counts: events dropped because the queue was full.
  - Labels: none.
  - Unit: events (counter).
- `pulsar_authn_listener_errors_total`
  - What it counts: listener calls that threw.
  - Labels: `listener` (the listener class name).
  - Unit: calls (counter).
- `pulsar_authn_listener_dispatch_seconds`
  - What it measures: how long it takes to hand an event to listeners (to catch a slow one).
  - Labels: none.
  - Unit: seconds (histogram).

# Monitoring

- Watch `pulsar_authn_events_dropped_total`. If it is above zero or rising, your audit trail has gaps, because a listener cannot keep up. Either the listener is too slow, or `authenticationEventQueueSize` is too small.
- Watch `pulsar_authn_listener_errors_total`. If it climbs, a listener is misbehaving.
- The events themselves are the real monitoring material. Rules like "too many failures from one IP", "this user just appeared from two far-apart places," or "first time we have seen this source for this role" live in your SIEM, built on the event stream - not on Pulsar's own metrics.

# Security Considerations

- **No secrets in events.** `AuthenticationEvent` leaves out all credentials on purpose: no token, no password, no SCRAM proof. It carries who and where, not the secret. The contract says listeners should not try to get secrets, and none are handed to them.
- **Listeners are trusted code running inside the broker.** Like authentication providers and interceptors, they run in-process, so operators must review the code they plug in. The types expose only the event, not the broker's internals.
- **It cannot weaken authentication.** Delivery happens after the decision, off to the side, and never blocks. A listener cannot let a rejected login through, cannot reject an accepted one, and cannot stall the handshake. When the queue is full we drop events (choosing availability), but we count the drops so operators who need every event can size the queue and alert on drops. A stricter "store the event before allowing the login" mode would block logins and is a separate proposal, not this one.
- **Personal data.** Events include principals and source addresses. If you send them to a SIEM, handle them under your own data rules. This is normal for audit logging and just worth calling out. (Related: PIP-402 controls how roles show up in broker logs.)
- **Multi-tenancy.** These events are for the broker operator - an audit of the broker's own logins. They are not tenant-facing, and no tenant can see another tenant's events.

# Backward & Forward Compatibility

## Upgrade

Nothing to do. The feature is fully additive.

- **Option A:** the new interceptor method does nothing by default, so existing interceptors and setups are unaffected. With no interceptor watching authentication, the emit calls short-circuit.
- **Option B:** with `authenticationEventListeners` empty (the default), no listener loads, no queue is created, and the emit calls short-circuit. No change in behavior or performance.

## Downgrade / Rollback

There is no stored state, so there is nothing to clean up. Remove the listener or interceptor setting, or downgrade to a version without the feature. Authentication behaves exactly as before.

## Pulsar Geo-Replication Upgrade & Downgrade/Rollback Considerations

The hook is per-broker and keeps no state. Each broker audits the logins it handles, and there is no link between clusters. In a geo-replicated setup, turn the listener on for every broker whose logins you want audited; brokers in different clusters emit on their own. Upgrading or rolling back one cluster does not affect auditing in another.

# Alternatives

- **Use `BrokerInterceptor` as it is.** 
  It only sees successful binary logins, runs on the hot path, is not really about authentication, does not give a clean HTTP outcome, and cannot be reached from `pulsar-broker-common` (see *Background knowledge*). *Growing* it is Option A; using it unchanged does not give a failure/refresh audit trail.
- **Read provider log files.** 
  Messy, provider-specific, usually missing, and hard to collect centrally.
- **More metrics.** 
  Counters cannot carry the user, source, time, and reason of each login, which is the whole point. (PIP-471 adds *authorization* metrics - a nice complement, not a replacement for per-login authentication audit.)
- **A blocking "store before allow" hook.** 
  Making every login wait for the event to be saved turns a slow audit sink into a login outage. The non-blocking, drop-and-count design is the safe default; a blocking mode can come later for teams that accept the trade-off.
- **Write to a fixed built-in sink (file or topic).**
  A pluggable hook lets each operator point at their own SIEM. Concrete sinks can be added later on top of the hook.

# General Notes

This is a small, contained change: one record type, one background queue, and a few emit calls placed right next to the existing `AuthenticationMetrics` updates - attached either to the interceptor Pulsar already has (Option A) or to a small new hook (Option B). It plays well with the other authentication proposals: things like SCRAM failures and delegation-token changes all show up as `AuthenticationEvent`s, so operators get one audit stream for the whole authentication surface. We note where a future `AuthorizationEvent` could plug in, but we do not build it here.
