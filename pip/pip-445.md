# PIP-445: Add Builder Methods to Create Message-based TableView

# Background knowledge

* **TableView**: In Pulsar, a `TableView` is a client-side abstraction that provides a key-value map interface over a Pulsar topic. It consumes messages from the topic (typically a compacted one) and maintains an in-memory view of the latest value for each key. This allows applications to easily query the current state of a key without managing a consumer manually.

* **Pulsar `Message<T>`**: A Pulsar message is not just its data payload. The `Message<T>` object is a container that includes the deserialized **payload** (`T`) as well as important **metadata**, such as a message key, user-defined properties (a key-value map), event time, publish time, and more.

# Motivation

The current `TableView` API provides a `get(String key)` method that only returns the deserialized **value** (`T`) of the latest message for a given key. This limits its usefulness for applications that need access to the message's metadata.

For instance, a user might need to inspect the message **properties** to get a trace-id or check the **event time** to determine if the data is recent. Currently, the only way to access this metadata is to create a separate, redundant `Consumer` on the same topic, which is inefficient and undermines the convenience of using a `TableView`.

This proposal aims to solve this problem by providing a way to create a `TableView` that exposes the entire `Message<T>` object.

# Goals

## In Scope

* Add new generic methods, `createMapped()` and `createMappedAsync()`, to the `TableViewBuilder<T>` interface, which accept a `TableViewMessageMapper<T, V>`.
* Allow users to create a `TableView<V>` instance by providing a mapper that transforms a `Message<T>` into a custom object `V`. This includes the ability to create a `TableView<Message<T>>` by passing an identity mapper (`msg -> msg`).
* Define what happens when the mapper throws for a message, and give the application a callback to observe such failures.
* Ensure the change is fully backward-compatible and does not impact the performance of existing `TableView` users.

## Out of Scope

* Modifying the API of the existing `create()` and `createAsync()` methods in the builder.
* Changing the underlying topic compaction logic or any broker-side functionality.
* Supporting a `TopicCompactionStrategy` for mapped table views. A `TopicCompactionStrategy` compares values of the topic's schema type, which a mapped table view does not store, so the combination is rejected rather than defined.
* Retrying, re-reading or otherwise recovering messages that the mapper failed to map. Such messages are skipped; the application decides what to do about it through the error callback.

# High Level Design

The proposed solution is a simple and non-breaking addition to the public client API. Instead of adding a specific method for retrieving messages, we will introduce a more flexible, generic mapping mechanism.

1.  New generic methods, `<V> TableView<V> createMapped(...)` and `<V> CompletableFuture<TableView<V>> createMappedAsync(...)`, will be added to the `TableViewBuilder<T>` interface.
2.  These methods will accept a new functional interface, `TableViewMessageMapper<T, V>`, as a parameter. Its `map` method defines how to transform an incoming raw `Message<T>` into a value `V` to be stored in the `TableView`; its `onMappingError` default method is called when `map` throws for a message.
3.  This approach provides maximum flexibility. Users who need the entire `Message<T>` object can simply pass `msg -> msg` as the mapper. Other users can create custom, memory-efficient objects containing only the necessary data from the message payload and metadata. Users who need to observe mapping failures implement the interface as a class and override `onMappingError`.
4.  A dedicated interface is used instead of `java.util.function.Function` so that the error callback lives next to the mapping code that caused the error, so that `map` may throw checked exceptions, and so that further callbacks can be added later as `default` methods without breaking existing implementations. Because an implicitly typed lambda is applicable to both a `Function` and a `TableViewMessageMapper` parameter, the two cannot coexist as overloads of `createMapped`; the dedicated interface is the only parameter type.
5.  The existing `create()` and `createAsync()` methods keep their API and their behavior, with one exception described below: a message whose lazily decoded value throws is now skipped consistently in both the initial replay and the tailing phase, instead of failing `create()` in the former and being dropped with a misleading log in the latter.

# Detailed Design

## Design & Implementation Details

The changes will be confined to the Pulsar client library.

* **Refactoring of `org.apache.pulsar.client.impl.TableViewImpl<T>`**:
  * The existing `TableViewImpl<T>` class is refactored into a new inheritance structure.
  * The core logic is moved to a new abstract base class, `org.apache.pulsar.client.impl.AbstractTableViewImpl<T, V>`.
  * To preserve the original functionality, the existing `org.apache.pulsar.client.impl.TableViewImpl<T>` class becomes a simple subclass that extends `AbstractTableViewImpl<T, T>`.

* **New `MappedTableViewImpl` implementation**:
  * `org.apache.pulsar.client.impl.MappedTableViewImpl<T, V>`: A new package-private class that extends `AbstractTableViewImpl<T, V>`. It implements the logic for the new `createMapped` methods, using the supplied `TableViewMessageMapper<T, V>` to transform messages into the values stored in the `TableView` and delegating mapping failures to the mapper's `onMappingError`.
  * Message pooling is disabled for mapped table views, since the mapper may retain the `Message` instance.

* **Mapping failures in `AbstractTableViewImpl`**:
  * The value extraction of a keyed message is guarded. If it throws, the message is skipped: the view is not modified for the key, listeners are not notified, and the read position used by `refreshAsync()` still advances so that a pending refresh (including one issued from the error callback) observes the message as processed.
  * The failure is reported through a protected hook that `MappedTableViewImpl` routes to `TableViewMessageMapper.onMappingError`. If the hook returns `false` — the default — the table view logs the failure at `ERROR` level with the topic, key and message id. Exceptions thrown by the callback are logged and ignored.
  * Previously, an exception from the value extraction escaped into the reader loop, where it was logged as a reader failure: during the initial replay it failed table view creation while leaving the reader open, and during tailing the message was dropped without any attributable log.
  * When the initial replay fails, the reader is now closed instead of being leaked. A failure of the `hasMessageAvailable` check during the replay now fails the replay as well, instead of leaving `create()` waiting forever.

* **Class `org.apache.pulsar.client.impl.TableViewBuilderImpl<T>`**:
  * The builder's implementation will be updated to use the new classes.
  * `create()` and `createAsync()` will keep instantiating `org.apache.pulsar.client.impl.TableViewImpl<T>` to provide the classic `TableView` behavior.
  * The new `createMapped()` and `createMappedAsync()` methods will instantiate `MappedTableViewImpl<T, V>` with the user-provided mapper. They reject a `null` mapper and a configured `topicCompactionStrategyClassName` with an `IllegalArgumentException` (a failed future in the asynchronous variant).

# Public-facing Changes

## Public API

A new functional interface is added to the `org.apache.pulsar.client.api` package, and new generic methods are added to the `org.apache.pulsar.client.api.TableViewBuilder<T>` interface.

* **New interface `TableViewMessageMapper<T, V>`**:
    ```java
    @InterfaceAudience.Public
    @InterfaceStability.Evolving
    @FunctionalInterface
    public interface TableViewMessageMapper<T, V> {

        V map(Message<T> message) throws Exception;

        default boolean onMappingError(Message<T> message, Throwable error) {
            return false;
        }
    }
    ```
  * `map`: Maps a keyed message with a non-empty payload to the value stored for the message key. Returning `null` removes the key. May throw; the message is then skipped.
  * `onMappingError`: Called when `map` throws. The message has already been skipped and the callback cannot change that. Returning `true` marks the failure as handled; the default returns `false`, which makes the table view log the failure at `ERROR` level with the topic, key and message id. Exceptions thrown by the callback are logged and ignored.
  * Both methods are invoked on the client's internal thread, one message at a time in read order, and must not block. An implementation that wants to stop the application on a mapping failure must signal another thread rather than close the table view or exit from the callback.
  * Further callbacks may be added later as `default` methods that do nothing unless overridden.

* **Method Signatures in `TableViewBuilder<T>`**:
    ```java
    <V> TableView<V> createMapped(TableViewMessageMapper<T, V> mapper) throws PulsarClientException;

    <V> CompletableFuture<TableView<V>> createMappedAsync(TableViewMessageMapper<T, V> mapper);
    ```
* **Description**: Creates a `TableView` instance where the values are produced by a user-defined `mapper` from each message. This provides a flexible way to create a key-value view over a topic, allowing users to extract data from the message payload, properties, and other metadata into a custom object `V`. To get a view of the full `Message<T>` objects, `msg -> msg` can be used as the mapper.
* **Parameters**:
  * `mapper`: A `TableViewMessageMapper<T, V>` that produces the value of type `V` for each `Message<T>`.
* **Return Value**: A `TableView<V>` instance.
* **Behavior Notes**:
  * Message pooling is not used for mapped table views, so the `Message` instance passed to the `mapper` can be safely retained (e.g. when `msg -> msg` is used as the mapper).
  * A keyed message with an empty payload is a tombstone: the key is removed from the `TableView` and the mapper is not called for it. A mapper that derives the value from the key or the properties alone therefore never sees such a message.
  * If the `mapper` returns `null`, it is treated as a tombstone message, and the corresponding key will be removed from the `TableView`.
  * If the `mapper` throws, the message is skipped: the key keeps its previous value in the `TableView` (or stays absent), listeners are not notified, a pending `refreshAsync()` still completes, and `onMappingError` is called. A message that fails to map is not retried; a later message for the same key updates the key normally.
  * A `null` mapper and a `topicCompactionStrategyClassName` loaded with `loadConf` are rejected with an `IllegalArgumentException` (`createMapped`) or a future failed with one (`createMappedAsync`).

# Monitoring

No new metrics are introduced by this change. Existing client-side metrics are unaffected.

# Security Considerations

This proposal has no security implications. The new method exposes message metadata that the client is already authorized to receive by consuming the topic. It does not alter any authentication or authorization mechanisms.

# Backward & Forward Compatibility

This change is fully backward-compatible.

* The addition of new methods to the builder interface and of a new interface is a non-breaking change. Existing code that uses `create()` or `createAsync()` will continue to function as before with no performance changes.
* One behavioral change applies to `create()` and `createAsync()`: a message whose lazily decoded value throws (for example a schema decoding failure) is now skipped and logged at `ERROR` level with the topic, key and message id, in both the initial replay and the tailing phase. Previously such a message failed `create()` during the initial replay (leaving the reader open) and was silently dropped during tailing with a log message that blamed the reader. The tailing behavior is therefore unchanged apart from the log message, and the replay behavior becomes consistent with it.
* This applies to the broker's own use of `create()` as well: the extensible load balancer's `ServiceUnitStateTableViewImpl` builds its channel view with `create()`. A `ServiceUnitStateData` message that fails to decode no longer prevents the channel from starting when it is replayed; it is skipped and logged at `ERROR` level, exactly as it already was when the same message arrived while tailing. This trade is deliberate: a broker that cannot start its load balancer channel because of one undecodable record is a worse outcome than a broker that skips the record and reports it. A programmatic failure signal for plain `create()` views, equivalent to `onMappingError`, is left for a follow-up proposal.

## Upgrade

The upgrade process is seamless. Applications can update their client dependency to a version containing this feature and start using the new builder methods without any other changes.

## Downgrade / Rollback

A downgrade is also seamless. If an application that uses the new `createMapped` methods is rolled back to an older client version, it will fail at compile time. Applications that do not use the new methods can be rolled back without any issues.

## Pulsar Geo-Replication Upgrade & Downgrade/Rollback Considerations

This is a client-side change and has no impact on geo-replication.

# Alternatives

## Add `getRawMessage(String key)` to `TableView`

An alternative considered was to add a `getRawMessage(String key)` method directly to the `TableView` interface. This would have required modifying the existing `TableViewImpl` to store the entire `Message<T>` object for all users.

This approach was rejected because it would be a **breaking change in terms of performance**. It would increase memory and CPU consumption for all `TableView` users, even those who do not need access to the raw message. The proposed builder-based approach is superior as it makes this an opt-in feature, preserving the performance characteristics of the existing `TableView`.

## Accept a `java.util.function.Function<Message<T>, V>` as the mapper

The initial version of this proposal accepted a plain `Function<Message<T>, V>`. It was replaced with the dedicated `TableViewMessageMapper<T, V>` interface because a plain function has no place for an error callback: a mapping failure could only be handled with a separate builder setter that would have to be ignored for `create()`, or left undefined. The dedicated interface keeps the error handling next to the mapping code, allows `map` to throw checked exceptions, and can be extended with further `default` methods later. Since an implicitly typed lambda is applicable to both parameter types, keeping both overloads would make every `createMapped(msg -> ...)` call ambiguous, so the `Function` variant is not offered.

## Add specific `createForMessages()` methods

Another alternative was to add specific, non-generic methods like `createForMessages()` that would always return a `TableView<Message<T>>`.

This approach was rejected because it is less flexible than the mapper-based solution. The `createMapped` approach covers the `createForMessages` use case (via `msg -> msg`) while also empowering users to perform custom transformations, making it a more powerful and future-proof API.
