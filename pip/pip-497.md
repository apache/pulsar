# PIP-497: Subscription-scoped internal statistics for persistent topics

> **Status:** Draft for discussion.

# Background knowledge

A persistent Pulsar subscription is backed by a managed-ledger cursor. The cursor tracks its read and
mark-delete positions, individually deleted ranges, persistence state, and pending reads. Durable
subscriptions persist this state; non-durable subscriptions retain it only while active.

The existing topic-level API:

```text
GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/internalStats
```

returns topic ledgers, every managed-ledger cursor, schema and compaction state, and optional BookKeeper
metadata. An operator interested in one subscription must retrieve and filter this complete response.
Some cursor fields, especially `individuallyDeletedMessages`, can be large.

A subscription name is not a generic cursor name. Topics also have implementation-specific cursors for
replication, deduplication, and transaction recovery. Those components need diagnostics beyond cursor
positions, and their raw names and lifecycles are not public contracts.

For a partitioned topic, each physical partition has an independent cursor, ledger IDs, positions, and
owner broker. These values cannot be reduced to one meaningful global cursor position.

# Motivation

Operators frequently need to diagnose why one subscription is not advancing. Fetching complete topic
internal statistics makes the broker inspect and serialize unrelated ledgers, cursors, schema state, and
compaction state, and transfers all of that data to the caller.

The problem is response scope, not missing diagnostic data: the required cursor fields already exist,
but they cannot be retrieved independently for one subscription.

This PIP adds a subscription-scoped diagnostic API. For an already-loaded topic, response assembly no
longer enumerates unrelated cursors or topic-level internal state. It is not necessarily cheap:
collecting the selected cursor can still stringify large deleted ranges and inspect ledger descriptors,
and an existing cold topic can still incur its normal load and recovery cost.

# Goals

## In Scope

- Query one existing subscription-backed cursor on a persistent non-partitioned topic or explicit
  partition.
- Query a partitioned base topic and return independent results for its physical partitions.
- Expose the existing `ManagedLedgerInternalStats.CursorStats` plus selected durability, persistence,
  and activity state.
- Provide REST, synchronous and asynchronous Java Admin, and `pulsar-admin topics` access.
- Preserve the existing topic-level internal-statistics contracts.
- Use the existing `TopicOperation.GET_STATS` authorization model.
- Do not create a missing topic or subscription, explicitly advance or reset a cursor, or invent a
  global cursor position. The operation does not request cursor or metadata mutation; existing side
  effects of normal cold-topic load and recovery remain unchanged.

## Out of Scope

- A public API for arbitrary raw managed-ledger cursor names.
- Type-specific diagnostics for replication, deduplication, compaction, or transactions.
- Non-persistent topics, exact backlog calculation, message payload access, or an atomic snapshot.
- Exposing private pending-operation queues without a concurrency-safe public accessor.
- Changes to the binary protocol, configuration, metrics, or stored metadata.

## Discussion focus

This draft makes concrete choices so the community can discuss one complete contract. The main choices
on which feedback is requested are:

- broker-side partition fan-out in the first version versus explicit partitions only;
- a response wrapper with supplementary fields versus bare `CursorStats`;
- full individual-deleted ranges by default versus a summary mode; and
- `GET_STATS` authorization versus subscription-level consume permission.

# High Level Design

This PIP introduces two read-only resources:

```text
GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/subscription/{subName}/internalStats
GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/subscription/{subName}/partitioned-internalStats
```

The first accepts a non-partitioned topic or explicit physical partition. The second accepts a
partitioned base topic and performs bounded asynchronous fan-out. The single-topic response wraps the
existing cursor statistics. The partitioned response retains each physical partition and explicitly
reports partial failures.

Both resources resolve `subName` through the topic's subscription registry. They can therefore query
durable subscriptions, active non-durable subscriptions, and system-managed entries currently present
in that registry. They do not provide system-subscription discovery or make reserved names stable.

# Detailed Design

## Resource model

| Cursor use | Addressable | Reason |
|---|---:|---|
| Durable subscription | Yes | It is an existing subscription-backed cursor. |
| Active non-durable subscription or reader | Yes | It is addressable while present and returns `404` after it disappears. |
| System-managed subscription-registry entry | Yes, while present | It follows normal subscription lookup; no discovery or stable-name contract is added. |
| Replication, shadow-replication, or deduplication cursor | No | It is not a subscription and needs component-specific state. |
| Transaction-recovery or separate transaction-ledger cursor | No | It is not a topic subscription and existing transaction APIs remain authoritative. |
| Schema or compacted ledger | No | It is a ledger, not a managed-ledger cursor. |

The API neither accepts nor returns a raw cursor name. A future proposal can add typed replication,
deduplication, or compaction diagnostics using stable logical identities.

## Single-topic retrieval

For a non-partitioned topic or explicit partition, the broker validates the names, `GET_STATS`
authorization, global routing, topic existence and kind, and physical ownership before resolving the
existing subscription and returning a best-effort snapshot. `subName` is included in the authorization
context.

Resolving an existing cold topic can load and recover it, but a missing topic or subscription is never
created. The nested `CursorStats` must have the same observable fields and semantics as the
corresponding entry in topic-level `internalStats`.

## Single-topic response

`SubscriptionCursorInternalStats` is added to
`org.apache.pulsar.common.policies.data`:

```java
public class SubscriptionCursorInternalStats {
    public String subscriptionName;
    public ManagedLedgerInternalStats.CursorStats cursor;
    public String persistentMarkDeletePosition;
    public boolean durable;
    public long lastActiveTimestamp;
    public int nonContiguousDeletedMessagesRangeSerializedSize;
    public CursorPersistenceStats persistence;

    public static class CursorPersistenceStats {
        public long persistLedgerSucceed;
        public long persistLedgerErrors;
        public long persistZookeeperSucceed;
        public long persistZookeeperErrors;
        public long writeCursorLedgerSize;
        public long writeCursorLedgerLogicalSize;
        public long readCursorLedgerSize;
    }
}
```

On every `200` response, `cursor` and `persistence` are non-null, and
`persistentMarkDeletePosition` remains present in JSON when its value is `null`.

| Field | Meaning |
|---|---|
| `subscriptionName` | Decoded logical subscription name supplied by the caller. |
| `cursor` | Existing `CursorStats` JSON shape and semantics, including positions, cursor ledger, deleted ranges, pending reads, state, activity, and properties. |
| `persistentMarkDeletePosition` | Last mark-delete position known to be persisted; nullable for a non-durable cursor or when none is available. |
| `durable` | Whether the cursor state is durable. |
| `lastActiveTimestamp` | Loaded cursor's activity time in epoch milliseconds. It is not a delivery timestamp and can reset when the cursor is reloaded. |
| `nonContiguousDeletedMessagesRangeSerializedSize` | Cached serialized size prepared for persistence. It can lag or reflect persistence-range truncation and is not an exact size of all current ranges. |
| `persistence` | Persistence success/error and cursor-ledger byte counters for the loaded cursor instance; they reset after unload, restart, or recreation. The `Zookeeper` field names are retained from the existing MXBean although they represent metadata-store persistence. |

Within `persistence`, `persistLedgerSucceed` / `persistLedgerErrors` count cursor-ledger persistence
operations, while `persistZookeeperSucceed` / `persistZookeeperErrors` count metadata-store persistence
operations. `writeCursorLedgerSize` uses BookKeeper write-quorum accounting;
`writeCursorLedgerLogicalSize` is the pre-quorum logical byte count; and `readCursorLedgerSize` counts
cursor-ledger bytes read.

The complete existing `individuallyDeletedMessages` string remains in `cursor` by default. This
preserves parity with topic-level internal statistics but can produce a large response.

The result is diagnostic, not transactionally consistent. In-memory mark-delete can be ahead of the
persisted position; fields and partitions can be sampled at different times; and no monotonicity is
guaranteed across requests. A client must not use this response as a cursor-mutation precondition.

## Partitioned-topic retrieval

The partitioned resource accepts only a partitioned base topic. It authorizes and validates the base,
captures partition metadata once, then queries the physical partition owners. The external caller is
authorized against the base; downstream requests use the broker identity and retain normal ownership
and redirect validation.

Fan-out must use bounded concurrency and a finite overall deadline. The concrete limit, scheduling
strategy, timeout source, and cancellation mechanism are implementation choices, not compatibility
guarantees. A partition that does not complete before the deadline is a timeout, and a late completion
cannot alter the finalized response.

`PartitionedSubscriptionCursorInternalStats` is added to
`org.apache.pulsar.common.policies.data`:

```java
public class PartitionedSubscriptionCursorInternalStats {
    public PartitionedTopicMetadata metadata;
    public boolean complete;
    public Map<String, SubscriptionCursorInternalStats> partitions;
    public Map<String, PartitionError> errors;

    public static class PartitionError {
        public int statusCode;
        public String errorCode;
        public String reason;
    }
}
```

Map keys are full physical-partition topic names; iteration order is unspecified. For every typed
`200` response:

- every partition in the captured metadata appears exactly once in `partitions` or `errors`;
- `partitions.size() + errors.size() == metadata.partitions`; and
- `complete` is true exactly when `errors` is empty.

The metadata can become stale after capture, but the response remains complete relative to that
snapshot. No cursor value or persistence counter is aggregated across partitions.

`PartitionError.statusCode` preserves the downstream status. A local timeout or transport failure
uses `503`; an unexpected local failure uses `500`. `errorCode` is stable and coarse:

| Condition | `errorCode` |
|---|---|
| Downstream `401` or `403` | `AUTHORIZATION_FAILED` |
| Downstream `404` | `NOT_FOUND` |
| Downstream `408` or `504`, internal-client timeout, or local deadline | `TIMEOUT` |
| Downstream `412` | `PRECONDITION_FAILED` |
| Downstream `429`, `502`, or `503`, or other transport failure | `UNAVAILABLE` |
| Any other status or unexpected local failure | `INTERNAL_ERROR` |

`reason` is short, human-readable, non-stable text. Clients may parse `errorCode`, but must not parse
`reason`.

At least one successful partition produces `200`, including a partial result. If none succeeds, all
`404` failures produce a top-level `404`; any other failure produces a top-level `503`. These
zero-success responses use the standard `ErrorData` body and do not contain per-partition maps.

Physical-partition ownership redirects are resolved during fan-out; a redirect or routing failure is
`UNAVAILABLE`. During a rolling upgrade, a downstream `404` cannot reliably distinguish an old broker
without the new route from a missing topic or subscription, so it remains the coarse `NOT_FOUND` error.

Implementation tests must cover resource and authorization boundaries, single-result field semantics,
partition completeness and error invariants, and consistent REST, Java Admin, and CLI behavior.

## Public-facing Changes

### Public API

The two REST paths are those defined in High Level Design. Both have no request body, use existing path
encoding, and accept the internal `authoritative` query parameter used by ownership routing.

Except for a normal `307` response with a `Location` header, non-`200` responses use the existing
`ErrorData` shape: `{"reason":"short human-readable reason"}`.

| Status | Single-topic resource | Partitioned resource |
|---:|---|---|
| `200` | The existing subscription snapshot. | At least one partition result; inspect `complete` and `errors`. |
| `307` | Normal topic-ownership redirect. | Global routing redirect; physical redirects are normally followed internally. |
| `401` | Missing authentication or denied `GET_STATS`. | Same. |
| `404` | Tenant, namespace, physical topic, or subscription missing. | Partition metadata missing, or every partition returned `404`. |
| `412` | Invalid name, a partitioned base topic, or a routing/ownership precondition failure. | Invalid name, a non-partitioned topic/explicit partition, or a global-routing precondition failure. |
| `500` | Unexpected snapshot failure. | An unexpected coordinator failure prevents a typed result. An unexpected per-partition failure is recorded as `PartitionError(500, INTERNAL_ERROR)`; zero successes follow the `503` rule. |
| `503` | Temporary metadata, routing, ownership, or broker failure. | Temporary pre-fan-out failure, or zero successes with at least one non-`404` failure. |

The following methods are added to `org.apache.pulsar.client.admin.Topics`:

| Method signature | Return type |
|---|---|
| `getSubscriptionCursorInternalStats(String topic, String subName) throws PulsarAdminException` | `SubscriptionCursorInternalStats` |
| `getSubscriptionCursorInternalStatsAsync(String topic, String subName)` | `CompletableFuture<SubscriptionCursorInternalStats>` |
| `getPartitionedSubscriptionCursorInternalStats(String topic, String subName) throws PulsarAdminException` | `PartitionedSubscriptionCursorInternalStats` |
| `getPartitionedSubscriptionCursorInternalStatsAsync(String topic, String subName)` | `CompletableFuture<PartitionedSubscriptionCursorInternalStats>` |

The names identify both the public subscription lookup and its internal cursor result. The prototype's
shorter `getCursorInternalStats` name is not adopted because it implies arbitrary cursor support.

All four are declared as `default` methods to preserve third-party `Topics` implementations. The sync
defaults throw an unsupported `PulsarAdminException`; async defaults return a failed future. All async
implementations report validation, lookup, and REST failures through the returned future rather than
throwing synchronously. There is no fallback to complete topic internal statistics. Their topic-kind
constraints match the REST resources.

### Binary protocol

No changes.

### Configuration

No changes.

### CLI

The existing commands gain `-s` / `--subscription`:

```text
pulsar-admin topics stats-internal --subscription <subscription> <physical-topic>
pulsar-admin topics partitioned-stats-internal --subscription <subscription> <partitioned-base-topic>
```

Without the option, behavior and output remain unchanged. For `stats-internal`,
`--subscription` and `--metadata` are mutually exclusive. The CLI rejects non-persistent topics and
does not extend the deprecated `persistent-topics` group.

A typed partial result is printed and exits with status `0`; automation requiring completeness must
inspect `complete`. Top-level `404` and `503` responses remain non-zero failures.

### Metrics

No changes. Returned persistence counters are existing cursor telemetry, not new metrics.

# Monitoring

This is an on-demand diagnostic feature. Operators can compare in-memory and persisted mark-delete
positions and persistence errors, inspect pending reads, and check `complete` before interpreting a
partitioned result. Existing Admin API latency and failure telemetry covers the endpoint itself.

# Security Considerations

Both resources use `TopicOperation.GET_STATS` and pass `subName` to the authorization context. The
default provider maps `GET_STATS` to lookup authorization, so a role with produce or consume
permission can be allowed. The current topic-operation validator returns `401` for both absent
authentication and denied authorization; this PIP preserves that behavior.

For partitioned requests, the caller is authorized against the base topic once. Fan-out uses the broker
identity, and each downstream request performs physical ownership and redirect validation. A downstream
topic or subscription identity is never treated as authority for another resource.

Most cursor fields are already available through topic-level internal statistics. The supplementary
fields expose operational state but no payload or mutation capability. Error reasons must omit stack
traces, credentials, internal headers, and message payloads. Tenant and namespace validation remains
unchanged, and only the requested subscription is returned.

# Backward & Forward Compatibility

Existing REST resources, Java methods, CLI behavior without `--subscription`, and JSON types are
unchanged. New resources and DTOs are additive, and `default` Java methods avoid adding abstract
methods to third-party `Topics` implementations.

## Upgrade

Old clients are unaffected. A new client calling an old broker normally receives `404` because the
route is absent. During a rolling upgrade, an upgraded partition coordinator can also receive `404`
from an old owner and cannot distinguish that from a missing resource. Results can therefore be partial,
`404`, or `503` until all relevant brokers are upgraded.

The implementation does not fall back to complete topic internal statistics, because that would restore
the avoided work and still could not distinguish the two `404` causes. No metadata migration, storage
rewrite, protocol negotiation, or configuration step is required.

## Downgrade / Rollback

Rollback removes the new resources and CLI capability. No data cleanup or conversion is needed; new
clients see the same unsupported-route behavior when they reach an old broker.

## Pulsar Geo-Replication Upgrade & Downgrade/Rollback Considerations

The response describes only local subscription state and neither contacts nor mutates a remote cluster.
Replicator cursors remain outside this API.

# Alternatives

| Alternative | Reason not selected |
|---|---|
| Filter the complete response on the client or add a filter to the existing endpoint | Client filtering saves no broker work; a server-side filter makes one endpoint return different semantic shapes and leaves topic-level sections ambiguous. |
| Return bare `CursorStats` | It cannot add persisted position, durability, activity, range-size, or persistence state without changing the existing topic-level cursor JSON. |
| Do not provide broker-side partition fan-out | Explicit-only or client-side fan-out is simpler, but duplicates behavior and cannot return one metadata snapshot with explicit partial results. Failing on any partition also discards useful diagnostic evidence. |
| Omit individual deleted ranges by default | Smaller, but less informative than the corresponding existing cursor entry. A later options object can add summary mode. |
| Expose a generic raw-cursor endpoint | It would freeze internal names while omitting the component-specific state needed to diagnose replication or deduplication. |
