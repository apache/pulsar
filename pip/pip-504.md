# PIP-504: Add an option to use subscription order for Failover on non-partitioned topics

- Mailing list discussion: pending
- Mailing list vote: pending

# Background

On a non-partitioned topic, Failover selects one active consumer by hashing the topic name across the highest-priority consumers. [PR #27665](https://github.com/apache/pulsar/pull/27665) extended this behavior from persistent to non-persistent topics.

The [5.0.x messaging guide](https://pulsar.apache.org/docs/5.0.x/concepts-messaging/#failover--non-partitioned-topics) describes subscription order for one non-partitioned topic and hashing for multiple topics. [Issue #24747](https://github.com/apache/pulsar/issues/24747) reports that the broker uses hashing even for a single topic.
The [5.0.x guide](https://pulsar.apache.org/docs/5.0.x/concepts-messaging/#failover--non-partitioned-topics) should describe the behavior shipped in that series. Starting with the release that adds this setting, document how it applies to both single-topic and multi-topic subscriptions.

# Motivation

We used a Failover subscription on one topic to elect a leader among workers and collect worker information. When we added workers, hashing sometimes replaced a healthy leader. We wanted new workers to join as standbys and wait their turn.

# High Level Design

[PR #27730](https://github.com/apache/pulsar/pull/27730) proposes a broker setting for all non-partitioned Failover subscriptions, both persistent and non-persistent.

```properties
nonPartitionedTopicFailoverUseSubscriptionOrder=false
```

- `false` (default) uses consistent hashing among the highest-priority consumers.
- `true` selects the earliest consumer still registered for that topic and subscription, regardless of priority. A reconnect joins the end of the list, even with the same consumer name and ID.

For example, A, Z and B subscribe in that order. When A disconnects, Z takes over. If A returns with a higher priority, it queues behind B. When Z disconnects, B takes over.

[PIP-392](pip-392.md) introduced `activeConsumerFailoverConsistentHashing` to control assignment on partitioned topics, including partition 0. The proposed name starts with `nonPartitionedTopic` to make its scope clear. An alternative, `activeConsumerFailoverUseSubscriptionOrderForNonPartitionedTopics`, would group the two settings under the same prefix.

# Detailed Design

With subscription order enabled, each dispatcher selects the first consumer in its list.

- **Multi-topic and regex subscriptions.** Each topic elects its own active consumer. A worker that subscribes first to all 100 topics can receive traffic for all 100.
- **Seek or cursor reset.** On a persistent topic, a client seek or an admin cursor reset disconnects the active consumer. The broker defers the election during that disconnect. If A was active and Z was waiting, the broker selects Z when A resubscribes. Z receives any replayed messages, so a seek can move leadership even when both workers are healthy.
- **Silent connection loss.** If A reconnects before the broker detects the loss of its old connection, the old A remains active. If Z was already waiting, Z takes over when the broker removes the old A.
- **Topic unload or broker restart.** Consumers establish a new order as they resubscribe. If a client moves to another cluster, the destination broker uses its local setting.

Applications can observe handoffs through Failover consumer events. On persistent topics, `activeConsumerName` in topic stats shows the name, which two connections can share.

# Backward & Forward Compatibility

Existing clients can use either mode. Set the option to `true` and restart the brokers to enable subscription order, or set it to `false` and restart to restore hashing. During a rolling restart, each topic follows its owning broker's setting.
Downgrading to a version that predates this setting restores that version's selection rules. Subscription order is held in memory, so rollback needs no metadata migration.

# Alternatives

A [topic or namespace policy](https://github.com/apache/pulsar/pull/27730#issuecomment-7190244966) would let operators use subscription order for leader election and hashing for other workloads on the same broker. We propose a broker setting for deployments that want one rule across topics. It avoids adding policy storage and an admin API.

Consumer priority suits a deployment with a preferred leader. When that worker returns, it can preempt a healthy leader, which is precisely the handoff we want to avoid.
