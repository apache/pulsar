# PIP-502: Improve replication observability in the Admin API

# Background knowledge

Pulsar geo-replication asynchronously copies messages from a topic in the source cluster to the same topic in each target cluster selected by the replication policy. Applications in those clusters can consume the messages locally. Deploying the clusters in different regions supports cross-region backup and disaster recovery. If the source region becomes unavailable, applications can switch to a target cluster and consume the messages already replicated there.

# Motivation

Geo-replication spans two clusters. A slowdown or failure at any of the following stages can show up as a growing backlog at the source.

- **Network connectivity.** An unreachable target prevents the replicator from connecting. An intermittent link can interrupt sends or acknowledgements and lead to retries.
- **Authentication and authorization.** Expired credentials can prevent the source broker from authenticating. Even with valid credentials, its replication identity may lack permission to query topic metadata or publish at the target.
- **Topic metadata.** If the source and target disagree on the partition count, the replicator can fail to start for the affected topic.
- **Source read rate.** Slow storage reads can leave the replicator waiting for a batch. If reads consistently lag behind incoming writes, the backlog grows even when the target has spare capacity.
- **Schema compatibility.** A target can reject the schema of the next message to replicate. Retrying schema registration can hold up later messages for the same target.
- **Message deduplication.** After an interrupted send, the target may need to determine whether it has already persisted the retried entry. An inconclusive deduplication check can cause another retry at the same position.
- **Send rate to the target.** Slow writes or acknowledgements at the target can fill the source producer's queue and pause further reads. The delay then looks like a stalled source cursor.
- **Rate limiting.** A replicator that exhausts either its message or byte quota waits for permits before reading more entries. A limit below the incoming rate can sustain a backlog on an otherwise healthy link.

Backlog and send rate alone give operators little indication of which stage last made progress. In difficult incidents, operators often have to capture and download a heap dump from the affected broker, then inspect pending reads, queued sends and cursor recovery state to identify the root cause. This takes time while replication continues to fall behind.

# Goals

Expose more of the runtime state of geo-replication through the Admin API so operators can more easily identify where replication slows down or stalls.

# High Level Design

- Extend topic internal stats with a `replicators` map keyed by target cluster (`GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/internalStats`).
- Extend `topic-stats.replication` (`GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/stats`)

# Detailed Design

## Public-facing Changes

### Public API

All fields introduced below apply to non-partitioned persistent topics and individual persistent partitions. For non-persistent topics, the broker omits these properties from both topic stats and topic internal stats.

#### Extension to topic stats

`GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/stats` gains six fields in each `replication[cluster]` object. Callers use the existing path parameters, authorization and stats options. In `partitioned-stats`, the aggregate `replication[cluster]` omits all six fields. With `perPartition=true`, each partition reports them under `partitions[partitionTopic].replication[cluster]`. This example shows the additions for one target.

```json
{
  "replication": {
    "cluster-b": {
      "replicatorState": "STARTED",
      "producerState": "READY",
      "replicatorHealth": {
        "healthy": true,
        "message": null
      },
      "lastCursorReadStartedAt": 1793780130000,
      "lastSendStartedAt": 1793780130010,
      "lastReplicationSucceededAt": 1793780129045
    }
  }
}
```

All timestamps introduced by this proposal are signed 64-bit integers (`long`) in milliseconds since the Unix epoch. Each of the six new topic stats fields is nullable. An activity timestamp is `null` if the current replicator has not observed the event or the value is unavailable.

| New response field | JSON type | Meaning and use |
| --- | --- | --- |
| `replicatorState` | string or null | Current outbound replicator lifecycle state. Values are `DISCONNECTED`, `STARTING`, `STARTED`, `DISCONNECTING`, `TERMINATING` and `TERMINATED`. An existing replicator can be `DISCONNECTED` before its first start. An unavailable instance yields `null`. |
| `producerState` | string or null | State of this replicator's producer. Values are `UNINITIALIZED`, `CONNECTING`, `READY`, `CLOSING`, `CLOSED`, `TERMINATED`, `FAILED`, `REGISTERING_SCHEMA` and `PRODUCER_FENCED`. An absent producer yields `null`. If the target's schema policy rejects a message, the producer retries registration with increasing backoff up to a maximum. While the policy continues to reject that schema, most samples show `REGISTERING_SCHEMA`. At the start of a retry, the producer briefly passes through `READY` before re-entering `REGISTERING_SCHEMA`. Even if a sample catches `READY`, check `sendingMessageSchemaCompatible` for the current queue head's schema state. Compare `lastReplicationSucceededAt` across samples to see whether send callbacks have resumed requesting cursor entry deletions. This timestamp can also advance for another message or a skipped entry. |
| `replicatorHealth` | object or null | The source broker's assessment of outbound replication to this target. `healthy` is a boolean. When false, `message` gives a concrete troubleshooting step. When true, `message` is `null`. The entire field is `null` when the broker cannot yet assess the replicator. |
| `lastCursorReadStartedAt` | integer (int64) or null | Source-broker time when the latest cursor read began. Use it with the backlog and the read position of an unfinished batch to investigate a long read. If `replicationBacklog` is zero and `lastCursorReadStartedAt` has remained unchanged for a long time, the topic currently has no data pending replication to this target. This can happen when the source topic has received no new messages for a long time. |
| `lastSendStartedAt` | integer (int64) or null | Source-broker time when a message was last submitted to this target's producer. It shows whether the reader continues to supply sends during a backlog. |
| `lastReplicationSucceededAt` | integer (int64) or null | Source-broker time when the producer's send callback most recently called `cursor.asyncDelete()` for this target. The callback does this after a successful send or when it skips an entry on `InvalidMessageException`. Only deletes initiated by this callback update the timestamp. |

The broker evaluates health from local observations for the current replicator, independently of how often stats are queried. An unavailable or retiring instance returns `null`. For an active replication target, the following rules apply.

- A producer start failure makes health false while that startup attempt is being retried. For example, `replicatorHealth` can be `{"healthy": false, "message": "Producer creation failed. Check lastProducerStartFailure in stats-internal."}`. A successful start ends this condition even though the failure record remains available.
- Otherwise, a replicator with no backlog or pending sends is healthy, including one disconnected after being idle. With a backlog, health is true while the broker observes a successful send acknowledgement or forward movement of the replication cursor within the past minute. Cursor progress includes skipping filtered or expired entries.
- If work has been pending continuously for at least one minute without either kind of progress, health is false. A read waiting for dispatch permits points to the effective `replicatorDispatchRate`. Schema registration points to `sendingMessageSchemaCompatible`. An outstanding read or send points to the relevant task, failure record or target acknowledgement. If the stage is unclear, the message directs the operator to inspect `inFlightTasks` in `stats-internal`.
- The observation window starts when work becomes pending, including after an idle period or a restart. Until the broker observes progress, a producer startup retry, or a full minute of pending work, health is `null`.

#### Extension to topic internal stats

`GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/internalStats` adds a top-level `replicators` map to `PersistentTopicInternalStats` for a non-partitioned persistent topic or an individual partition. Each key is a target cluster name. For a partitioned topic, `GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/partitioned-internalStats` omits `replicators` at the top level. Each returned partition exposes its own map at `partitions[partitionTopic].replicators`. The existing Java Admin methods, authorization and topic loading behavior apply. The example shows the new field for one target.

```json
{
  "replicators": {
    "cluster-b": {
      "producerQueueSize": 5,
      "producerQueueMaxSize": 1000,
      "sendingMessageSchemaCompatible": true,
      "lastProducerStartFailure": {
        "timestamp": 1793780000000,
        "message": "AuthorizationException"
      },
      "lastReadFailure": {
        "timestamp": 1793780040000,
        "message": "Too many pending read requests"
      },
      "lastPublishFailure": {
        "timestamp": 1793780120000,
        "message": "TopicTerminatedException"
      },
      "inFlightTasks": [
        {
          "readPos": "100:201",
          "readingEntries": 10,
          "entries": 10,
          "completedEntries": 5,
          "skipReadResultDueToCursorRewind": false,
          "readException": null
        }
      ]
    }
  }
}
```

Each target has all seven response fields. A policy target with no observable replicator has seven null values. The map is empty (`{}`) when the topic has no replication targets.

| Response field | JSON type | Meaning and use |
| --- | --- | --- |
| `producerQueueSize` | integer or null | Number of pending messages in this producer's send queue. Zero means an observed empty queue. An absent producer yields `null`. Repeated samples show whether the queue stays close to capacity. |
| `producerQueueMaxSize` | integer or null | Capacity actually assigned to this replicator's producer queue. Changing the broker setting applies to newly created replicators, so the observed capacity can differ across instances. An absent replicator yields `null`. |
| `sendingMessageSchemaCompatible` | boolean or null | Derived from the current `schemaState` of the message at the head of the replication producer's send queue. `Ready` maps to `true`, `Broken` to `false`, and `None` to `null`. An absent producer or head message also yields `null`. |
| `lastProducerStartFailure` | object or null | Most recent failure while preparing the target topic or creating the replication producer. The record is available even if no producer was created. Its `message` contains only the exception class name. |
| `lastReadFailure` | object or null | Most recent failure when submitting or completing a replication cursor read for this target. Its `message` contains the exception message verbatim, or `null` if the exception has no message. The record remains available after the failed batch leaves `inFlightTasks`. |
| `lastPublishFailure` | object or null | Most recent failure when submitting or completing a replicated send to this target. Its `message` contains only the exception class name. For example, sending to a terminated target topic can raise `TopicTerminatedException` and trigger a cursor rewind. On `InvalidMessageException`, the replicator skips the entry and preserves the previous failure record. The send callback updates `lastReplicationSucceededAt` when it calls `cursor.asyncDelete()` for that entry. |
| `inFlightTasks` | array or null | Unfinished read batches in queue order. A replicator with no unfinished reads returns `[]`, including when it is `DISCONNECTED` after an idle period. The field is `null` if no replicator instance exists for the target cluster. Comparing task lists helps identify a batch that has stopped progressing. |

A new read-only method on `GeoReplicationProducerImpl` will read `schemaState` from the message at the head of `pendingMessages`. The producer also marks a replicated message that needs no schema registration as `Ready`, so it yields `true`. Once the queue advances, the field describes the new head. Reading this field makes no cross-cluster request and requires no admin permission on the target.

Each failure record includes the source broker's `timestamp` (int64, Unix epoch milliseconds). Callers authorized to read topic internal stats can see the full text of a read exception. For producer creation and publish failures, use the timestamp and exception class name to find the details in the source broker logs. Each outbound replicator keeps the latest record of each kind in memory until another failure of the same kind replaces it. The records survive retries, successful operations, cursor rewinds and producer reconnects within that instance. Each field is `null` until the instance observes its first failure of that kind.

Each task has the following six fields.

| Task field | JSON type | Meaning and use |
| --- | --- | --- |
| `readPos` | string or null | Starting position of this read, formatted as `ledgerId:entryId`, or `null` if unavailable. It helps identify where reads stall or repeat. |
| `readingEntries` | integer | Number of entries requested in the batch. It shows the amount of read capacity reserved while the result is outstanding. |
| `entries` | integer or null | Number of entries in the read result. `null` means the result is pending. Zero means the task has an empty result, including a result cleared during recovery. |
| `completedEntries` | integer | Entries whose local processing has finished. This includes successful sends, skipped entries and failure cleanup. |
| `skipReadResultDueToCursorRewind` | boolean | Whether recovery or shutdown has marked the read result for discard. This explains why a batch can be read again from an earlier position. |
| `readException` | string or null | Verbatim exception message for this batch's read failure. The value is `null` if the batch has no recorded read failure or the exception has no message. |

# Monitoring

Compare successive samples for the same topic or partition and target cluster.

1. **Backlog after enabling replication.** If `replicationBacklog` is large, use `pulsar-admin topics info-internal <topic>` on the source to look up the replication cursor’s creation time. With the default cursor prefix, the field is `cursors["pulsar.repl.<target-cluster>"].creationDate`. Check which `replicationStartAt` value was in effect when that cursor was created. With the default `latest`, the backlog accumulated after cursor creation. With `earliest`, it can also include retained messages published before replication was enabled. A shrinking backlog shows that the replicator is catching up. Use `lastReplicationSucceededAt` to see when the producer's send callback last requested a cursor delete.
2. **Replication producer startup.** If `replicatorHealth.healthy` is false, follow its `message`. For a producer startup retry, inspect `replicators[cluster].lastProducerStartFailure` in `stats-internal` for the timestamp and exception class name, then check the source broker logs for the cause.
3. **Idle replicator.** If replication was working, `replicationBacklog` has stayed at zero, and `replicatorState` changes to `DISCONNECTED`, the broker has likely closed the idle replication producer to conserve resources. The producer is then no longer registered on the target topic.
4. **Stalled schema registration.** If `producerState` stays in `REGISTERING_SCHEMA` with a backlog, inspect `replicators[cluster].sendingMessageSchemaCompatible` in topic internal stats. The field describes only the queue head, even when the producer is registering a schema for a later message.
5. **Stalled cursor read.** If a backlog persists, `lastCursorReadStartedAt` stays unchanged, and the same `readPos` in `inFlightTasks` continues to show `null` for `entries`, that read is still waiting for a result. Check `lastReadFailure` for the latest read error even after a failed batch leaves the queue. With zero backlog, the cursor can legitimately wait for new messages.
6. **Stalled sends.** While a backlog persists, use `lastSendStartedAt` to see whether the replicator is still submitting new sends. Replication sends have no acknowledgement timeout. If the producer queue stays nonempty and replication delay grows, check for outstanding sends even if `lastPublishFailure` has no new entry. A `lastReplicationSucceededAt` later than the failure means a subsequent send callback requested a cursor delete after a successful send or an `InvalidMessageException`.
7. **Send queue near capacity.** If `producerQueueSize` stays close to `producerQueueMaxSize` across samples, the source is usually submitting messages faster than the producer can send them to the target and receive acknowledgements.
8. **Replication blocked by an incompatible schema.** If `sendingMessageSchemaCompatible` stays `false` while the queue is stalled, the head message's schema state is `Broken`. Retrying registration can hold up later sends. A value of `true` means the head message is ready to send as far as its schema is concerned. It may still be awaiting acknowledgement.

# Backward & Forward Compatibility

- **Java implementations of `ReplicatorStats`.** Each new getter is a Java `default` method that returns `null`. Implementations can override individual getters when they have a value. `NonPersistentReplicatorStats` inherits the same defaults. A source compatibility test will recompile an existing implementation unchanged against the updated interface. A binary compatibility test will keep the implementation compiled against the old interface and verify that calling each new getter through the updated interface returns `null`.
- **Older admin client with a newer broker.** The broker includes the new properties wherever they apply, regardless of the client version. The older Java Admin client ignores unknown properties during deserialization, so `pulsar-admin` prints the fields it recognizes and completes without error.
- **Newer admin client with an older broker.** The broker omits the new properties. The Java Admin client leaves them `null`, including the `replicators` map. By default, `pulsar-admin` omits null properties from its output. This also applies to responses served by older brokers during a rolling upgrade or after a rollback.
