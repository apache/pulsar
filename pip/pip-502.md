# PIP-502: Diagnose geo-replication backlogs with the Admin API

# Background knowledge

Pulsar geo-replication asynchronously copies messages from a topic in the source cluster to the same topic in each target cluster selected by the replication policy. Applications in those clusters can consume the messages locally. Deploying the clusters in different regions supports cross-region backup and disaster recovery. If the source region becomes unavailable, applications can switch to a target cluster and consume the messages already replicated there.

# Motivation

Geo-replication spans two clusters. A slowdown or failure at any of the following stages can show up as a growing backlog at the source.

- **Network connectivity.** An unreachable target prevents the replicator from connecting. An intermittent link can interrupt sends or acknowledgements and lead to retries.
- **Authentication and authorization.** Expired credentials can prevent the source broker from authenticating. Even with valid credentials, its replication identity may lack permission to query topic metadata or publish at the target.
- **Topic metadata.** If the source and target disagree on the partition count, the replicator can fail to start for the affected topic.
- **Source read rate.** Slow storage reads can leave the replicator waiting for a batch. If reads consistently lag behind incoming writes, the backlog grows even when the target has spare capacity.
- **Schema compatibility.** A target can reject the schema of the next message to replicate. Retrying schema registration can hold up later messages for the same target.
- **Message deduplication.** After an interrupted send, the target may need to determine whether it has already persisted the retried entry. An inconclusive deduplication check can cause another retry at the same position.
- **Send rate to the target.** Slow writes or acknowledgements at the target can fill the source producer's queue and pause further reads. The delay then looks like a stalled source cursor.
- **Rate limiting.** A replicator that exhausts either its message or byte quota waits for permits before reading more entries. A limit below the incoming rate can sustain a backlog on an otherwise healthy link.

Backlog and send rate alone give operators little indication of which stage last made progress. In difficult incidents, operators often have to capture and download a heap dump from the affected broker, then inspect pending reads, queued sends and cursor recovery state to identify the root cause. This takes time while replication continues to fall behind.

# Goals

Expose more of the runtime state of geo-replication through the Admin API so operators can more easily identify where replication slows down or stalls.

# High Level Design

- Add `replicator-stats` (`GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/replicatorInternalStats`)
- Extend `topic-stats.replication` (`GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/stats`)

# Detailed Design

## Public-facing Changes

### Public API

#### Extension to topic stats

`GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/stats` gains six fields in each `replication[cluster]` object. Callers use the existing path parameters, authorization and stats options. This example shows the additions for one target.

```json
{
  "replication": {
    "cluster-b": {
      "createAt": "2026-11-04T08:00:00.000Z",
      "replicatorState": "STARTED",
      "producerState": "READY",
      "lastCursorReadStartedAt": "2026-11-04T08:15:30.000Z",
      "lastSendStartedAt": "2026-11-04T08:15:30.010Z",
      "lastReplicationSucceededAt": "2026-11-04T08:15:30.045Z"
    }
  }
}
```

Each new field is nullable. Timestamps are UTC RFC 3339 strings. An upgraded broker returns `null` when a value is unavailable. For activity timestamps this includes the period before the first corresponding event on the current replicator.

| New response field | JSON type | Meaning and use |
| --- | --- | --- |
| `createAt` | string or null | Creation time of this target's replication cursor metadata record. A recent value helps explain a backlog after replication was enabled. |
| `replicatorState` | string or null | Current outbound replicator lifecycle state. Values are `DISCONNECTED`, `STARTING`, `STARTED`, `DISCONNECTING`, `TERMINATING` and `TERMINATED`. An existing replicator can be `DISCONNECTED` before its first start. An unavailable instance yields `null`. |
| `producerState` | string or null | State of this replicator's producer. Values are `UNINITIALIZED`, `CONNECTING`, `READY`, `CLOSING`, `CLOSED`, `TERMINATED`, `FAILED`, `REGISTERING_SCHEMA` and `PRODUCER_FENCED`. An absent producer yields `null`. |
| `lastCursorReadStartedAt` | string or null | Source-broker time when the latest cursor read began. Use it with the backlog and the read position of an unfinished batch to investigate a long read. If `replicationBacklog` is zero and `lastCursorReadStartedAt` has remained unchanged for a long time, the topic currently has no data pending replication to this target. This can happen when the source topic has received no new messages for a long time. |
| `lastSendStartedAt` | string or null | Source-broker time when a message was last submitted to this target's producer. It shows whether the reader continues to supply sends during a backlog. |
| `lastReplicationSucceededAt` | string or null | Source-broker time when the replicator last observed a successful send acknowledgement from this target. If sends continue and this time stays fixed, inspect pending sends and recovery. |

#### Replicator diagnostics

`GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/replicatorInternalStats` supports only a non-partitioned topic or an individual partition of a partitioned topic.

```json
[
  {
    "cluster-b": {
      "producerQueueSize": 5,
      "producerQueueMaxSize": 1000,
      "sendingMessageSchemaCompatible": true,
      "reasonOfWaitForCursorRewinding": null,
      "inFlightTasks": [
        {
          "readPos": "100:201",
          "readingEntries": 10,
          "entries": 10,
          "completedEntries": 5,
          "skipReadResultDueToCursorRewind": false,
          "readException": null
        }
      ]
    }
  }
]
```

Each target has all five response fields. A policy target with no observable replicator has five null values. An unloaded topic returns HTTP 503 so that a diagnostic call cannot start replication by loading it.

| Response field | JSON type | Meaning and use |
| --- | --- | --- |
| `producerQueueSize` | integer or null | Number of pending messages in this producer's send queue. Zero means an observed empty queue. An absent producer yields `null`. Repeated samples show whether the queue stays close to capacity. |
| `producerQueueMaxSize` | integer or null | Capacity actually assigned to this replicator's producer queue. Changing the broker setting applies to newly created replicators, so the observed capacity can differ across instances. An absent replicator yields `null`. |
| `sendingMessageSchemaCompatible` | boolean or null | Whether the schema of the message currently being sent is compatible. `true` means compatible and `false` means incompatible. `null` covers an absent send, unavailable schema or inconclusive remote check. |
| `reasonOfWaitForCursorRewinding` | string or null | Currently recorded reason for cursor recovery or termination. Values are `FAILED_PUBLISHING`, `FETCHING_SCHEMA`, `DISCONNECTING` and `TERMINATING`. `FETCHING_SCHEMA` refers to obtaining the source schema. `null` means no such event occurred in the current snapshot. |
| `inFlightTasks` | array or null | Unfinished read batches in queue order. `[]` means there are no unfinished tasks. `null` means the replicator has not started. Comparing task lists helps identify a batch that has stopped progressing. |

Each task has the following six fields.

| Task field | JSON type | Meaning and use |
| --- | --- | --- |
| `readPos` | string or null | Starting position of this read, formatted as `ledgerId:entryId`, or `null` if unavailable. It helps identify where reads stall or repeat. |
| `readingEntries` | integer | Number of entries requested in the batch. It shows the amount of read capacity reserved while the result is outstanding. |
| `entries` | integer or null | Number of entries in the read result. `null` means the result is pending. Zero means the task has an empty result, including a result cleared during recovery. |
| `completedEntries` | integer | Entries whose local processing has finished. This includes successful sends, skipped entries and failure cleanup. |
| `skipReadResultDueToCursorRewind` | boolean | Whether recovery or shutdown has marked the read result for discard. This explains why a batch can be read again from an earlier position. |
| `readException` | string or null | Sanitized, length-limited message of a recorded read error, or `null` if no read error occurred. |

### CLI

```bash
pulsar-admin topics replicator-stats persistent://example-tenant/example-ns/orders-partition-0
pulsar-admin topics stats persistent://example-tenant/example-ns/orders-partition-0
```

# Monitoring

Compare successive samples for the same topic or partition and target cluster.

1. **Backlog after enabling replication.** A large `replicationBacklog` and a recent `createAt` usually mean that replication to this target has just started and is copying historical messages. An advancing `lastReplicationSucceededAt` confirms that replication is making progress.
2. **Replication producer startup.** If a backlog persists and `replicatorState` never reaches `STARTED`, check whether the replicator can create a producer on the target topic. Repeated transitions between `STARTING` and `DISCONNECTED` indicate retries.
3. **Idle replicator.** If replication was working, `replicationBacklog` has stayed at zero, and `replicatorState` changes to `DISCONNECTED`, the broker has likely closed the idle replication producer to conserve resources. The producer is then no longer registered on the target topic.
4. **Stalled schema registration.** If `producerState` stays in `REGISTERING_SCHEMA`, the producer may be retrying registration of a schema that is incompatible at the target. Call `replicatorInternalStats` to check compatibility for the current message.
5. **Stalled cursor read.** If a backlog persists, `lastCursorReadStartedAt` stays unchanged, and the same `readPos` in `inFlightTasks` continues to show `null` for `entries`, that read is still waiting for a result. With zero backlog, the cursor can legitimately wait for new messages.
6. **Stalled sends.** While a backlog persists, use `lastSendStartedAt` to see whether the replicator is still submitting new sends. If the producer queue stays nonempty and `lastReplicationSucceededAt` stops advancing, check whether sends or acknowledgements from the target have stalled.
7. **Send queue near capacity.** If `producerQueueSize` stays close to `producerQueueMaxSize` across samples, the source is usually submitting messages faster than the producer can send them to the target and receive acknowledgements.
8. **Replication blocked by an incompatible schema.** If replication stalls and `sendingMessageSchemaCompatible` is `false`, the target considers the current message's schema incompatible, which can hold up subsequent messages. A value of `true` means the schema is compatible. A value of `null` means the check yielded no verdict.
