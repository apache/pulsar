# PIP-502: Improve replication observability in the Admin API

# Background knowledge

Pulsar geo-replication asynchronously copies messages from a topic in the source cluster to the same topic in each target cluster selected by the replication policy. Applications in those clusters can consume the messages locally. Deploying the clusters in different regions supports cross-region backup and disaster recovery. If the source region becomes unavailable, applications can switch to a target cluster and consume the messages already replicated there.

# Motivation

Geo-replication spans two clusters. A slowdown or failure at any of the following stages can show up as a growing backlog at the source.

- **Network connectivity.** An unreachable target prevents the replicator from connecting. An intermittent link can interrupt sends or acknowledgements and lead to retries.
- **Authentication and authorization.** Expired credentials can prevent the source broker from authenticating. Even with valid credentials, its replication identity may lack permission to query topic metadata or publish at the target.
- **Topic metadata.** If the source and target disagree on the partition count, the replicator can fail to start for the affected topic.
- **Source read rate.** Slow storage reads can leave the replicator waiting for a batch. If reads consistently lag behind incoming writes, the backlog grows even when the target has spare capacity.
- **Schema compatibility.** A target can reject the schema of the next message to replicate. Retrying schema registration can hold up later messages for the same target.
- **Message deduplication.** After an interrupted send, the target may need to determine whether it has already persisted the retried entry. An inconclusive deduplication check can cause another retry at the same position.
- **Send rate to the target.** Slow writes or acknowledgements at the target can fill the source producer's queue and pause further reads. The delay then looks like a stalled source cursor.
- **Rate limiting.** A replicator that exhausts either its message or byte quota waits for permits before reading more entries. A limit below the incoming rate can sustain a backlog on an otherwise healthy link.

Backlog and send rate alone give operators little indication of which stage last made progress. In difficult incidents, operators often have to capture and download a heap dump from the affected broker, then inspect pending reads, queued sends and cursor recovery state to identify the root cause. This takes time while replication continues to fall behind.

# Goals

## In Scope

Expose more of the runtime state of geo-replication through the Admin API so operators can more easily identify where replication slows down or stalls.

# High Level Design

Operators first query topic stats on the source cluster to find the affected target and the stage that needs attention. Topic internal stats then show the latest failed read, unfinished work, and any target error that caused the producer to retry. A failed read and an inconclusive deduplication check both carry a source ledger position when available, so operators can follow the same batch or entry across samples and broker logs.

# Detailed Design

## Public-facing Changes

### Public API

The existing stats GET requests take no request body. A successful request returns HTTP 200 with the additional JSON fields below, including when replication is unhealthy. None of these fields requires a new query option.

Under `/admin/v2/persistent/{tenant}/{namespace}/{topic}/`, `stats` and `partitioned-stats` accept the existing boolean options `getPreciseBacklog`, `subscriptionBacklogSize`, `getEarliestTimeInBacklog`, `excludePublishers` and `excludeConsumers`. Use `perPartition` on `partitioned-stats` to request individual partitions. `internalStats` accepts `metadata` to include ledger metadata. All four operations, including `partitioned-internalStats`, keep their existing `authoritative` option for broker redirects.

HTTP 307 redirects the caller to the owner. Authentication and authorization failures use 401 or 403, a missing topic or namespace uses 404, and an invalid topic name can return 412. Broker errors use 500, and failure to validate global cluster configuration can return 503. Existing error responses carry their usual details.

All fields introduced below apply to non-partitioned persistent topics and individual persistent partitions. For non-persistent topics, the broker omits these properties from both topic stats and topic internal stats.

The broker samples replication state on a best-effort basis. Fields in one response can reflect different instants. For example, a send can be acknowledged between sampling the producer queue and sampling `inFlightTasks`. The broker reads values without locking wherever safe. If a mutable queue requires a lock, the broker holds only that queue's lock while copying the values it needs, then releases it before sampling another queue or serializing the response.

#### Extension to topic stats

`GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/stats` gains six fields in each `replication[cluster]` object. Callers use the existing path parameters, authorization and stats options. In `partitioned-stats`, the aggregate `replication[cluster]` omits all six fields. With `perPartition=true`, each partition reports them under `partitions[partitionTopic].replication[cluster]`. This example shows the additions for one target.

```json
{
  "replication": {
    "cluster-b": {
      "replicatorState": "STARTED",
      "producerState": "READY",
      "replicatorHealth": {
        "healthy": true,
        "message": null
      },
      "lastCursorReadStartedAt": 1793780130000,
      "lastSendStartedAt": 1793780130010,
      "lastReplicationSucceededAt": 1793780129045
    }
  }
}
```

All timestamps introduced by this proposal are signed 64-bit integers (`long`) in milliseconds since the Unix epoch. For each of the six new topic stats fields, an omitted property and an explicit `null` both mean the value is unavailable. Per-partition results may use either representation during a rolling upgrade. An activity timestamp is unavailable until the current replicator observes the event.

| New response field | JSON type | Meaning and use |
| --- | --- | --- |
| `replicatorState` | string or null | Current outbound replicator lifecycle state. Values are `DISCONNECTED`, `STARTING`, `STARTED`, `DISCONNECTING`, `TERMINATING` and `TERMINATED`. An existing replicator can be `DISCONNECTED` before its first start. An unavailable instance yields `null`. |
| `producerState` | string or null | State of this replicator's producer. Values are `UNINITIALIZED`, `CONNECTING`, `READY`, `CLOSING`, `CLOSED`, `TERMINATED`, `FAILED`, `REGISTERING_SCHEMA` and `PRODUCER_FENCED`. An absent producer yields `null`. If the target's schema policy rejects a message, the producer retries registration with increasing backoff up to a maximum. While the policy continues to reject that schema, most samples show `REGISTERING_SCHEMA`. At the start of a retry, the producer briefly passes through `READY` before re-entering `REGISTERING_SCHEMA`. Even if a sample catches `READY`, check `sendingMessageSchemaCompatible` for the current queue head's schema state. Compare `lastReplicationSucceededAt` across samples to see whether send callbacks have resumed requesting cursor entry deletions. This timestamp can also advance for another message or a skipped entry. |
| `replicatorHealth` | object or null | The source broker's assessment of outbound replication to this target. `healthy` is a boolean. When false, `message` gives a concrete troubleshooting step. When true, `message` is `null`. The entire field is `null` when the broker cannot yet assess the replicator. |
| `lastCursorReadStartedAt` | integer (int64) or null | Source-broker time when the cursor last started reading available entries. The field is `null` while the cursor has no messages to read, including when a read is waiting for new entries. If entries arrive while a read is waiting, the timestamp is set when the cursor starts reading those entries. |
| `lastSendStartedAt` | integer (int64) or null | Source-broker time recorded immediately before calling `sendAsync()` on this target's producer. The send callback can run before the call returns. This timestamp shows whether the reader continues to submit sends during a backlog. |
| `lastReplicationSucceededAt` | integer (int64) or null | Source-broker time when the producer's send callback most recently called `cursor.asyncDelete()` for this target. The callback does this after a successful send or when it skips an entry on `InvalidMessageException`. Only deletes initiated by this callback update the timestamp. |

The broker records a start time once for each read of available entries and each send attempt. Completion callbacks report the outcome without updating either start timestamp. For example, a failed read callback updates `lastReadFailure`, and a send callback reporting `TopicTerminatedException` updates `lastPublishFailure` in topic internal stats.

The broker evaluates health from local observations for the current replicator, independently of how often stats are queried. An unavailable or retiring instance returns `null`. For an active replication target, the following rules apply.

- A producer start failure makes health false while that startup attempt is being retried. For example, if the target refuses the metadata request, the broker returns `{"healthy": false, "message": "Topic preparation was denied. Verify the replication credentials and topic metadata permissions. See lastProducerStartFailure in stats-internal and the source broker log at its timestamp."}`. If the target topic is missing and automatic creation is disabled, the message identifies the topic type to create and names the source setting `createTopicToRemoteClusterForReplication`. If the partition counts differ, the message includes both values (for example, `source=2, target=1`). A denied producer creation points to the replication identity’s publish permission on the target. A successful start ends this condition even though the failure record remains available.
- Otherwise, a replicator with no backlog or pending sends is healthy, including one disconnected after being idle. With a backlog, health is true if the broker observed a successful send acknowledgement or an advance in the replication cursor's mark-delete position within the past minute. Skipping filtered or expired entries counts as cursor progress only when it advances that position. For example, if the mark-delete position is at entry 9 and entry 10 is still outstanding, deleting entry 11 leaves the position at 9.
- If work has been pending continuously for at least one minute without either kind of progress, health is false. The message identifies the following conditions from the source broker's observations.
  - A terminated replication producer reports that the target topic cannot accept writes and points to `lastPublishFailure`. Cursor rewinds while retrying that publish do not change the diagnosis.
  - When the target has rejected the queue head's schema (`sendingMessageSchemaCompatible=false`), the message suggests comparing the two topic schemas and checking the target compatibility policy. While the producer is in `REGISTERING_SCHEMA` without a confirmed rejection for the queue head, the message says registration is pending and points to the target broker logs.
  - For sends waiting for target acknowledgements, the message gives the most recent observed retry reason and timestamp when available. If the target explicitly reports inconclusive deduplication for the current queue head, the message identifies that source entry and points to outstanding target writes. Older targets can report only `PersistenceError` with no source position. The message reports that observation without attributing it to a particular entry.
  - A read waiting for dispatch permits points to the effective `replicatorDispatchRate`. While retrying a failed read, the message includes the known batch starting position, the exception class, whether an exception message was absent, and the source broker timestamp to look up. An outstanding read without a recorded failure points to the in-flight tasks. If the stage is unclear, inspect `inFlightTasks` in `stats-internal`.
- The observation window starts when work becomes pending, including after an idle period or a restart. A cursor read waiting for new entries on an idle topic does not start the window. Until the broker observes progress, a producer startup retry, or a full minute of pending work, health is `null`.

#### Extension to topic internal stats

`GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/internalStats` adds a top-level `replicators` map to `PersistentTopicInternalStats` for a non-partitioned persistent topic or an individual partition. Each key is a target cluster name. For a partitioned topic, `GET /admin/v2/persistent/{tenant}/{namespace}/{topic}/partitioned-internalStats` omits `replicators` at the top level. Each returned partition exposes its own map at `partitions[partitionTopic].replicators`. The existing Java Admin methods, authorization and topic loading behavior apply. The example shows the new field for one target.

```json
{
  "replicators": {
    "cluster-b": {
      "producerQueueSize": 5,
      "producerQueueMaxSize": 1000,
      "sendingMessageSchemaCompatible": true,
      "lastProducerStartFailure": {
        "timestamp": 1793780000000,
        "message": "AuthorizationException: Producer creation was denied. Check the replication identity's publish permission on the target."
      },
      "lastReadFailure": {
        "timestamp": 1793780040000,
        "message": "readPos=100:195 ManagedLedgerException: Bookie operation timeout error code: -23"
      },
      "lastPublishFailure": {
        "timestamp": 1793780120000,
        "message": "TopicTerminatedException"
      },
      "lastProducerRetry": {
        "timestamp": 1793780129050,
        "reason": "DEDUPLICATION_UNDECIDED",
        "sourcePosition": "100:206"
      },
      "inFlightTasks": [
        {
          "readPos": "100:201",
          "readingEntries": 10,
          "entries": 10,
          "completedEntries": 5,
          "skipReadResultDueToCursorRewind": false,
          "readException": null
        }
      ]
    }
  }
}
```

The map lists the outbound targets selected by the topic's effective replication rules. If a target has no observable replicator yet, the map includes the target's key with a `null` value, for example `{"replicators":{"cluster-b":null}}`. This can happen if opening the replication cursor fails before the instance is created. Once an instance exists, its map value is an object with all eight response fields, even if its producer has not started.

When the policy removes a target, its entry remains visible while the existing replicator shuts down, so operators can inspect its unfinished reads in `inFlightTasks`. The entry disappears when that replicator reaches `TERMINATED` if the target is still absent from the effective policy. The map is empty (`{}`) when the topic has no outbound targets or retiring replicators left.

| Response field | JSON type | Meaning and use |
| --- | --- | --- |
| `producerQueueSize` | integer or null | Number of source ledger entries pending in this producer's send queue. An entry containing a batch of messages occupies one queue slot, regardless of the number of messages in the batch. Zero means an observed empty queue. An absent producer yields `null`. Repeated samples show whether the queue stays close to capacity. |
| `producerQueueMaxSize` | integer | Capacity assigned to this replicator's producer queue, measured in source ledger entries. Changing the broker setting applies to newly created replicators, so the observed capacity can differ across instances. |
| `sendingMessageSchemaCompatible` | boolean or null | Derived from the current `schemaState` of the message at the head of the replication producer's send queue. `Ready` maps to `true`, `Broken` to `false`, and `None` to `null`. An absent producer or head message also yields `null`. |
| `lastProducerStartFailure` | object or null | Most recent failure while preparing the target topic or creating the replication producer. Its `message` includes the exception class and a source-broker diagnostic, even after a later attempt succeeds. The broker builds this text from the startup stage, exception class and known topic metadata. For example, a partition count mismatch includes the two counts. Exception messages from clients or remote services can contain credentials or other private data and are excluded from this record. |
| `lastReadFailure` | object or null | Most recent failure while submitting or completing a replication cursor read. Its `message` includes the failed batch's starting position as `readPos=ledgerId:entryId` when known, followed by the exception class and its text. A batch can span several entries. If the exception supplies no text, the message ends with `(no exception message)`. |
| `lastPublishFailure` | object or null | Most recent failure when submitting or completing a replicated send to this target. Its `message` contains only the exception class name. For example, sending to a terminated target topic can raise `TopicTerminatedException` and trigger a cursor rewind. On `InvalidMessageException`, the replicator skips the entry and preserves the previous failure record. The send callback updates `lastReplicationSucceededAt` when it calls `cursor.asyncDelete()` for that entry. |
| `lastProducerRetry` | object or null | Latest explicit target send error that caused the replication producer to reconnect and retry, or to resend after verifying a checksum. `timestamp` is the source-broker observation time in epoch milliseconds. The string `reason` is `DEDUPLICATION_UNDECIDED` when the target explicitly reports an inconclusive check, otherwise the Pulsar server error name, such as `PersistenceError` or `ChecksumError`. The string `sourcePosition` is the source entry (`ledgerId:entryId`) identified by the target, or `null` when the target supplied no position. For example, checksum verification can fail before the target reads the entry metadata. |
| `inFlightTasks` | array | Unfinished read batches in queue order. A replicator that is `DISCONNECTED` after an idle period can still list a cursor read waiting for new entries, with `entries` set to `null`. A replicator with no unfinished reads returns `[]`. Comparing task lists helps identify a batch that has stopped progressing. |

A replicated message that needs no schema registration reports `true` while at the queue head. Once the queue advances, the field describes the new head. The source can report this from local state.

A target can delay an acknowledgement without returning an error. In that case `lastProducerRetry` retains its previous value, initially `null`. Retrying an outstanding send keeps its callback pending, so `lastPublishFailure` can also be `null`. A retry record survives recovery, cursor rewinds and producer reconnects until a newer observed retry replaces it or the replicator instance is discarded. A healthy replicator can therefore report a historical retry.

Each failure record contains exactly two fields, a 64-bit integer `timestamp` in Unix epoch milliseconds on the source broker and a string `message`. Callers authorized to read topic internal stats can see the full text of a read exception. Each outbound replicator keeps the latest record of each kind in memory until another failure of the same kind replaces it. The records survive retries, successful operations, cursor rewinds and producer reconnects within that instance. Each field is `null` until the instance observes its first failure of that kind.

Each task has the following six fields.

| Task field | JSON type | Meaning and use |
| --- | --- | --- |
| `readPos` | string or null | Starting position of this read, formatted as `ledgerId:entryId`, or `null` if unavailable. It helps identify where reads stall or repeat. |
| `readingEntries` | integer | Number of entries requested in the batch. It shows the amount of read capacity reserved while the result is outstanding. |
| `entries` | integer or null | Number of entries in the read result. `null` means the result is pending. Zero means the task has an empty result, including a result cleared during recovery. |
| `completedEntries` | integer | Entries whose local processing has finished. This includes successful sends, skipped entries and failure cleanup. |
| `skipReadResultDueToCursorRewind` | boolean | Whether recovery or shutdown has marked the read result for discard. This explains why a batch can be read again from an earlier position. |
| `readException` | string or null | Exception text for this batch, or its simple class name if the exception message is `null`. The value is `null` until the batch records a read failure. |

### Binary protocol

`CommandSendError` gains two optional fields for replicated publishes. `source_position` (field 5, `MessageIdData`) carries the source ledger ID and entry ID known to the target. `deduplication_undecided` (field 6, boolean, default `false`) is set when the target cannot determine whether this publish was already persisted. The existing error code, sequence ID and error text retain their meanings. A sequence ID can occur in entries from different source producers, so the receiver does not use it as a ledger position.

# Monitoring

Compare successive samples for the same topic or partition and target cluster.

1. **Backlog after enabling replication.** If `replicationBacklog` is large, use `pulsar-admin topics info-internal <topic>` on the source to look up the replication cursor’s creation time. With the default cursor prefix, the field is `cursors["pulsar.repl.<target-cluster>"].creationDate`. Check which `replicationStartAt` value was in effect when that cursor was created. With the default `latest`, the backlog accumulated after cursor creation. With `earliest`, it can also include retained messages published before replication was enabled. A shrinking backlog shows that the replicator is catching up. Use `lastReplicationSucceededAt` to see when the producer's send callback last requested a cursor delete.
2. **Replication producer startup.** If `replicatorHealth.healthy` is false, follow its `message`. To investigate an earlier startup failure after recovery, use the explanation in `replicators[cluster].lastProducerStartFailure.message` and look up the source broker log at the recorded timestamp.
3. **Idle replicator.** If replication was working, `replicationBacklog` has stayed at zero, and `replicatorState` changes to `DISCONNECTED`, the broker has likely closed the idle replication producer to conserve resources. The producer is then no longer registered on the target topic.
4. **Stalled schema registration.** If `producerState` stays in `REGISTERING_SCHEMA` with a backlog, inspect `replicators[cluster].sendingMessageSchemaCompatible` in topic internal stats. If the field is `false`, compare the source and target schemas and the target compatibility policy. If it is `null`, the broker has no registration result for the queue head. Use the target broker logs to trace the pending registration. The field describes only the queue head, even when the producer is registering a schema for a later message.
5. **Stalled cursor read.** If a backlog persists, `lastCursorReadStartedAt` stays at the same non-null timestamp, and the same `readPos` in `inFlightTasks` continues to show `null` for `entries`, that read is still waiting for a result. After a failed batch leaves the queue, `lastReadFailure.message` still identifies the exception and, when known, the starting position. Use `lastReadFailure.timestamp` to find the read in source broker logs. Repeated failures at the same starting position narrow the search to one batch. An idle cursor waiting for new messages reports `null` for `lastCursorReadStartedAt`.

   When transactions are enabled, an open transaction can hold the maximum readable position behind the ledger's `lastConfirmedEntry` even as the replication backlog grows. Both `topics stats` and `topics stats-internal` omit this limit. To see it, query the transaction buffer on the source cluster for the affected topic or individual partition.

   ```bash
   pulsar-admin transactions transaction-buffer-stats --topic persistent://example-tenant/example-ns/orders-partition-0
   ```

   The response gives `maxReadPosition` as `ledgerId:entryId`. Compare it with the replication cursor's `readPosition` in `topics stats-internal`. If the cursor's next entry is beyond `maxReadPosition` but at or before `lastConfirmedEntry`, that entry is stored and replication must wait for the transaction buffer's read limit to advance.

6. **Stalled sends.** While a backlog persists, use `lastSendStartedAt` to see whether the replicator is still submitting new sends. Replication sends have no acknowledgement timeout. If the producer queue stays nonempty and replication delay grows, check for outstanding sends even if `lastPublishFailure` has no new entry. A `lastReplicationSucceededAt` later than the failure means a subsequent send callback requested a cursor delete after a successful send or an `InvalidMessageException`.
   If `lastProducerRetry.reason` is `DEDUPLICATION_UNDECIDED`, check the target topic’s `pendingAddEntriesCount` and `lastConfirmedEntry` while watching the source cursor. A retry and a stationary cursor for the same source entry can indicate that the target is still completing an earlier write. Compare timestamps with subsequent progress before treating a retained retry as current.

7. **Send queue near capacity.** If `producerQueueSize` stays close to `producerQueueMaxSize` across samples, the source is usually submitting messages faster than the producer can send them to the target and receive acknowledgements.
8. **Replication blocked by an incompatible schema.** If `sendingMessageSchemaCompatible` stays `false` while the queue is stalled, the head message's schema state is `Broken`. Retrying registration can hold up later sends. A value of `true` means the head message is ready to send as far as its schema is concerned. It may still be awaiting acknowledgement.

# Backward & Forward Compatibility

## Upgrade

- **Java implementations of `ReplicatorStats`.** Each new getter is a Java `default` method that returns `null`. Implementations can override individual getters when they have a value. `NonPersistentReplicatorStats` inherits the same defaults. A source compatibility test will recompile an existing implementation unchanged against the updated interface. A binary compatibility test will keep the implementation compiled against the old interface and verify that calling each new getter through the updated interface returns `null`.
- **Older admin client with a newer broker.** The broker returns the same stats regardless of the client version. The older Java Admin client ignores unknown properties during deserialization, so `pulsar-admin` prints the fields it recognizes and completes without error.
- **Newer admin client with an older broker.** The broker omits the new properties. The Java Admin client leaves them `null`, including the `replicators` map. By default, `pulsar-admin` omits null properties from its output. This also applies to responses served by older brokers during a rolling upgrade or after a rollback.

## Downgrade / Rollback

After a source broker rollback, clients see the stats fields supported by that broker version and treat omitted fields as unavailable. Diagnostic records live in memory and a new replicator starts with empty records. No metadata migration is required.

## Pulsar Geo-Replication Upgrade & Downgrade/Rollback Considerations

Older senders ignore the two optional send-error fields. An updated source connected to an older target reports the error code it receives (for example, `PersistenceError` or `MetadataError`) with `sourcePosition: null`. The specific deduplication reason requires the target’s explicit indication. Upgrading or rolling back either side preserves the existing retry and acknowledgement behavior.
